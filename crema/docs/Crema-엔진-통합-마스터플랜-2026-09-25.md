# Crema 엔진 통합 마스터플랜 — Hermes 포크를 Crema 안으로

작성: 2026-09-25 · 상태: **구현 중 — 1~5단계 코드·CI 통과(`cc534b5`), 로그인 정책 수정본 CI 전, 상류 테스트 대조 미완 (2026-09-26 중지)** · 선행 문서: [배포 전제조건·SSP 점검](Crema-배포-전제조건-SSP-점검-2026-09-25.md)

점검 문서의 수정 중 Hermes 연결에 관한 것(게이트웨이 켜기, Hermes 위치 판정, 버전 확인, 설치 훅)은 이 계획에서 엔진 내장으로 대체된다. 글꼴·기본값·저장 경고·예시 답변 제거는 그대로 유지한다.

## 1. 의도와 성공

**문제.** Crema는 사용자 PC에 따로 설치된 Hermes에 기대어 동작한다. 깨끗한 Windows에서 설치본을 검증하자 Hermes 공식 설치 스크립트가 세 번 연속 다른 이유로 실패했다(실패를 숨김 → PowerShell 7 모듈 경로 → 고정 버전 체크아웃). 성공 경로의 가장 큰 부분이 우리가 고칠 수 없는 남의 설치 과정에 걸려 있다. 상류 Hermes는 하루 2,287커밋이 쌓일 만큼 빠르게 바뀐다.

**결정(사용자, 2026-09-25).**
- Hermes를 포크해 Crema에 통합한다. **별도 Hermes 설치는 없애고 Crema만 남긴다.**
- Hermes 전체가 아니라 **필수 뼈대와 도구만** 가져오고, 필요해지면 나중에 그 부분만 가져와 붙인다.

**성공.** Crema 설치 파일 하나로 어떤 Windows PC에서도 다음이 된다. 기준은 깨끗한 Windows CI와 이 PC의 실제 사용 경로다.
1. 설치할 때 git·PowerShell 스크립트·Hermes 다운로드가 필요 없다.
2. 첫 실행에 엔진이 자동으로 켜지고 "연결됨"이 된다. "Hermes 연결 켜기"는 없다.
3. Provider에 로그인하면 첫 질문에 실제 답이 온다.
4. 도구(파일·터미널)는 승인 요청을 거쳐 실행된다.
5. 재부팅·재실행 뒤에도 대화와 로그인이 유지된다.
6. 사용자가 따로 쓰는 Hermes(이 PC의 텔레그램 봇 등)와 서로 간섭하지 않는다.

## 2. 기술 검토 — "필요한 부분만 가져와 붙이기"가 좋은 방식인가

### Hermes 구조에서 확인한 사실 (a25cf4d, 0.21.4)
| 영역 | 사실 | 뜻 |
|---|---|---|
| 도구 | `tools/*.py`가 `tools/registry.py`에 **스스로 등록**하고, `model_tools.py`가 시작할 때 `discover_builtin_tools()`로 전부 불러온다. 켜고 끄기는 `toolsets.py`와 `config.yaml` | 불러오기를 **명시적 허용 목록**으로 바꾸면 도구를 파일 단위로 넣고 뺄 수 있다 |
| Provider | `hermes_cli/auth.py`의 `PROVIDER_REGISTRY` 행 + `agent/transports/*` 전송 + 로그인 흐름별 파일(`auth_codex.py` 등). 단 `auth.py`가 모든 로그인 흐름을 **맨 위에서 한꺼번에 import** | Provider도 파일 단위로 붙일 수 있다. 처음 한 번 `auth.py`의 한꺼번에 불러오기를 끊어야 한다 |
| 공통 기반 | `hermes_cli`가 중심축이다. `agent/` 122개, `tools/` 135개 파일이 import한다(auth, config, runtime_provider, model_switch, inventory, tools_config, plugins, env_loader 등) | 자체 엔진으로 새로 짜면 로그인(`agent/credential_pool.py` 약 3,000줄)·승인·세션 저장을 전부 다시 만들어야 한다 |
| 대화 실행 API | `gateway/platforms/api_server.py`(aiohttp)가 게이트웨이 안에서 돈다. 단독 실행은 가능해 보이나 `_create_agent()`가 `gateway/run.py`의 도우미 5개를 불러와 게이트웨이 전체(믹스인 약 20개)가 딸려 온다 | 도우미 몇 개를 옮기고 **자체 실행기**를 쓰면 게이트웨이 없이 돌릴 수 있다 |
| 설정 API | `hermes serve`는 FastAPI 대시보드 전체(라우터 약 30개, 시작 작업 다수). Crema가 쓰는 건 `web_routers/`의 `oauth.py`·`config_env.py`·`models.py`·`audio.py` 네 개뿐 | 이 네 라우터만 올린 작은 앱으로 충분하다 |
| 데이터 위치 | 모든 파일이 `get_hermes_home()`(`HERMES_HOME` 우선)을 따른다: `state.db`, `response_store.db`, `config.yaml`, `.env`, `auth.json` | 엔진에 Crema 전용 `HERMES_HOME`을 주면 사용자 Hermes와 분리된다 |
| git | 실행에는 git 체크아웃이 필요 없다(`code_skew`는 git이 없으면 아무것도 안 함) | 설치본에 git이 필요 없다 |
| 라이브러리 | aiohttp는 기본 의존성이 아니라 선택 묶음에만 있다. fastapi·uvicorn은 대시보드용 | 엔진 의존성 목록을 새로 정해야 한다 |

### 세 방식 비교
| 방식 | 기능 하나 붙이는 비용 | 상류 수정 따라가기 | 처음 만드는 비용 | 판단 |
|---|---|---|---|---|
| **가지치기 포크** — 경로·이름 그대로, 안 쓰는 것만 삭제, 허용 목록으로 켬 | 상류의 같은 경로 파일을 되살리고 허용 목록에 한 줄 추가 | 경로가 같아 파일별로 비교·반영 가능(`git diff upstream -- 경로`) | 중간: 실행기 작성, import 3곳 끊기 | **추천** |
| 등록부 이식 — 뼈대만 새 구조에 두고 모듈을 옮겨 심음 | 경로가 달라 매번 옮겨 심고 import를 고침 | 경로가 달라 비교가 어려움 | 중간~큼 | 가지치기 포크보다 나은 점이 없음 |
| 자체 엔진 — 새로 짜고 Hermes는 참고 | 기능마다 새로 구현 | 해당 없음 | 큼: 로그인·승인·세션·전송을 다시 만듦 | 부담이 가장 큼 |

**결론.** 원래 자리를 유지하는 **가지치기 포크 + 명시적 허용 목록**이 요청하신 방식을 가장 싸게 실현한다. Hermes가 이미 도구·Provider를 등록 방식으로 붙이고, 모든 경로가 `HERMES_HOME` 하나를 따르기 때문이다. 대신 `hermes_cli` 중심축은 줄일 수는 있어도 없앨 수 없다. 처음에 공통 기반이 어느 정도 딸려 오는 것은 받아들여야 한다.

**붙이는 규칙.**
- 가져온 파일은 상류와 같은 경로·이름을 유지하고, 우리 수정은 최소로 한다.
- 새 기능을 붙일 때는 필요한 파일과 그 파일의 의존성만 되살린다.
- 허용 목록(도구·Provider·라우터)에 추가하고, 그 기능의 CI 검증을 함께 넣는다.
- 포크의 `CREMA.md`에 기준 상류 커밋, 되살린 파일 목록, 우리 수정 목록을 기록한다.

## 3. 목표 구조

```text
Crema 설치 파일
 ├─ Crema 앱 (Tauri)
 └─ 엔진 (포크한 Hermes 뼈대 + 내장 Python 실행 환경)

실행: Crema가 시작할 때 엔진을 직접 켜고, 끝날 때 함께 끈다
 ├─ 빈 포트 + 무작위 토큰을 엔진에 넘김 (파일에 키를 쓰지 않음)
 ├─ 엔진 데이터: Crema 전용 HERMES_HOME (%LOCALAPPDATA%\local.agentclient.prototype\engine)
 └─ 한 프로세스 안에 대화 실행 API(aiohttp)와 설정 API(FastAPI 4개 라우터)
```

없어지는 것:
- 설치 훅의 Hermes 설치
- `hermes_home()`·`enable_local_api`·`hermes serve` 따로 켜기
- 게이트웨이 서비스·예약 작업
- `.env` 키 추가, 고정 포트 8642, Hermes 버전 확인
- "Hermes 연결 켜기"

## 6. 단계

각 단계는 **실제 사용 경로(깨끗한 Windows CI 설치본, 이 PC는 격리 밖 실행)**에서 확인되어야 끝난다.

1. **기준선 잠금** — 지금 이 PC에서 되는 기능 목록과 결과를 적는다(대화, 도구 승인, 모델 고르기, Codex 로그인, 첨부, 그림 표시, 세션 삭제, 제목·다음 입력 예측). D1~D8을 확정한다.
2. **엔진 포크와 가지치기** — 포크 → 안 쓰는 폴더·파일 삭제 → 자체 실행기(게이트웨이 없이 대화 API + 설정 라우터 4개) → import 3곳 끊기(`gateway/run.py` 도우미 이동, 도구 허용 목록, `auth.py` 로그인 흐름) → 남긴 모듈의 상류 테스트 통과 → 소스 상태로 임시 `HERMES_HOME`에서 실행 확인.
3. **패키징** — CI에서 내장 Python과 엔진 의존성을 만들어 설치 파일에 넣는다. 설치 파일 크기와 첫 시작 시간을 잰다. 깨끗한 Windows에서 엔진이 혼자 뜨는지 확인한다.
4. **Crema 연결 교체** — Tauri가 엔진을 켜고 끄며 포트·토큰을 넘긴다. Hermes 전용 코드와 설치 훅을 지우고 연결 설정 화면을 단순하게 한다. 첨부는 엔진 데이터 폴더로 넣는다.
5. **실제 경로 검증** — CI: 설치 → 실행 → 엔진 연결 → (D8) 실제 답변 → 도구 승인 → 재실행. `%LOCALAPPDATA%\hermes`가 생기지 않는지도 본다. 이 PC: 격리 밖 설치, 기존 Hermes(게이트웨이·텔레그램)가 계속 도는지, 기준선 기능이 그대로인지 확인한다.
6. **전환과 릴리스** — 0.2.0을 CI에서 릴리스한다. 이 PC 전환(새 엔진에서 Codex 로그인). README·문서를 갱신하고 옛 Hermes 연동 흔적을 정리한다.
