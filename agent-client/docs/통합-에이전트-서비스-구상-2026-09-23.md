# 아름다운 인터페이스와 업무 메모리를 결합한 통합 에이전트 서비스

작성일: 2026-09-23 · 구상 정리 v0.2 · 작업명: Agent Client · 정식 제품명 미정

> **아름다워서 선택하고, 나를 기억해서 계속 쓰며, 함께 좋아지는 제품이어서 기꺼이 구독하는 에이전트 서비스.**

이 문서는 Telegram 대화창 커스터마이징에서 출발해 범용 에이전트 클라이언트, 업무 메모리를 갖춘 통합 서비스, 구독과 커뮤니티 운영으로 발전한 구상을 정리한 현재 제품·사업 방향 문서입니다. 앞선 [클라이언트 중심 제품 기획 v0.1](제품기획-2026-09-23.md)의 후속 문서이며, 구현 작업지시서나 출시 승인 문서는 아닙니다.

사용자가 명시한 요구와 경험은 **출발점**, 그로부터 발전시킨 상품·운영 설계는 **제안**, 아직 선택하지 않은 가격·기술·운영 조건은 **미정**으로 구분합니다. 제안에 적었다는 이유로 구현·모집·공개·결제·배포가 승인된 것으로 해석하지 않습니다.

## 1. 한눈에 보는 구상

| 질문 | 현재 구상 |
|---|---|
| 무엇을 만드는가? | 예쁜 대화·작업 화면, 편한 연결, 지속적인 업무 메모리, 신뢰할 수 있는 실행 방식을 하나로 묶은 에이전트 서비스 |
| 누구에게 먼저 제공하는가? | Hermes 등 에이전트를 이미 쓰는 개인·소규모 팀. 이후 설치·설정을 어려워하는 일반 사용자로 확장 |
| 왜 처음 선택하는가? | 보기 좋고, 갖고 싶고, 읽기 편하며, 자신의 취향대로 바꿀 수 있기 때문 |
| 왜 계속 사용하는가? | 이전 업무·결정·지식·실패와 교훈을 다시 설명하지 않고 다음 작업에 활용할 수 있기 때문 |
| 무엇에 돈을 내는가? | 직접 설치·연결·관리할 수고 없이, 더 넓고 깊게 이어지는 메모리와 업무 경험을 편하게 누리는 가치 |
| 어떻게 수익화하는가? | 무료 / 중간 / 프리미엄의 3단계 구독 구상. 구체 가격·한도는 미정 |
| 어떻게 지속적으로 발전시키는가? | 창업자가 제품의 기본 품질을 만들고, 디자인·기능 기여를 받아 개선하며, 구독 수익으로 운영과 기여 보상을 지원 |
| 지금 하는 일은 무엇인가? | 구상을 일관된 문서로 정리하는 일. 서비스 구현·운영 전환·출시·공개 모집은 별도 단계 |

핵심은 오픈소스 부품의 개수가 아닙니다. 사용자가 그 부품을 알아보거나 조립하지 않아도, **좋아 보이는 제품을 열어 자연스럽게 쓰고 그동안의 일을 이어갈 수 있는 경험**이 상품입니다.

## 2. 출발점: 이미 체감한 가치를 다른 사람도 쉽게 누리게 한다

### 사용자의 실제 경험

사용자는 메인서버의 Hermes와 로컬 데스크톱의 Hermes에서 GBrain을 연결해 이미 잘 사용하고 있다고 설명했습니다. 업무 맥락·결정·시도·실패·교훈이 이어지는 장점을 직접 활용하고 있으며, 이제 GBrain이 없으면 상당히 불편해지는 단계입니다.

따라서 이 구상의 출발점을 “GBrain이 쓸모 있는지부터 알아보자”로 되돌리지 않습니다. **사용자가 이미 누리는 가치를 다른 사람도 쉽게 경험하게 만드는 것**이 과제입니다. 다만 이 진술은 사용자의 사용 경험에 근거하며, 이번 문서 작업에서 두 설치 환경을 새로 운영 점검했다는 뜻은 아닙니다.

### 시장 기회에 대한 관찰

AI를 깊이 사용하는 일부 개발자는 이런 도구를 찾아 직접 설치하고 연결할 수 있습니다. 그러나 대부분의 사람은 필요성을 명확히 인식하지 못하거나, 알아도 조사·설치·연결·관리까지 하지 않습니다. “찾아보면 할 수 있다”와 “실제로 편하게 쓰고 있다” 사이에는 큰 간격이 있다는 것이 사용자의 관찰입니다.

우리가 상품화하려는 것은 GBrain의 이름이나 설치 방법이 아니라 그 간격을 없앤 결과입니다.

- 내가 어떤 일을 했고 왜 그렇게 결정했는지 다시 설명할 필요가 줄어듭니다.
- 예전에 실패한 방식과 배운 점을 다음 작업에 활용할 수 있습니다.
- 읽고 모은 정보가 흩어져 끝나지 않고, 필요할 때 업무 맥락과 함께 돌아옵니다.
- 기기나 대화가 바뀌어도 나와 프로젝트를 이해하는 경험이 이어집니다.

새롭게 확인해야 할 것은 기본 기능의 존재가 아니라 **다른 고객도 이 가치를 쉽게 경험하는지, 믿고 지속적으로 사용하는지, 어느 범위에 얼마를 지불하는지**입니다.

## 3. 선택을 만드는 디자인, 지속을 만드는 효용

사용자의 핵심 관점은 다음과 같습니다.

> 사람은 먼저 호감과 감각으로 끌리고, 이후 실질적인 이유를 통해 자신의 선택을 납득하고 유지한다. 예쁜 디자인은 선택의 입구이고, 메모리의 효용은 그 선택을 오래 지속시키는 이유다.

시스템 1·시스템 2는 이 제품의 선택 경험을 설명하는 기획 관점으로 사용합니다. 모든 구매가 반드시 같은 순서로 일어난다는 법칙이나, 디자인만 좋으면 결제한다는 보장으로 단정하지 않습니다.

| 단계 | 사용자가 느껴야 하는 것 | 제품이 보여줄 것 |
|---|---|---|
| 첫인상 | “예쁘다. 한번 써 보고 싶다.” | 정돈된 대화 화면, 좋은 글꼴과 간격, 매력적인 테마, 실제 사용 장면 |
| 첫 사용 | “생각보다 쉽다.” | 복잡한 설명 없이 시작하고 연결되는 흐름, 즉시 이해되는 다음 행동 |
| 가치 발견 | “내가 전에 했던 일을 알고 있네.” | 과거 결정과 관련 자료가 현재 작업에 실제로 도움이 되는 경험 |
| 결제 판단 | “내 업무에 이 정도면 돈을 낼 만하다.” | 늘어나는 활용 범위, 줄어드는 재설명과 검색 수고, 명확한 요금·포함 범위 |
| 지속 사용 | “내 맥락이 잘 이어진다.” | 기억의 정확성·수정 가능성, 안정적인 복귀, 축적된 설정과 프로젝트 맥락 |
| 애착과 참여 | “이 제품이 계속 좋아졌으면 좋겠다.” | 개선 내용, 채택된 기여, 참여 기회, 운영·개발에 대한 신뢰 |

이 관점에서 디자인은 기능 개발이 끝난 뒤의 포장이 아닙니다. 초기 제품부터 확보해야 할 핵심 품질입니다. 동시에 예쁜 화면으로 기능 부족이나 과금 조건을 감추지 않습니다. 호감은 입구를 만들고, 실제로 유용한 경험이 그 약속을 지킵니다.

## 4. 제품을 구성하는 여섯 가지 가치

| 구성 요소 | 제품 안에서 맡을 역할 | 고객에게 전달할 표현 |
|---|---|---|
| Hermes | 요청을 이해하고 도구를 사용해 업무를 수행하는 실행 기반 | “대화에서 끝나지 않고 일을 진행합니다.” |
| GBrain | 업무 맥락·결정 이유·지식·실패와 교훈을 장기적으로 축적하고 필요할 때 활용하는 기반 | “전에 했던 일을 다시 설명하지 않아도 됩니다.” |
| 문제해결 방식 | 보이는 증상과 원인을 구분하고, 근거를 확인하고, 해결 결과를 검증하는 품질 규칙 | “왜 문제가 생겼고 무엇을 확인했는지 이해할 수 있습니다.” |
| SSP | 시도와 교훈을 이해 가능한 공식 작업 경로에 반영하고 상태·복구·기존 성공을 보존하는 운영 원칙 | “같은 일을 처음부터 헤매지 않고 이어갑니다.” |
| 최소코드 지침 | 필요한 변경인지 먼저 판단하고, 기존 구현·표준 기능을 재사용하며, 불필요한 코드를 늘리지 않는 개발 원칙 | “복잡한 기능을 덧붙이기보다 필요한 일을 단순하고 안정적으로 처리합니다.” |
| UX·디자인 | 연결·대화·읽기·판단·승인·복귀를 편하게 만들고 취향에 맞게 표현하는 제품의 접점 | “쓰고 싶고, 오래 읽어도 편한 나만의 작업 공간입니다.” |

SSP를 “분기나 복구가 없는 단 한 줄의 경로”로 해석하지 않습니다. 최소코드도 단순히 코드 줄 수를 줄이라는 뜻이 아니며, 코딩 업무에 적용할 원칙을 모든 일반 업무에 억지로 노출하지 않습니다.

Hermes·GBrain·운영 지침을 고객이 각각 이해해야 제품을 쓸 수 있게 만들지 않습니다. 내부 구성은 필요한 사람에게 설명하되, 첫 화면과 상품 소개는 고객의 일과 결과를 중심으로 작성합니다. 이 조합이 오류를 없애거나 완전한 기억을 보장한다고 약속하지 않습니다.

## 5. 고객과 제품의 확장 방향

### 첫 고객: 기존 에이전트 사용자

명시적으로 선택한 초기 고객은 Hermes 등 에이전트를 이미 쓰는 개인·소규모 팀입니다. 이들은 현재 도구의 가독성·모바일 연결·맥락 단절을 비교해 평가하기 쉽고, 초기 피드백과 커뮤니티의 출발점이 될 수 있습니다.

Hermes를 첫 연결 대상으로 삼고, 이후에는 실제 연동 기능이 있는 다른 에이전트로 넓히는 범용 클라이언트 지향을 유지합니다. OpenClaw 등은 확장 후보이며, 모든 에이전트를 지금 지원한다는 뜻은 아닙니다.

### 더 큰 고객층: 설치·연결을 원하지 않는 사람

장기적으로는 에이전트나 GBrain을 직접 설치하지 않아도 업무 기억의 가치를 누리고 싶은 사람에게 도달하려 합니다. 이때의 목표 경험은 “서버와 API를 공부한 뒤 사용”이 아니라 “가입하고 필요한 자료나 업무를 연결한 뒤 사용”입니다.

이를 위해 에이전트·메모리를 대신 운영하는 관리형 서비스가 필요할 수 있습니다. 다만 운영 방식과 비용은 아직 정하지 않았습니다. **기존 사용자의 자기 서버 연결 경로와 일반 사용자의 간편한 서비스 경로는 구별하되, 일관된 앱 경험을 제공하는 방향**을 제안합니다.

초기 고객과 장기 확장 고객을 혼동해 모든 것을 첫 버전에 넣지 않습니다. 기존 사용자만 쓸 수 있는 복잡한 설정 경험을 일반 사용자용 완성형으로 홍보하지도 않습니다.

## 6. 디자인과 읽기 경험의 기준

### 반드시 이어받을 대화 화면

- 에이전트 답변은 **본문 영역의 전체 너비**를 사용하며, 답변 전체를 감싸는 말풍선은 없습니다. 큰 화면에서는 편하게 읽을 수 있는 본문 최대 폭과 좌우 여백을 둡니다.
- 사용자 요청은 오른쪽의 단순한 말풍선으로 구분합니다. 기본 최대 폭은 본문 영역의 약 60~70%, 기준값은 3분의 2입니다. 짧은 요청까지 그 폭으로 늘이지 않습니다.
- 밝은 기본 화면은 사용자가 제공한 Codex 설정 이미지의 `배경 #FDFDFD / 본문 #202020 / 강조 #339CFF`를 시각 기준으로 삼습니다.
- UI·본문 글꼴의 참조는 HCR, 코드 글꼴의 참조는 NanumGothicCoding입니다. HCR의 배포 권리는 확인 전이므로 제품에 포함하기로 확정하지 않습니다. 글꼴이 없는 기기의 대체 글꼴과 줄바꿈도 확인해야 합니다.
- 폰트 패밀리·크기·굵기뿐 아니라 **자간, 행간, 문단 간격, 본문 폭, 좌우 여백**을 개별적으로 중요하게 다룹니다. 예쁜 색상만으로 디자인 요구를 충족했다고 보지 않습니다.
- Markdown의 제목·강조·목록·인용·링크·표·코드가 실제로 읽기 좋게 표시되어야 합니다. 코드 블록은 전용 글꼴, 복사, 필요한 가로 스크롤을 제공합니다.

이 기준은 시각적 취향과 읽기 경험의 참조입니다. Codex의 로고·공식 브랜드를 사용하거나 공식 제품으로 보이게 만드는 구상이 아닙니다. 참조 이미지에서 확인되지 않은 글자 크기·자간·행간을 실제 Codex 설정값처럼 만들지 않습니다.

### 개인화와 적응형 표현

완성도 높은 기본 디자인을 먼저 제공하고, 읽기·코딩·야간 같은 프리셋과 세부 조정을 함께 제공하는 방향입니다. 폰트와 간격을 고치기 위해 여러 설정 화면을 헤매지 않게 하고, 변경 결과를 즉시 확인하고 기본값으로 되돌릴 수 있게 합니다.

설명·코드·표·이미지·동영상·파일·진행 상태는 성격에 맞게 보여줍니다. 필요하면 Jev 등 판단용 모델이 준비된 표현 방식 중 적절한 것을 고르는 적응형 UI를 검토합니다. 이는 채택이나 성능 검증이 끝난 기술이 아니라 후보입니다.

표현 판단은 원문을 몰래 다시 쓰거나 임의의 HTML·실행 코드를 생성하는 기능과 구별합니다. 이미 구조가 정해진 데이터는 그대로 활용하며, 판단 기능이 없어도 기본 Markdown과 필수 작업 상태는 정상적으로 보여야 합니다. 승인·중단·오류의 의미와 사용자 설정은 표현 모델이 바꾸지 못하게 합니다.

### 멀티OS와 가벼움

HTML 기반 공통 UI를 바탕으로 Windows·macOS·Android·iOS를 지향합니다. 그러나 같은 화면 코드를 쓴다는 것이 네 OS에서 연결·키보드·파일·알림·결제가 자동으로 검증된다는 뜻은 아닙니다. 출시 순서와 앱 포장 기술은 미정입니다.

가벼움은 설치 용량뿐 아니라 시작 속도, 입력 반응, 긴 대화의 스크롤, 메모리·배터리 사용, 읽는 사람의 부담까지 포함합니다. 대형 편집기나 모든 미디어 기능을 처음부터 불러오지 않고 필요한 기능을 필요한 때 제공하는 방향입니다. 실제 성능 목표는 제품 범위와 기기를 정해 측정합니다.

키보드 조작, 선명한 초점 표시, 충분한 대비, 큰 글자, 터치 영역, 과한 움직임을 줄이는 설정은 기본 품질입니다. 아름다움을 이유로 가독성·접근성을 포기하지 않습니다.

## 7. 심리스한 연결과 최초 가치 경험

API는 연결을 위한 수단입니다. 고객이 제품에서 느껴야 하는 것은 API 주소를 찾아 입력하는 능력이 아니라 “내 에이전트를 어렵지 않게 만나고, 언제든 이어서 쓸 수 있다”는 경험입니다.

기존 Hermes 사용자는 소유자가 연결 준비를 한 뒤 초대 링크·QR 등으로 기기를 연결하는 흐름을 우선 검토합니다. 일반 사용자용 관리형 경로는 가입 후 바로 시작하는 것을 목표로 합니다. 초대·기기별 접근 해제는 **제품이 설계해야 할 기능**이며, Hermes API를 켜는 것만으로 제공되는 완성 기능이라고 설명하지 않습니다. QR만으로 사설 서버에 접속할 수 있는 것도 아닙니다.

실제 연결에서는 로그인, 접근 범위, 연결 실패 안내, 기기 분실 시 해제, 화면을 닫았다가 돌아왔을 때 같은 작업을 다시 찾는 경험까지 이어져야 합니다. 연결 복구가 같은 명령의 중복 실행으로 바뀌어서는 안 됩니다.

### 처음 느끼게 할 핵심 경험 — 제안 시나리오

1. 예쁜 실제 대화 화면을 보고 앱을 열어 간단한 업무를 시작합니다.
2. 필요한 작업이나 자료를 연결하고, 무엇을 기억할지 이해할 수 있습니다.
3. 대화 중 결정한 내용·관련 자료·유용한 교훈이 허용된 범위에서 기록됩니다.
4. 다음에 관련 업무를 요청하면, 이전 결정과 실패 이유가 답변과 행동에 반영됩니다.
5. 사용자는 “그 얘기를 다시 하지 않아도 되는구나”를 경험하고, 필요한 경우 기억의 근거를 열어 확인하거나 수정합니다.

예를 들어 지난 제안서에서 보류한 조건을 다음 제안서에 반영하거나, 이전에 실패한 접근의 이유를 확인한 뒤 다른 방법을 선택하는 장면입니다. 데모에서는 예시 데이터임을 표시하고, 실제 고객에게는 정말 저장·조회·활용한 기억만 보여줍니다.

처음부터 기능 설명과 설정을 모두 보여주기보다 현재 행동에 필요한 것부터 제시합니다. 복잡함을 숨겨 없어진 것처럼 만들지 않고, 제품과 운영자가 맡아 사용자의 부담을 줄입니다.

## 8. 메모리를 핵심 상품 가치로 만든다

### 무엇을 기억하는가

기억의 후보는 진행한 업무와 결과, 결정과 이유, 시도와 실패, 배운 교훈, 프로젝트 맥락, 사용자의 선호, 허용된 자료에서 얻은 지식입니다. “모든 일을 기억한다”는 비전은 사용자가 연결하고 허용한 업무 범위에서 구체적인 기능으로 실현합니다. 연결하지 않은 앱이나 모든 생활 정보를 저절로 수집한다는 뜻이 아닙니다.

대화 로그를 오래 저장하는 것과 업무 메모리를 제공하는 것은 다릅니다. **필요한 내용을 찾고, 현재 상황과 맞는지 확인하고, 실제 답변과 작업에 반영하는 것**까지가 가치입니다. 사실·추정·시점·출처를 구별하고, 최신 지시와 현재 상태가 오래된 기억보다 우선하도록 합니다.

### 고객이 믿고 쓸 수 있는 기억

고객은 필요한 때 무엇을 기억하고 있는지 확인하고, 틀린 내용을 고치고, 기억하지 않도록 하거나 삭제·내보내기 할 수 있어야 합니다. 매번 저장 승인을 반복하게 만들기보다 이해하기 쉬운 기본 범위와 예외 조정을 제공하는 방향입니다.

Hermes의 기존 기록·메모리와 GBrain에 같은 사실을 서로 다른 정본으로 중복 관리하지 않도록 역할을 정해야 합니다. 어느 기억을 어디에 저장하고 언제 불러오는지는 기존 기능을 확인한 뒤 설계합니다. 개인과 팀의 공유 범위도 분명히 구별합니다.

### 무엇을 유료로 제공하는가

유료 가치의 중심은 GBrain이라는 도구에 붙이는 통행료가 아니라, **연결·정리·검색·맥락 활용·동기화·운영을 편하게 누리는 통합 경험과 그 활용 범위**입니다. 기존 사용자가 자신의 Hermes·GBrain에서 이미 쓰는 기능을 일부러 막았다가 유료로 다시 열어주는 방식은 제안하지 않습니다.

메모리는 꾸미기 기능에 딸린 부가 기능이 아니라 요금제 구분의 중심 후보입니다. 동시에 요금이 낮다는 이유로 기억을 일부러 부정확하게 사용하거나 안전한 실행을 빼지 않습니다.

무료판은 일부러 못생기거나 불편하게 만들지 않습니다. 첫인상이 유입의 핵심이므로 무료 사용자도 제품의 디자인과 유용한 기억을 체험할 수 있어야 합니다. 추가 테마나 프리셋은 확장 가치가 될 수 있지만, 기본 가독성을 인질로 삼지 않습니다.

구독 종료·하향 시 새로 사용할 수 있는 범위와 기존 기록의 보관·열람·내보내기 정책을 사전에 분리해 설명해야 합니다. 기록을 잃을 공포나 해지의 어려움으로 구독을 유지시키지 않습니다. 구체 보관 정책은 아직 미정입니다.

## 10. 수익화: 서비스 대가와 지속 발전에 대한 지지

### 구독의 두 가지 의미

첫 번째는 실제 제공되는 편리함과 지속 운영에 대한 대가입니다. 두 번째는 자신이 좋아하는 제품과 커뮤니티가 계속 발전하기를 바라는 지지입니다. 두 의미가 함께 존재할 수 있지만, 고객에게 제공할 기능·한도·지원 책임은 먼저 분명해야 합니다.

따라서 “도네이션처럼 기꺼이 구독하고 싶은 제품”은 좋은 방향이며, **일반 구독과 별도의 선택적 후원은 구별하는 방식**을 제안합니다. 필수 서비스 요금을 후원이라는 말로 모호하게 만들거나, 후원 의사를 이용해 결제를 압박하지 않습니다.

구독 수익이 운영·개발·커뮤니티 기여 보상에 실제로 쓰인다면 이를 이해하기 쉽게 보여줄 수 있습니다. 처음부터 정해진 배분율, 수익 공유, 재단·비영리 조직 설립을 약속한 것은 아닙니다.

### 가격을 정하기 전에 알아야 할 비용

자기 서버를 연결하는 클라이언트와 에이전트·메모리를 대신 운영하는 서비스의 비용은 다릅니다. 모델 호출, 기억 생성·갱신·검색, 저장·백업, 자료 연결, 에이전트 실행, 사용자 지원, 결제·유통 비용, 커뮤니티 보상을 함께 보아야 합니다.

계산의 출발점은 다음과 같습니다.

> 구독 수입 − 실제 결제·유통 비용 − 모델·에이전트·메모리 제공 비용 − 운영·지원·기여 보상 비용

사용자가 모델·서버 비용을 직접 내는지, 구독에 일정 사용량을 포함하는지는 미정입니다. 판매 시에는 고객이 부담할 총비용을 알 수 있어야 합니다. 서비스 범위와 실제 이용량을 확인하기 전 무제한 제공이나 수익성을 약속하지 않습니다.

**이전 v0.1의 월 6,900원·연 59,000원, Free/Plus 2단계와 손익 계산은 순수 클라이언트 가정의 이력입니다. 현재 통합 서비스의 가격이나 수익 전망으로 승계하지 않습니다.** 새 구상에 맞는 가격과 비용은 별도로 검토합니다.

## 11. 디자인과 기능을 함께 발전시키는 커뮤니티

### 사용자가 제시한 아이디어

처음에는 창업자가 출발점을 만들고, 이후 Hermes 사용자 커뮤니티 등에서 디자인과 기능 기여를 받습니다. 디자이너가 UI 제안이나 PR을 올리고, 채택된 기여에 이득을 제공하며, 함께 제품을 발전시키는 구조입니다. 구독은 이 발전을 지속시키는 재원이자 참여 의사가 될 수 있습니다.

이 아이디어를 “너무 나간 계획”으로 배제할 필요는 없지만, 커뮤니티가 생기면 운영과 개발이 자동으로 해결된다고 가정하지도 않습니다. 초기 제품의 매력, 기여하기 쉬운 구조, 공정한 채택 기준이 먼저 있어야 합니다.

### 기여의 진입 경로 — 제안

- 일반 고객은 제품을 쉽게 쓰고 의견을 남깁니다. 모든 고객에게 개발 참여를 요구하지 않습니다.
- 디자이너는 이미지·디자인 파일·프로토타입·이슈로도 제안할 수 있게 합니다. Git과 PR 사용을 모든 디자이너의 필수 조건으로 두지 않습니다.
- 코드 기여가 가능한 사람은 PR로 제안하고, 디자인만 제출된 경우에는 채택 후 구현 PR로 연결합니다.
- 초기 기여 영역은 테마·타이포그래피 프리셋·콘텐츠 뷰어·사용성 개선·문서 등 경계가 선명한 부분부터 검토합니다. 이후 연결 기능·스킬 등으로 확장할 수 있습니다.

### 보상과 지속성 — 후보

채택된 기여의 고정 보상금, 일정 기간 프리미엄 이용, 동의한 기여자 표시와 포트폴리오 활용, 지속 기여자 후원 등이 후보입니다. 금액·예산·지급 조건·권리 처리·선정 기준은 모집 전에 정해야 합니다. 이번 구상이 보상 예산 승인이나 모집 개시는 아닙니다.

처음부터 테마 장터와 매출 배분 플랫폼 전체를 만들 필요는 없습니다. 반복 기여가 실제로 생기고 운영할 수 있을 때 다음 구조를 선택합니다.

### 제품의 일관성을 지키는 책임

기여가 많아져도 최종 제품의 디자인 일관성, 성능, 인증, 결제, 개인·팀 데이터 경계, 출시 품질은 운영 주체가 책임져야 합니다. 모든 PR을 채택하거나 기여 기능을 기본 탑재하는 방식은 아닙니다.

공개할 코드의 범위와 라이선스는 아직 미정입니다. 커뮤니티 개발은 고객의 대화·업무 메모리를 공개한다는 뜻이 아니며, 제품 개발 참여와 고객 데이터 접근은 구별합니다.

## 12. 제품과 커뮤니티가 함께 커지는 순환

```text
창업자가 매력적인 첫 제품과 분명한 기준을 만든다
    → 디자인에 끌린 사용자가 쉽게 시작한다
    → 실제 업무에서 기억의 가치를 경험한다
    → 더 넓은 활용과 지속 운영을 위해 구독한다
    → 수익과 피드백이 운영·개발·기여 보상을 뒷받침한다
    → 커뮤니티의 디자인과 기능이 제품을 더 좋게 만든다
    → 더 좋아진 제품이 새로운 사용자를 끌어들인다
```

이 순환은 자동으로 발생하는 사실이 아니라 만들고 확인해야 할 사업 가설입니다. 기여자 수보다 채택된 개선의 품질과 유지 가능성이 중요하고, 다운로드 수보다 실제로 업무가 이어지고 유료 가치를 체감하는지가 중요합니다.

고객과의 관계도 “떠나기 어려워서 남는 것”이 아니라 “쌓인 맥락을 계속 활용하고 싶어서 남는 것”을 지향합니다. 내보내기와 해지가 가능해도 계속 쓰고 싶은 제품을 목표로 합니다.

확인할 지표의 후보는 첫 연결 성공과 소요 시간, 첫 유용한 기억 경험까지의 시간, 재설명·검색 수고의 감소, 기억 수정 빈도, 업무가 이어지는 재사용, 실제 결제·갱신·해지 이유, 사용자당 제공·지원 비용입니다. 아직 숫자 목표나 시장 검증 완료를 선언하지 않습니다.
