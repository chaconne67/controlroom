## 1. 제품의 약속과 고객

### 확정된 방향

- 독립적인 범용 Agent Client로 만든다. Telegram Mini App이나 Hermes 전용 테마가 제품의 최종 형태는 아니다.
- 첫 연결 대상은 Hermes. 이후 OpenClaw 등 외부 연결 API를 제공하는 에이전트로 넓힌다.
- 초기 고객은 **Hermes 등 에이전트를 이미 사용하는 개인·소규모 팀**이다. 2026-09-23 사용자 선택으로 확정했다.
- Windows·macOS·Android·iOS를 지향하고 HTML 기반 UI와 공통 로직을 공유한다.
- 앱스토어 출시, 무료·유료 제공, 수익화를 목표로 한다.
- 핵심은 **심리스한 UX / 예쁜 디자인 / 디자인 커스터마이징 / 가벼움**이다.

### 누구의 어떤 불편을 해결하는가

1. 개인 파워유저: 서버의 에이전트를 PC와 휴대폰에서 이어 쓰고 싶지만 연결·가독성·작업 상태 확인이 번거롭다.
2. 개발·리서치 실무자: 설명·코드·표·로그·파일이 섞인 답변을 읽고, 복사하고, 판단하는 비용이 크다.
3. 소규모 팀의 운영자와 구성원: 운영자는 연결을 한 번 준비하고, 구성원은 비밀키나 서버 설정을 배우지 않고 초대로 사용하고 싶다.

초기에는 자체 AI 모델 판매, 서버가 없는 일반 사용자의 에이전트 호스팅, 에이전트 개발 도구 전체를 제공하지 않는다. 화면은 가벼워도 서버에서 수행하는 업무의 강도는 제한하지 않는다. 원격 서버의 도구가 사용자의 휴대폰 파일까지 자동으로 다룬다고 설명하지 않는다.

### 성공 경험

“연결 링크를 열었더니 내 에이전트가 보이고, 읽기 편해서 계속 쓰게 되며, 기기를 바꿔도 하던 대화를 바로 찾을 수 있다.”

핵심 반복 흐름은 알림 또는 필요에 의해 열기 → 최근 대화에서 요청 → 읽고 판단 → 취향·연결·기록이 유지되어 다음 사용이 쉬워지는 것이다. 불필요한 방문 유도, 출석 보상, 응답 중 광고는 넣지 않는다.

## 4. 핵심 사용자 흐름

### 4.1 첫 실행: 가입보다 경험을 먼저

첫 화면의 주 행동은 **내 에이전트 연결**이다. 보조 행동으로 **샘플로 둘러보기**를 제공한다. 샘플은 로컬의 가상 대화임을 표시하고, AI를 호출하거나 실제 서버처럼 보이게 하지 않는다. 가입을 요구하기 전에 가독성과 개인화 가치를 느끼게 한다.

연결 진입은 링크/QR을 우선하고, 직접 연결은 접힌 고급 경로로 둔다. 초대 링크로 실행했다면 연결 정보 입력을 건너뛰고 서버 이름·접근 범위 확인으로 간다. QR은 서버 연결 등록용이며 유료 기능을 우회 해제하는 라이선스 수단으로 사용하지 않는다.

### 4.2 서버 소유자의 최초 준비

1. 연결 도우미가 설치 버전·API 지원·접속 경로를 확인한다.
2. 기존 인증·대화·모델·도구 설정을 보존하면서, 클라이언트 접근을 명시적으로 허용한다.
3. 서버의 HTTPS 도달 가능성과 인증 성공을 확인한다. 이 확인에 임의의 에이전트 작업을 실행하지 않는다.
4. 제한된 수명의 연결 링크/QR을 발급한다.

이 도우미와 일회성 기기 연결은 **추가 개발할 제품 기능**이다. 현재 Hermes 일반 API가 그대로 제공하는 기능이라고 설명하지 않는다. 기본값은 서버 소유자 배포의 얇은 연결 모듈이며, Hermes 내부를 포크하거나 인증을 약화하지 않는다. 기존 공식 로그인·플러그인·인증 라이브러리의 재사용 가능성을 먼저 검증한다.

같은 LAN/사설망에만 있는 서버는 VPN 또는 소유자가 승인한 접속 경로가 필요하다. QR만으로 네트워크가 뚫리지 않는다. 공개 릴레이·NAT 우회 서비스는 1.0 필수 범위에서 제외하고, 지원하지 않는 환경은 연결 전 명확히 알린다.

### 4.3 개인 사용자·초대된 구성원의 연결

링크 열기/QR 스캔 → 대상 서버·에이전트 확인 → 로그인 또는 소유자 승인 → 연결 완료 → 첫 대화.

- API 키는 서버에 보관하고 일반 사용자의 복사·붙여넣기를 없앤다. 앱에는 기기별 취소 가능한 자격증명을 저장한다.
- 기존 계정으로 가능한 인증을 재사용하되, 앱 계정과 에이전트 접근 권한은 구분한다.
- 에이전트 하나면 선택 화면을 생략한다. 모델도 서버 기본 설정을 사용한다.
- 연결 성공은 실제 인증과 지원 기능 확인으로 판단한다. 연결 성공이 추론 제공자의 잔액·가용성까지 보장하지는 않는다.
- 모바일에는 앱 링크, 데스크톱에는 복사 가능한 링크를 우선한다. QR을 유일한 연결 수단으로 만들지 않는다.
- 화면에는 “내 Hermes에 연결됨”과 다음 행동만 우선 표시한다. 버전·주소·진단 로그는 상세 보기로 둔다.

### 4.4 대화·작업·복귀

사용자 요청은 간결한 오른쪽 말풍선, 응답은 본문 영역 전체를 사용하는 문서 형태다. 전송 즉시 접수 상태를 보이고, 진행·도구 실행·승인 요청과 최종 답변을 구별한다. 요청이 대기 중인지 실제 실행 중인지 서버 상태를 기준으로 표시한다.

화면을 닫거나 통신이 끊겼을 때 요청을 자동으로 재실행하지 않는다. 대화 ID·작업 ID·중복 방지 키를 보존하고 상태/기록을 재조회한다. 복구 중에도 입력 초안을 지킨다. 긴 기록은 필요한 구간만 불러오고, 사용자가 과거를 읽을 때 강제 스크롤하지 않는다.

다른 기기에서 같은 대화를 불러오는 기능과 연결 복구는 Free에서도 제공한다. 같은 에이전트에 접근 가능한 기기 사이의 대화 지속은 기본 가치다. 유료 동기화는 별도로 **앱의 프리셋·정리 상태·설정**을 자동 맞추는 가치다.

### 4.5 연결 실패·권한 만료·해제

좁은 화면·큰 글자에서 말풍선 ⅔가 가독성을 해치면 사용자 설정과 접근성 확대를 우선한다. 원래 비율은 기본값이며 읽기 불가능한 고정 제한이 아니다. 문서·코드·표의 넘침은 각 콘텐츠 안에서 처리하고 화면 전체 가로 스크롤을 만들지 않는다.

강조색 `#339CFF`는 작은 글자·흰 글자 버튼에 그대로 적용하면 대비가 부족할 수 있다. 선택 표시에는 사용자 색을 쓰되, 텍스트와 주요 버튼은 대비를 검증한 파생색 또는 어두운 글자 조합을 사용한다.

### 설정 UX

기본은 **색상 / 글자 / 간격 / 콘텐츠** 네 묶음이다. 선택 즉시 실제 대화 예시에 반영하고, 저장 전 되돌리기와 기본값 복원을 제공한다. 읽기·코딩·야간 프리셋에서 시작해 필요할 때 세부값을 연다. 본문과 코드 글꼴은 독립이다.

Free에서도 글꼴 선택, 크기·자간·줄간격·본문 너비·기본 색 조절을 제공한다. Plus의 가치는 조절 권한 자체보다 **여러 스타일 저장, 에이전트별 자동 적용, 기기 간 동기화, 고급 콘텐츠 레이아웃**이다.

임의 CSS/JS·원격 폰트 URL을 실행하는 테마 엔진은 1.0에 넣지 않는다. 허용된 디자인 값으로 표현하고, 폰트는 필요한 것만 로드한다. 폰트 배포 권리를 확인하기 전에는 HCR 파일을 복사하거나 업로드하지 않는다.

접근성: OS 글자 확대·스크린리더·키보드 포커스·동작 줄이기, 충분한 대비, 모바일 주요 터치 영역 최소 44px(플랫폼 권고에 맞춰 확대). 한국어·영어·이모지·혼합 코드에서 잘림과 줄바꿈을 확인한다.

## 6. 콘텐츠 표현과 AI의 역할

### 1.0의 읽기 경험

Markdown 문단·제목·목록·표·인용·코드, 코드 언어 강조와 복사, 접을 수 있는 긴 로그, 이미지 미리보기, 안전한 링크·파일 참조, 작업 상태·승인 요청을 제공한다. 미디어는 **표시 가능**과 **서버에 업로드/처리 가능**을 구분해 지원 기능에 따라 버튼을 연다. 오디오·실시간 음성을 일반 API가 지원한다고 가정하지 않는다.

### AI 기반 표현: 핵심 차별화 후보로 검증

에이전트 응답·구조화 이벤트 → 내용 블록 → 표현 판단 모델 → 검증된 레이아웃 선택 → 사용자 디자인 값 적용.

- 판단 대상은 읽기 / 코드+결과 / 미디어 묶음처럼 준비된 구성의 선택이다. 원문을 다시 쓰거나 승인 상태를 추측하지 않는다.
- Jev는 후보이며 가격·한국어 품질·실제 지연·가용성을 비교 평가한 뒤 선택한다. 공급자 성능 홍보와 우리 실측을 구분한다. [TypeSafe 공식 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)
- 원본 Markdown과 사실을 항상 보존한다. 원문 보기와 수동 레이아웃 선택을 제공한다.
- 답변 표시를 판단 모델 때문에 지연시키지 않는다. 기본 렌더링을 즉시 제공하고, 완료 후 안정된 지점에 적용한다. 읽는 중인 내용을 예고 없이 재배치하지 않는다.
- 실패·시간 초과·낮은 확신이면 기본 화면을 유지한다. 보안·실행 권한 판단에는 사용하지 않는다.
- 별도 AI로 본문을 보낼 때 목적·대상·범위를 설명하고 동의받는다. 비밀값 제거와 최소 내용 전달, 로그 비저장을 기본으로 한다. 계정별 비용 상한과 캐시가 필요하다.

1.0에는 제한된 표현 판단을 베타 검증 범위로 포함한다. 출시 합격 기준을 못 넘으면 기본 Markdown·수동 레이아웃으로 출시하고, AI 표현을 유료 구독의 확정 제공 기능처럼 판매하지 않는다. 요금 계산의 추론 비용은 확인 전까지 예산 가설이다.

## 7. Free / Plus와 수익화

### 한 앱, 두 단계 — 제안

별도의 Lite 앱·유료 앱을 나누지 않는다. 같은 앱에서 업그레이드·구매 복원·해지할 수 있게 해 연결·대화·리뷰가 분산되지 않도록 한다.

| 항목 | Free | Plus |
|---|---|---|
| 연결 | 에이전트 1개, 안전한 간편 연결 | 여러 연결 저장·빠른 전환 |
| 대화·작업 | 서버가 허용하는 대화, 기록, 기본 작업 상태·중단·승인 | 동일; 안전 기능을 유료로 막지 않음 |
| 기본 디자인 | 좋은 기본 화면, 밝게·어둡게, 기본 읽기/코딩 프리셋 | 동일 |
| 가독성 조절 | 폰트·코드 폰트·크기·자간·줄간격·너비·색상 | 동일 |
| 프리셋 | 사용자 프리셋 1개 + 기본 프리셋 | 여러 프리셋·에이전트별 스타일·내보내기/가져오기 |

| 앱 설정 | 기기 내 저장 | 앱 설정·프리셋·북마크 자동 동기화 |
| 작업 정리 | 대화 검색·기본 기록 내보내기 | 여러 연결 통합 정리·저장한 보기·고급 검색 범위 |
| 표현 | Markdown·코드·표·미디어 기본 표시 | 고급 혼합 레이아웃, 검증 통과 시 AI 자동 표현의 명시된 월 제공량 |

“무제한 대화”를 자체 AI 무제한 제공으로 표현하지 않는다. 앱이 메시지 수를 과금하지 않더라도 실제 에이전트·모델·호스팅의 제한과 비용은 사용자 또는 운영자에게 있다. 연결 복구, 승인/거절, 보안 업데이트, 접근성, 자기 데이터 내보내기는 무료에서 유지한다.

구독 종료 후 저장된 스타일과 연결 목록을 삭제하지 않는다. 기존 대화는 읽고 내보낼 수 있게 하며 Free에서 활성화할 연결 1개를 선택하게 한다. 현재 스타일을 강제로 보기 나쁘게 바꾸지 않는다. 유료 서버 기능과 추가 편집·동기화의 종료 시점만 명확히 알린다.

### 가격 가설

**Plus 월 6,900원 / 연 59,000원**을 첫 검증안으로 제안한다. 연간은 월 환산 약 4,917원, 월 결제 12회보다 약 28.7% 낮다. 출시 가격·스토어 가격 단계·국가별 세금·환율은 미확정이다. 한국어·영어를 준비하되 실제 판매 국가는 제출 전 결정한다.

구독의 대가는 지속되는 설정 동기화·연결 관리·지원·개선이다. 이 가치가 부족하고 사용자 수요가 로컬 꾸미기에만 집중되면, **로컬 고급 기능 일회성 구매 + 실제 서버 서비스 선택 구독**으로 다시 검증한다. 처음부터 평생 클라우드 이용권을 팔지 않는다. 일회성 옵션을 추가할 경우 기존 구매자의 권리를 뒤집지 않는다.

초기에는 무료만으로 기본 제품을 충분히 체험하게 한다. 결제창은 두 번째 연결 저장이나 추가 프리셋 저장처럼 가치를 이해한 시점에만 제시한다. 첫 실행 직후 전면 결제창, 반복 방해 팝업, 허위 할인·품절 문구를 쓰지 않는다.

가격 검증은 5,900 / 6,900 / 8,900원과 연간 대안을 비교하되, 소규모 인터뷰 결과를 통계적 검증이라고 부르지 않는다. 이미 결제한 고객은 표시한 계약을 보존한다. 구독 구매·환불·갱신 실패·복원·중복 가입 방지를 실제 스토어 테스트 환경에서 검증한다.

### 추가 수익원 — 출시 이후

1. **Team:** 구성원 초대·권한·팀 프리셋·연결 배포·퇴사자 접근 해제. 월 좌석당 9,900~14,900원은 인터뷰용 가설이다. 사람별 에이전트 실행·데이터 격리 검증 전에는 팀 보안을 판매하지 않는다.
2. **공식 디자인 팩:** 제품 품질을 확인한 뒤 비소모성 인앱 구매 후보. 기본 접근성이나 글꼴 확대를 팩으로 팔지 않는다.
3. **설치·연결 지원:** 조직의 기존 서버에 연결 모듈을 배포하는 지원 서비스. 지원 범위·시간을 명확히 한 별도 계약 후보이며 인앱 디지털 기능 판매 우회 수단이 아니다.
4. **관리형 호스팅:** 별도 사업 검증 이후. 모델 비용·서버 운용·사용자 격리를 갖추기 전에는 포함하거나 수익을 잡지 않는다.

초기 매출 계획에는 Plus만 반영한다. 광고, 대화 데이터 판매, 무제한 추론 재판매는 수익원에서 제외한다.

## 8. 단위 경제성과 손익 시나리오

아래 수치는 **산술 시나리오이며 매출 예측·실제 비용 견적·세무 판단이 아니다.** 아직 유입·결제·유지율을 측정하지 않았다. 월 구독 환산액과 연 결제 시점의 현금 유입은 다르다.

### 입력 가정

- 월 결제 30%, 연 결제 70% → 유료 1인당 월 환산 결제액 5,511.67원.
- 소비세 등을 단순화한 가상의 세금계수 10% → 계산상 기준액 5,010.61원. 실제 시장별 정산은 별도 대조한다.
- 유효 스토어 비용 15% / 보수 시나리오 30%, 환불·조정 충당 3%를 계산상 기준액에 적용한다. 실제 공제 순서와 세율을 의미하지 않는다.
- 유료 이용자 1인당 월 변동비 800원, 무료 활성 이용자 1인당 30원, 공통 고정비 월 600,000원으로 가정한다.
- 변동비는 작은 메타데이터 동기화·알림·제한된 표현 판단 등을 가정한다. 일반 AI 답변 생성·상시 전체 대화 릴레이·큰 파일 저장 비용은 포함하지 않는다. 그런 기능을 넣으면 다시 계산해야 한다.
- 활성 이용자의 유료 비중 3% 가정. MAU는 월간 활성 이용자이며 다운로드 수가 아니다.
- 개발·운영 인건비, 유료 마케팅, 법률·디자인 외주, 개발 장비와 계정 가입비는 아래 잔여액에서 제외했다. 따라서 영업이익이라고 부르지 않는다.

### 계산식

```text
월 환산 결제액 R = 0.3 × 6,900 + 0.7 × (59,000 / 12)
계산상 세금 제외 기준액 B = R / 1.10
유료 1인 기여액 C = B × (1 - 수수료율 - 0.03) - 800
월 잔여액 = 유료 수 × C - 무료 MAU × 30 - 600,000
```

| MAU | 유료 수(3%) | 월 환산 총 결제액 | 15% 비용 시 잔여액 | 30% 비용 시 잔여액 |
|---:|---:|---:|---:|---:|
| 10,000 | 300 | 1,653,500원 | 101,609원 | -123,868원 |
| 50,000 | 1,500 | 8,267,500원 | 2,908,045원 | 1,780,659원 |
| 100,000 | 3,000 | 16,535,000원 | 6,416,091원 | 4,161,318원 |

위 가정에서 고정비만 충당하려면 유료 약 257~379명이다. 인건비 월 600만원을 **추가 가정**하면 약 2,823~4,159명으로 올라간다. 무료 사용자 지원비·전환율·유지율이 나빠지면 더 많아진다. “몇 백 명만 결제하면 사업이 된다”는 결론을 내리지 않는다.

수수료 15%를 확정 적용하지 않는다. Apple Small Business Program은 자격·등록 조건이 있고, Google은 시장·프로그램·거래 종류에 따른 구조와 변경 중인 지역별 체계가 있다. 실제 판매 국가와 계정 계약으로 재계산한다. [Apple 프로그램](https://developer.apple.com/app-store/small-business-program/), [Google 수수료](https://support.google.com/googleplay/android-developer/answer/112622)

유료 광고는 실측 CAC(유료 고객 1명 획득 비용)를 기여액 기준 6개월 안에 회수할 가능성이 확인된 뒤 확대한다. LTV는 단순 추정치로 광고비를 정하지 않고 최소 몇 개 월별 유지 집단의 갱신·환불 데이터를 보고 산정한다. 출시 전에는 광고 집행이나 유료 API 실험을 하지 않는다.

## 9. 가벼운 멀티OS 구조

### 책임 분리

```text
공통 HTML UI·디자인 값·대화 상태
        ↕
에이전트별 연결부(Hermes 우선, 이후 OpenClaw 등)
        ↕
소유자 서버의 연결 모듈 → 기존 에이전트 API

플랫폼 기능: 안전한 자격증명 저장 / 링크 열기 / 알림 / 파일 선택 / 결제
선택 서비스: 앱 설정 동기화 / 구매 권한 / 내용 없는 운영 측정
```

중앙 서비스가 원문 대화를 기본 저장·중계하지 않는 구조를 우선한다. 서버 소유자의 연결 모듈과 직접 통신하고, 제품의 클라우드는 계정·구매 권한·설정 같은 최소 데이터만 맡긴다. 표현 AI를 켜면 별도 본문 전송이 생긴다는 사실을 분리 고지한다. 종단간 암호화는 실제 설계·검증 전까지 홍보하지 않는다.

### 기술 후보와 선택 기준

- 공통 UI는 TypeScript 기반 웹 앱. 기존 Vite·Markdown 정제·강조·타이포그래피 시제품에서 검증된 자산을 재사용하되 그대로 제품 완성으로 간주하지 않는다. React 등 UI 라이브러리 채택은 상태·화면 복잡도와 번들 측정 후 선택한다.
- 패키징 1차 후보는 **Tauri 2**. 공식적으로 데스크톱·모바일과 웹 프런트엔드를 다루며 App Store 배포 안내가 있다. 실제 결제·알림·키체인·딥링크·키보드 동작을 시험해 결정한다. [Tauri](https://tauri.app/), [App Store 배포](https://v2.tauri.app/distribute/app-store/)
- 모바일 플러그인·출시 검증에서 이점이 확인되면 **Capacitor 모바일 + Tauri 데스크톱**을 비교한다. 웹 코어는 공유하되 두 셸의 유지 비용을 기록한다. [Capacitor](https://capacitorjs.com/docs)
- Electron은 기존 경험 때문에 자동 채택하지 않는다. 무게와 모바일 별도 구현 부담을 함께 비교한다. PWA는 체험·개발 채널로 활용하되 앱스토어 출시 목표를 대체하지 않는다.
- 하나의 소스는 플랫폼 검증이 하나라는 뜻이 아니다. iOS/macOS 서명·샌드박스와 Android/Windows 결제·저장·알림은 각각 검증한다. iOS 빌드에는 실제 macOS/Xcode 실행 환경을 준비해야 한다.

## 10. 앱스토어 출시 설계

### 배포 범위 제안

제품은 처음부터 네 OS를 고려한다. 첫 공개 출시는 iOS·Android, 같은 코어의 Windows·macOS는 베타로 검증 후 별도 스토어 또는 서명 배포를 결정하는 순서를 제안한다. 네 플랫폼 동시 정식 출시를 무리하게 약속하지 않는다. Mac App Store·Microsoft Store 등록 여부는 미정이며, 미지원 플랫폼을 광고에 표시하지 않는다.

### 결제·로그인·심사

앱 내 디지털 Plus 기능은 StoreKit·Google Play Billing을 기본으로 설계한다. 외부 결제·링크 예외는 국가·프로그램별 조건을 따로 확인하며 전 세계 공통 우회 경로로 쓰지 않는다. 플랫폼 간 구매 권한을 연결할 때 복원·중복 구독·환불을 서버 영수증 상태와 대조한다. [Apple 3.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase), [Google 결제](https://support.google.com/googleplay/android-developer/answer/10281818)

웹페이지 포장만으로 출시하지 않는다. 보안 저장·앱 링크·파일 선택·공유·알림·오프라인 초안·플랫폼 접근성이 실제 사용자 가치를 제공하도록 한다. 서버 결과는 안전한 구성요소로 표시하고 임의 원격 코드를 내려받아 앱 기능을 바꾸지 않는다. 외부 에이전트·챗봇 연결 기능은 Apple 4.2/4.7 등 적용 검토를 제출 전 통과해야 하며, 승인 보장은 하지 않는다. [Apple 디자인·소프트웨어 기준](https://developer.apple.com/app-store/review/guidelines/)

심사자는 실제 주요 기능을 시험할 수 있어야 한다. 별도의 격리된 심사용 에이전트·테스트 계정·연결 안내를 준비하고 비용과 도구 권한을 제한한다. 주인님의 운영 Hermes·개인 인증·대화를 심사 계정으로 제공하지 않는다. 단순한 가짜 샘플만으로 실제 연결 심사를 대신하지 않는다.

앱 기본 계정에 외부 소셜 로그인을 쓰면 Apple 로그인 서비스 기준의 적용 여부와 동등한 선택지를 검토한다. 계정 생성이 있으면 앱 안에서 삭제를 시작할 수 있게 하고, 원격 데이터와 구독에 미치는 효과를 구분한다. [계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

### 개인정보·AI 콘텐츠

- App Privacy·Google Data safety·개인정보처리방침은 실제 데이터 경로와 일치해야 한다. 대화 본문·첨부·키를 분석 로그로 모으지 않는다.
- 별도 표현 AI에 데이터를 보내는 기능은 기본 연결과 분리해 설명·동의·끄기를 제공한다.
- Google의 AI 콘텐츠 정책에 맞춰 인앱 신고와 대응 절차, 금지 콘텐츠 예방 조치를 설계한다. “외부 에이전트가 만들었다”는 이유로 책임을 면제받는다고 가정하지 않는다. [Google AI 콘텐츠 정책](https://support.google.com/googleplay/android-developer/answer/14094294?hl=en)
- 임의 HTML·스크립트 실행, 승인 요청 위장, 외부 링크·첨부의 위험을 처리한다. 에이전트의 작업 승인 의미를 디자인 모델이 바꾸지 못하게 한다.
- 고객센터·신고·환불 안내·약관·기기 접근 해제가 앱 안에서 쉽게 보여야 한다. 공유 커뮤니티·공개 테마 마켓은 신고·운영 부담을 늘리므로 1.0 범위에서 제외한다.
- Hermes·폰트·의존성 라이선스와 외부 모델 서비스 이용 조건을 검토한다. 개인 구독 인증을 여러 고객에게 재판매하는 사업을 전제하지 않는다.

계정 종류에 따라 Google의 신규 개인 개발자 계정 테스트 요건 등이 적용될 수 있다. 등록 계정·대상 국가·출시일을 정한 뒤 최신 요구를 다시 확인한다. [Google 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465)

## 11. 출시·성장과 측정

### 작은 시장에서 시작

Hermes 기존 사용자 커뮤니티와 개인·소규모 팀 20~30명을 디자인 파트너로 모집하는 것을 제안한다. 운영자 5명 이상을 포함해 서버 연결 준비와 구성원의 초대 연결을 모두 관찰한다. 모집·게시·메시지 발송은 별도 실행 단계다.

스토어 메시지는 “AI를 새로 사는 앱”이 아니라 “이미 쓰는 에이전트를 더 편하게”로 잡는다. 설치 조건·지원 에이전트·추론 비용 별도를 설명한다. 첫 스크린샷은 로그인 화면보다 읽기 좋은 대화, 두 번째는 글꼴·간격 조절, 세 번째는 연결/이어쓰기, 네 번째는 작업 상태를 보여준다. 제품 자체의 이름과 시각 언어를 사용한다.

유입 채널 후보는 공식 호환 연결 가이드, 실제 사용 전후 영상, 허가된 커뮤니티 소개, 공개된 가벼움 측정 결과다. 후기 보상이나 억지 알림으로 지표를 늘리지 않는다. 설치 성공률·유지율을 먼저 확보하고 광고 지출을 검토한다.

|---|---|---|
| 0. 기획·기술 검증 / 1~2주 가설 | 연결 모듈·인증 재사용, 실제 모바일 셸, 결제 복원·딥링크·키보드·알림 시험, 가격 인터뷰 | 지원 환경·성능·스토어 경로를 근거로 아키텍처와 출시 범위 선택 |

### 필수 검증 과제

1. API 키를 사용자에게 배포하지 않는 기기 연결과 개별 해제. 공식 인증 재사용 여부, 연결 모듈의 설치·업데이트 경로.
2. 서버 준비와 사용자 연결의 시간·오류 분리. 서버를 모르는 사용자도 초대로 연결할 수 있는지.
3. 모바일 백그라운드·화면 잠금·망 전환 중 작업 완료, 재접속, 승인 대기, 중복 전송 방지. Hermes 스트림만 재연결하면 모든 이벤트가 복원된다고 가정하지 않음.
4. 앱/에이전트/사용자/기기/대화/실행의 식별과 권한 분리. 팀의 서로 다른 계정이 다른 대화·파일에 접근하지 못하는지. 프로필만으로 OS 파일 격리까지 보장하지 않음.
5. 네이티브 구매·복원·환불·기한 만료·오프라인·플랫폼 간 중복 결제 방지.
6. AI 표현의 한국어·코드 혼합 평가, 원문 보존, p95 지연·요청당 비용·추가 데이터 전달 동의.

## 13. 현재 자산, 보호 범위, 미정 결정

### 현재 확인한 자산

기존 시제품에는 Vite, Markdown 정제·코드 강조, NanumGothicCoding, 사용자 말풍선/응답 본문 구조와 스트리밍 연결 코드가 있다. 문서 작성 때 패키지 구성을 다시 읽었다. 이는 재사용 후보이지 앱스토어 제품의 인증·결제·동기화·성능 검증은 아니다.

직전 API 점검(2026-09-23)에서는 메인서버 Hermes `9fe737aef2dd18a351dff3c4de608d63879a6524`의 상태·인증·지원 기능·대화 목록 조회가 정상이고, 일반 API는 프로필 키 인증임을 확인했다. 작업/세션/중단/승인 지원 선언과 설치 코드를 확인했지만, 새 제품의 전체 UX를 실제 동작 시험한 것은 아니다. [Hermes 공식 API](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server), [해당 버전 코드](https://github.com/NousResearch/hermes-agent/blob/9fe737aef2dd18a351dff3c4de608d63879a6524/gateway/platforms/api_server.py)

현재 Telegram 미니앱·RNDLOG 배포 경로·메인서버 Hermes와 개인 인증은 보존한다. 새 제품을 위해 자동 교체·중지·데이터 이동하지 않는다. 새 제품은 RNDLOG 업무 서비스와 배포·권한·데이터 책임을 분리하는 것을 원칙으로 검토한다.

### 이 기획의 검토 결과

무료판의 기본 UX를 의도적으로 불편하게 만들지 않는지, 기존 Hermes UI와 차별화할 구매 이유가 있는지, 구독료와 모델 비용이 혼동되지 않는지, 연결·결제·가벼움에 실제 완료 기준이 있는지를 자체 대조했다. 수정·검증 상태와 문서 저장 내역은 작업 응답으로 보고한다. 앱스토어 심사·실기기 성능·수익성은 아직 검증되지 않았다.
