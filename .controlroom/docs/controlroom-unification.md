# controlroom 저장소 통합

사용자 승인: 두 저장소를 controlroom으로 합친다. 공개·비공개 설정은 사용자가 나중에 결정하므로 변경하지 않는다.

기존 private control-room-docs를 controlroom으로 이름 변경하고 public kmh-agent-kit의 코드·이력을 가져온다. 원래 공개 키트는 이전 안내를 남긴 보관 저장소로 전환한다. 비공개 자료를 기존 공개 저장소에 올리지 않는다.

- 기준선: kit 50030c2, docs 5915f9d, 두 작업 폴더 clean. 이전 대화의 미커밋 스킬은 다른 작업에서 이미 커밋됐다.
- 보존: 두 Git 이력, 문서 94개 원문, 사용자 등록 경로·Venture 작업·로그인·키·서버 데이터·기존 스킬 실행.
- 구조: 키트 코드는 루트, 공통 설명은 docs, 문서 저장소의 파일은 projects 아래에 이식한다. 프로젝트의 기존 지침/스킬과 docs가 같은 저장소에 있게 한다. 문서 루트 README·provenance·원문 보관 규칙도 함께 보존한다.
- 명령: controlroom pull/push를 공식 이름으로 추가하고 kitpull/kitpush는 호환 진입점으로 유지한다. Git 로컬 설정 키는 기존 등록을 보존해 재사용한다.
- 실행 경로: 셸 명령 → 통합 저장소 main 수신/저장 → 기존 OS 설치기 → 프로젝트 docs 연결/검증 → Venture 기존 커밋 동기화. 별도 기획 저장소 clone·commit·push 단계는 제거한다.
- 최소 구현: 기존 install.sh/install.ps1, shell/kit-aliases.sh와 Git 병합 기능을 재사용한다. 새 동기화 서비스·데몬·DB를 만들지 않는다.
- 검증: 변경 전 관련 검사를 기록하고, 변경 후 Windows/macOS/Linux 설치·Git 왕복, 문서 원문/이력 보존, 새 명령과 호환 명령, 실제 PC의 프로젝트 연결과 작업 보존을 확인한다. code-review-loop로 같은 변경 범위를 검토한다.
- 전환: 임시 체크아웃에서 구현·검증 후 GitHub 이름을 바꾸고 게시한다. 로컬 기존 체크아웃은 복구 가능한 위치로 보존하고 공식 controlroom 경로와 기존 경로 호환 연결을 설치한다.
- 완료: GitHub controlroom main, 두 이력 포함, 통합 문서/도구 수신, 실제 설치/동기화 검증, 이전 저장소 보관 안내를 확인한다. 공개 범위는 원래 private 대상 설정 그대로 둔다.

### 설치·업데이트의 책임과 순서

설치 진입점과 `controlroom pull`이 같은 업데이트 절차를 사용한다. 설치와 이후 갱신에서 기존 자료에 대한 정책이 달라지지 않도록 한다.

1. **확보:** 새 저장소/커밋과 필요한 설치 파일을 임시 위치에 먼저 확보한다. 예상 원격 주소·설치에 필요한 파일·설치기 문법·스킬 의존관계를 확인한 뒤 기존 대상을 변경한다.
2. **백업:** 이번에 교체할 기존 디렉터리 전체와 설치기가 바꾸는 도구용 파일을 압축 보관한다. 숨김 파일, 미추적 파일, 로컬 변경과 미전송 커밋을 복구할 Git 상태도 포함한다. 백업은 동기화 루트 밖의 `~/backups/controlroom`에 두며 원격 Git에 올리지 않는다.
3. **확인:** 압축 파일을 열어 항목·크기·내용을 대조하고 기존 상태를 복구할 수 있는지 확인한다. 외부 자료를 가리키는 링크는 대상 위치를 기록하고 대상까지 따라가 별도 고객 자료를 수집·교체하지 않는다.
4. **적용:** 일반 `docs` 충돌, 로컬 변경, 미전송 커밋이 있다는 이유로 중단하지 않는다. 복구 가능한 백업을 확보한 뒤 최신 승인 원본을 적용한다. 새 구조의 실제 폴더와 파일을 배치하고 옛 구조 연결을 제거한다.
5. **검증:** 공식 프로젝트 경로에서 문서·지침·스킬 내용과 Git 원격/커밋을 확인한다. 각 대상별 적용 결과와 백업 위치를 명확하게 표시하고 전체 적용이 끝났을 때 성공한다.
6. **복구:** 적용 도중 실패하면 이번 변경을 이전 상태로 되돌린다. 새 원본과 옛 지침이 섞인 상태를 성공으로 표시하지 않는다. 실패 지점과 복구 결과를 표시한다.

다운로드·백업 생성·백업 검증이 실패했거나, 접근 권한·사용 중인 파일 때문에 정상 적용/복구가 불가능한 경우는 실제 실행 실패다. 그 경우 기존 상태를 보존하고 필요한 조치를 구체적으로 알린다. 기존 자료의 존재 자체는 실행 실패가 아니다.

`controlroom push`는 검토한 공통 Git 변경과 Venture의 검토된 커밋을 전송하는 책임을 유지한다. pull/update가 오래된 로컬 자료를 최신 원본으로 되돌린다는 이유로 이를 자동 push하거나 강제 push하지 않는다.

교체 단위는 공통 관리 디렉터리, 각 프로젝트의 `docs`·원본 스킬·지침, 해당 도구용 배치 파일과 승인된 Git 추적 코드다. 이 단위의 기존 내용 전체를 압축한 후 최신 내용으로 갱신한다. `~/projects` 아래 모든 파일을 새 clone으로 밀어내는 방식은 사용하지 않는다. 같은 프로젝트 안의 고객 자료·인증·환경·별도 산출물은 기존 위치에서 계속 사용하게 보존한다.

### 변경 범위와 보호할 상태

변경 대상은 공통 저장소의 물리적 레이아웃, 두 OS 설치기, 셸 명령의 루트 탐색/갱신 절차, 스킬 배치 관리·검사, README·운영 설명·경로 안내, 관련 검증과 설치 배치본이다. GitHub 원격 저장소와 각 장비의 동일한 상대 디렉터리를 실제로 맞춘다.

보호 대상은 고객 자료와 일반 산출물, 비밀값·Git/SSH 인증·앱 로그인, 에이전트 대화·플러그인·시스템 스킬·별도 사용자 스킬, 원격 코드·제품 서비스·DB·배포, 기존 개인 GBrain 소스와 기존 Git 이력이다. 자료의 저장소 소유권이나 공개 범위를 바꾸지 않는다. Venture의 외부 고객자료 연결은 저장소 구조를 위한 호환 링크와 구분해 보존한다.

프로젝트 안의 고객 자료·환경·산출물은 공통 Git의 명시적인 제외 대상으로 설정한다. 공통 push의 stage 대상도 공통 관리 경로와 명시된 프로젝트 지침·문서·원본 스킬로 한정한다. `~/projects`를 Git 루트로 만든다는 이유로 고객 자료나 별도 코드 저장소를 자동 편입하지 않도록 한다. 구조만 옮기는 기존 문서·지침·스킬은 원문과 줄바꿈을 보존하고, `.gitattributes`의 해당 경로 규칙도 새 구조로 이관해 해시로 대조한다.

현재 PC에서는 다른 작업이 동시에 변경을 저장하고 있다. 2026-09-18 조사 중 HEAD는 `639791d`에서 `e207fad`로 진행했고 최종 확인 때 Exdigm의 README 수정과 신규 계획 문서가 남았다. 실제 전환 직전에 파일 내용·스테이징·미추적 파일·HEAD·Git 원격을 다시 잠근다. 다른 작업의 작성 중 내용을 이번 변경 커밋에 포함하거나 지우지 않는다. 구조 이동은 기존 변경을 새 상대경로에 그대로 이어 옮기고, 이후 사용자가 업데이트를 실행해 최신본을 적용할 때는 승인된 압축 백업 정책을 사용한다.

### 기존 구현 재사용과 최소 구현

기존 `install.sh`, `install.ps1`, `shell/kit-aliases.sh`, 스킬 manifest/등록 도구와 검사 스크립트를 재사용한다. 새 동기화 서비스·데몬·DB·중복 설치 경로를 만들지 않는다.

확인 근거: 두 설치기와 셸 명령에서 `Backup-Entry`, `Link-Entry`, `Link-Profile`, `_kit_root`, `_kit_restore_control_repositories`, `kitpull`을 확인했다. `zipfile`, `tarfile`, `Compress-Archive`, `rollback` 검색에서는 필요한 전체 압축 백업·복구 구현이 발견되지 않았다. 기존 설치기 책임 안에서 표준 압축 기능과 파일 배치 기능을 사용한다. 압축 방식은 숨김/Git 상태와 필요한 크기를 실제로 처리할 수 있는지를 기준으로 선택한다.

구현 직전 최소 구현 게이트는 각 변경에 적용한다. 배치·업데이트의 기존 책임을 먼저 재사용하고, 새로 필요한 압축·복구는 표준 라이브러리 또는 플랫폼 기능에서 멈춘다. 프로필 링크를 대신하는 별도 추상화 계층을 신설하지 않는다.

### 실제 경로와 검증

새 공식 경로: 사용자 설치 명령 또는 `controlroom pull` → `~/projects/.controlroom`의 기존 명령/설치기 → 최신 원본 확보 → 교체 대상 전체 압축 백업·확인 → 실제 파일 배치 → 공식 프로젝트 경로 검사 → 성공 또는 이전 상태 복구.

수정 전 확인 결과:

- 현재 PowerShell 설치기 문법 오류는 0개다.
- 기존 스킬 의존성 검사 첫 실행은 Windows cp949 출력에서 UnicodeEncodeError로 종료됐다. 코드를 바꾸지 않고 `python -X utf8 scripts/check-skill-deps.py`로 다시 실행해 종료 코드 0을 확인했다. 스킬 50개, 전역 Claude/Codex 각 28개, 프로젝트별 배치가 검사됐으며 FundKeeper의 TestBed 사용은 현재 경고로 표시된다. 새 배치 manifest에서도 이 확인된 관계를 보존한다.
- 변경 대상인 기존 통합 계획 문서에는 수정 전 사용자 diff가 없었으며 SHA-256은 `57A550FB3D1B95361DFCFEBC8F25F064DD0F405B2AA9D138F8769D3FF4F965EE`다.
- 설치·폴더 전환 검증은 아직 실행하지 않았다. 현재 문서와 폴더 조사는 실제 새 구조의 적용 검증을 대신하지 않는다.

구현 후 필요한 확인:

- 새 장비 설치, 기존 일반 `docs`와 같은 이름 파일이 있는 장비 업데이트, 옛 세 경로가 남은 장비 전환이 모두 공식 진입점에서 완료된다.
- 두 격리 장비의 실제 폴더 구조와 이름이 일치하고, 첫 장비 push 후 둘째 장비 pull에서 문서·지침·스킬·검토된 Venture 커밋이 실제로 갱신된다.
- 숨김/미추적 파일과 미전송 커밋이 백업에서 복구되며, 압축 확인 전 기존 대상을 변경하지 않는다.
- 적용 중 실패를 재현했을 때 이전 파일·Git·배치 상태가 복구되고, 일부 최신본만 남아 성공하는 경우가 없다.
- 고객 자료·환경·인증·앱의 지정 영역과 시스템/플러그인 스킬이 변경되지 않고, 공통 push에 들어가지 않는다.
- 실제 Windows CMD와 PowerShell 5.1 설치기/명령을 사용한다. 기존 사용자 PATH 형식과 값도 보존·대조한다. macOS/Linux 검증 상태는 실제 실행·CI 결과와 실장비 검증을 구분한다.
- 과거 실패를 기대하던 검사는 삭제하지 않고, 사용자 승인으로 바뀐 계약인 '백업 확인 후 갱신 완료'와 '실패 시 복구'를 실제로 검증하도록 변경한다. 그 외 기존 보호 검사는 유지한다.
- `code-review-loop`에서 같은 승인 범위와 보호 조건을 검토한다. 스킬 본문을 바꾸면 `skill-review`, 상위 지침을 바꾸면 지침 변경 관리 절차를 함께 수행한다.
