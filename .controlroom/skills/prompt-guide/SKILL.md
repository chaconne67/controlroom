# Prompt Guide

LLM 행동을 유도하는 텍스트를 작성하거나 검토할 때 사용한다. 대상은 앱이 런타임에 송출하는 프롬프트, 에이전트 지시문, 스킬 지시문, 재사용 지시 템플릿을 모두 포함한다.

## `$skill-writing-guide`와의 관계

두 스킬은 같은 문서의 다른 층을 본다. 배타적이지 않으므로 **한 문서에 동시에 적용할 수 있고, 각각 단독으로도 쓴다.**

| | 무엇을 판정하는가 | 대표 질문 |
|---|---|---|
| `$skill-writing-guide` | 그 문서에 **무엇을 넣고 뺄지** (내용 선별) | 이 문장은 LLM이 이미 아는 내용인가? |
| `prompt-guide` (이 스킬) | 남긴 문구가 **의도한 행동을 실제로 유도하는지** (문구 품질) | 이 지시가 처음 보는 상황에서도 통하는가? |

문서 종류로 어느 스킬을 쓸지 가르지 않는다. 넣고 뺄 것을 정할 때는 `$skill-writing-guide`, 남긴 문구의 품질을 볼 때는 이 스킬이다. 스킬 파일·CLAUDE.md처럼 둘 다 필요한 문서는 두 스킬을 함께 적용한다.

## 사용하지 않는 경우

질문의 본질이 프롬프트·지시문 품질이 아니면 사용하지 않는다.

- 코드 버그, 실패한 테스트, 런타임 오류, 데이터 모델 결함, 아키텍처 결정.
- 도메인 정확성, 비즈니스 정책, 법률·의료·금융 사실, 제품 결정.
- 구현 계획 검증, 단계 순서, 완료 게이트, 컨텍스트-계획 정합성.
- 권한 계층, 안전 정책, 도구 권한, 시스템/개발자 지시 우선순위.
- 사용자가 문구 검토를 명시적으로 요청하지 않은 일회성 지시.

요청이 위 범주에 속하면 멈추고 적절한 스킬이나 일반 추론으로 처리한다. 비프롬프트 문제가 정리된 뒤 문구 계층만 이 스킬로 다룰 수 있다.

## 검토 출력

각 이슈마다 다음을 보고한다.

- 원래 문구
- 위반한 골든룰 또는 안티패턴
- 왜 실패하는지와 예상 실패 양상
- 개선 방향

이미 괜찮은 부분은 언급하지 않는다. 침묵보다 실제 프롬프트 위험을 잡는 쪽을 택한다 — 놓친 문제는 프롬프트가 실전에서 실패할 때까지 드러나지 않지만, 잘못된 지적은 작성자가 "아니다"라고 판단하면 끝난다.

### 보고 전 검증

"아마 문제가 될 것이다"는 검증이 아니다. 아래 순서로 확인하고, 확인한 방법을 함께 적는다.

1. 프롬프트를 실행할 수 있으면 수정 전후 출력을 비교한다.
2. 실행할 수 없으면 실패를 유발하는 구체적 입력을 상상해 예상 실패 양상까지 적는다.
3. 둘 다 불가능하면 "검증하지 못함"이라고 밝힌다. 검증 없이 단정하지 않는다.

같은 문제가 다른 형태로도 나타나는지 함께 본다. 흔한 실패 형태는 지시 무시, 과잉 축약에 의한 정보 소실, 사실 조작, 거부·회피, 과잉 준수로 인한 유용성 상실이다.

## 왜 이 원칙이 필요한가

LLM은 규칙을 외우는 것이 아니라 맥락을 이해하고 추론한다. 프롬프트가 좋으면 처음 보는 상황에서도 올바르게 판단하고, 나쁘면 학습 데이터에서 본 패턴으로 퇴행한다. 아래 골든룰은 모두 이 성질에서 나온다.

## 효과 없는 것들

프롬프트를 고칠 때 흔히 손대지만 출력이 달라지지 않는 것들이다. 여기에 쓴 토큰은 제약조건이나 예시로 돌린다.

- **어조와 예의**: 존댓말·반말, "제발 잘 부탁드립니다" 같은 표현은 품질과 무관하다.
- **길이 자체**: 성공을 가르는 것은 길이가 아니라 명확성과 구체성이다.
- **문장 형태**: 행동을 규정하는 지시는 단문, 판단 근거를 주는 맥락은 서술로 쓴다. 단문으로 쓰면 모호해지는 내용은 맥락이므로 서술이 맞다.

| 유형 | 효과 |
|---|---|
| 짧고 모호 | 최악 — 모델이 의도를 추측해야 한다 |
| 짧고 명확 | 단순 작업에 최적 |
| 길고 구체적 | 복잡한 작업에 최적 — 맥락·제약·예시 포함 |
| 길고 장황 | 해로움 — 핵심이 묻힌다 |

## 세 가지 골든룰

### 1. 하드코딩 회피

실패 케이스 하나를 좁은 규칙으로 굳히지 않는다. 그 케이스가 왜 실패했는지 설명하는 원칙을 택한다.

하드코딩 신호:

- 미지의 변형이 나올 자리에 정확한 값을 다수 나열한다.
- 테스트 실패 후 "하지 마" 패치를 반복해서 덧붙인다.
- 미래에 C 같은 케이스가 나올 상황에서 "A면 X, B면 Y"로 분기한다.
- 입력 복잡도가 변하는데 고정 임계값을 판단 기준으로 쓴다.

하드코딩이 아닌 것:

- 출력 스키마, 날짜 형식, enum 이름, 필수 필드명은 명세다.
- 태스크를 설명하는 도메인 사실은 컨텍스트다.

### 2. 충분한 컨텍스트 제공

모델은 지시문 자체뿐 아니라 그 지시의 이유가 필요하다.

판단에 영향을 주는 누락된 컨텍스트를 넣는다:

- 출력 목적: 결과를 누가/무엇이 소비하는가.
- 이유: 그 지시가 왜 존재하는가.
- 실패 비용: 거짓 양성과 거짓 음성 중 무엇이 더 나쁜가.
- 입력 속성: 품질, 형태, 모호성, 예상 편차.

경고 신호:

- MUST, NEVER, "always", "절대"가 이유 없이 등장한다.
- 금지에 "대신 이렇게 하라"는 행동이 없다.
- 형식만 지정하고 비어 있거나 부분적이거나 모호한 입력의 처리 방법이 없다.

### 3. 최적화된 예시 사용

원칙만으로 여전히 모호할 때만 예시를 쓴다. 예시는 경계를 명확히 해야 하며 숨은 테스트 세트가 되어선 안 된다.

좋은 예시:

- 포함 케이스와 제외 케이스를 짝으로 보여준다.
- 분류의 이유를 설명한다.
- 일회성 테스트 케이스가 아니라 일반화된 패턴을 쓴다.
- 프롬프트가 실행될 도메인과 일치한다.

경고 신호:

- 양성 예시만 있다.
- 여러 예시가 같은 패턴을 반복한다.
- 특정 테스트 실패를 그대로 대표 예시로 붙인다.
- 원칙이 이미 명확한데도 예시가 남아 있다.

## 균형점

세 골든룰은 서로 당긴다. 하나를 끝까지 밀면 다른 하나를 깬다.

- 맥락을 너무 구체적으로 주면 하드코딩이 된다.
- 맥락이 충분하면 예시가 오히려 군더더기가 된다.
- 예시가 너무 구체적이면 그 자체가 하드코딩이다.

판단 기준은 하나다. **프롬프트에 적혀 있지 않은 엣지 케이스를 상상했을 때, 이 프롬프트만 읽은 LLM이 올바르게 처리할 수 있는가.**

검토 대상이 고유한 프로세스 역학(적대적 토론, 멀티 라운드 자기 교정, 반복 정제)을 가지면 범용 골든룰과 최적 방향이 반대일 수 있다. 예를 들어 단발성 리뷰에서 잘못된 승인은 비용이 낮지만, 적대적 토론에서는 토론을 끝내 버려 복구가 안 된다. 이때는 위반을 지적하되 최종 판단은 범위 밖으로 남기고, 방향이 뒤집힐 수 있음을 경고한다.

## 안티패턴

- 실패-금지 패치 루프: 실패마다 좁은 금지를 하나씩 더 붙인다.
- 노력으로서의 장황함: 문구 반복, 감정적 강조, 출력을 바꾸지 않는 배경 설명.
- 정보 손실 후 복구: 한 단계가 데이터를 버리고 이후 단계가 다시 추론하려 한다.
- 핵심 지시의 단일 배치: 긴 프롬프트에서 핵심 규칙이 한 번만 나와 희석된다.
- 용어 모호성: 골든룰이 내용의 품질이라면 용어는 그 내용을 실어 나르는 언어의 품질이다. 언어가 모호하면 좋은 원칙도 의도대로 전달되지 않는다. 세 가지로 본다.
  - **주체와 대상을 명시한다**: "검토한다"는 누가 무엇을 검토하는지 없으면 LLM이 임의로 정한다.
  - **구체 동사와 구체 명칭을 쓴다**: "처리한다"는 검증인지 변환인지 필터링인지에 따라 출력이 완전히 달라진다.
  - **일반 명사를 재사용하지 않는다**: result, data, item, content, target이 문서 안에서 서로 다른 대상을 가리키면 지시가 엉뚱한 대상에 적용된다. 하나의 대상은 하나의 표현으로, 하나의 표현은 하나의 의미로 쓴다.
- 컨텍스트 오염: 로그, 이전 실패, 다른 단계의 추론이 현재 단계 판단에 새어 든다.

## 체크리스트

체크리스트는 자동 처방이 아니라 진단 렌즈로 쓴다. 위 안티패턴과 겹치면 안티패턴 항목을 기준으로 삼는다.

- 같은 근본 실패를 세 개 이상의 예외 규칙이 덮고 있는가?
- 각 금지가 이유와 대체 행동을 설명하는가?
- 분류가 필요한 곳에 거짓 양성 대 거짓 음성 비용이 명시됐는가?
- 예시가 이유를 동반한 경계 짝을 이루는가?
- 측정 임계값이 테스트 복사가 아니라 태스크로 정당화됐는가?
- 행동 지시가 행위자·대상·구체적 동사를 명명하는가?
- 다단계 프롬프트에서 역할·입력 범위·출력 책임이 분리됐는가?
- 데이터 정규화 시 보존과 폐기 규칙이 명시됐는가?
- 긴 프롬프트에서 핵심 지시가 복붙 반복이 아니라 프레이밍·검증·출력 확인으로 보강됐는가?

## 보고 전 자체 점검

검토나 재작성을 마치기 전에 확인한다:

- 제안한 변경이 프롬프트의 핵심 목적을 보존하는가.
- 변경이 적대적 검토, 반복 정제, 자기 교정 같은 워크플로 실제 동역학과 충돌하지 않는가.
- 실패 비용의 방향이 이 워크플로에서도 유지되는가.
- 수정이 원본보다 더 좁은 하드코딩 규칙을 추가하지 않는가.
