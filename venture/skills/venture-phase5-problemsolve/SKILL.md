# 실행

## 사전 준비

- 아래 `companies/<회사>`의 `<회사>`는 `V<YYMMDD>-<한글회사명>` 형식의 회사 폴더명이다. 사용자가 한글회사명만 말하면 `companies/`에서 `V*-<한글회사명>` 폴더를 찾아 쓰고, 날짜가 다른 폴더가 둘 이상이면 임의로 고르지 말고 어느 것을 쓸지 사용자에게 확인한다.
- 회사 작업공간: `companies/<회사>`
- 입력 파일 존재 여부를 확인한다.
  - `companies/<회사>/README.md`
  - `companies/<회사>/distillation.md`
  - `companies/<회사>/values.md`
- 출력 폴더가 없으면 생성한다.
  - `companies/<회사>/texts/`
- Markdown 파일 읽기와 쓰기는 항상 UTF-8을 명시한다.
- PowerShell에서 한글 파일을 확인할 때는 먼저 `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)`를 실행한 뒤 `Get-Content -LiteralPath <path> -Encoding UTF8`로 읽는다.

## 입력 내용

- `README.md`
  - 회사명
  - 홈페이지 URL
  - 작성 방향
  - 현재 진행 상태
- `distillation.md`
  - 회사 개요
  - 주요 제품·서비스
  - 핵심 기술
  - 특허·인증
  - 시장환경
  - 경쟁·대체재 환경
  - 회사 기술의 위치
  - 차별성 작성 포인트
  - 확인 필요
- `values.md`
  - 기본 정보
  - 신청 유형
  - 기술·인증·사업화 값
  - 재무·협업·자금·ESG 후보

## 작업 내용

- 메인 에이전트는 작성 sub-agent를 호출하기 전에 `문제`, `해결`, `경과`, `계획` 키포인트를 먼저 정리한다.
- 키포인트는 별도 파일로 저장하지 않고 작성 sub-agent 프롬프트에 공통 제공한다.
- 4개 작성 sub-agent를 병렬로 호출해 각 항목 초안을 작성한다.
- 각 작성 sub-agent는 자기 항목의 본문 초안만 반환하고 파일을 수정하지 않는다.
- 검사 sub-agent는 4개 초안을 함께 검토해 흐름, 중복, 모순, 심각한 사실 오류, 명백한 창작, 작성자 방어식 표현을 점검한다.
- 메인 에이전트는 검사 결과를 확인한 뒤 최종 문구를 4개 Markdown 파일로 저장한다.

## 작문 규칙 로드

작문 규칙 정본은 아래 한 파일이다. 규칙을 이 파일에 복제하지 않는다.

```
skills/venture/references/writing-rules.md
```

- 작성·검사 sub-agent를 호출하기 전에 프로젝트 루트 기준 위 경로를 Read로 읽는다. 이미 읽었다고 판단해 건너뛰지 않는다.
- 파일 첫 절인 `## 역할과 입장`을 먼저 적용한다. 다른 모든 규칙보다 우선하며, sub-agent 프롬프트에 반드시 함께 포함한다.
- 읽지 않은 상태로 sub-agent를 호출하지 않는다.
- sub-agent 프롬프트에는 해당 절 전문을 그대로 포함한다. 요약하거나 경로만 알려주지 않는다.
- 규칙 파일의 `phase별 적용 범위` 표에서 이 phase에 해당하는 행을 확인하고 그대로 적용한다.

## 작성 sub-agent 공통 제공 내용

- 작성 규칙: 작문 규칙 파일의 `## 작문 공통 규칙` 전문
- 공통 키포인트:
  - 문제: 메인 에이전트가 입력 자료에서 정리한 회사가 해결하려는 문제
  - 해결: 메인 에이전트가 입력 자료에서 정리한 회사의 해결방안과 차별성
  - 경과: 메인 에이전트가 입력 자료에서 정리한 현재까지의 기술개발 근거와 성과
  - 계획: 메인 에이전트가 입력 자료에서 정리한 향후 3년 기술개발 방향
- 입력 자료:
  - `README.md`의 작성 방향
  - `distillation.md`의 회사 개요, 주요 제품·서비스, 핵심 기술, 특허·인증, 시장환경, 경쟁·대체재 환경, 회사 기술의 위치, 차별성 작성 포인트, 확인 필요
  - `values.md`의 기본 정보, 신청 유형, 지식재산권 보유 현황, ISO 인증 현황, 기술개발 성과, 연구개발 조직·인력·비용 후보
- 회사 제공 특허·인증·기술자료는 신청서 작성 근거로 신뢰한다.
- `values.md`의 `### company_application_status` 블록에서 `status: ready`, `value: new_company`이면 신규기업 관점을 반영한다.
- `values.md`의 `### company_application_status` 블록에서 `status: ready`, `value: reconfirmation_company`이면 재확인 기업 관점을 반영한다.
- `### company_application_status` 블록의 `status`가 `ready`가 아니면 일반적인 문제해결·기술개발 관점으로 작성한다.
- 성과·시장 수치·인력·예산·계약·투자 계획은 `distillation.md`와 `values.md`의 상태에 맞춰 확정 실적, 목표, 추정, 추진 계획이 구분되도록 작성한다.

## phase5 작성 방식

- 4개 항목(개발 배경 → 솔루션 → 기술개발 추진경과 → 향후 기술개발 계획)이 하나의 논리로 이어지게 작성한다: 배경에서 정의한 문제를 솔루션이 해결하고, 그 기술의 확보 경과와 향후 발전 계획으로 연결한다.
- 기술은 고객 문제, 기존 방식의 한계, 당사의 해결 방식과 연결해 설명한다(작문 규칙 파일의 `## 작문 공통 규칙`의 `기술명(해결 문제): 작동 방식·기대효과` 패턴 활용).
- 특허·인증·기술자료는 기술 경쟁력과 사업화 가능성의 근거로 적극 활용한다.
- 연도·단계·연차별 실행 단위, 수치 표기와 실적/목표 구분 등 세부는 아래 항목별 작성요령과 작문 규칙 파일의 `## 작문 공통 규칙`을 따른다.

## 항목별 작성 sub-agent 제공 내용

### problem_background

- 출력 항목: 개발 배경과 필요성
- 반환 내용: 개발 배경과 필요성 본문 초안
- 항목 작성요령:
  - 제품/서비스의 개발 배경 및 필요성에 대해 기술한다.
  - 주어진 자료를 바탕으로 회사가 해결하고자 하는 문제를 먼저 정의한다.
  - 회사가 어떤 회사인지 주력 제품·서비스를 중심으로 간단히 제시한다.
  - 회사의 차별성과 장단점을 간단히 요약한다.
  - 회사의 지향점과 현재 발전 방향을 제시한다.
  - 개발 완료 또는 개발 중인 기술·제품·서비스의 구체적 개발 배경과 동기를 제시한다.
  - 소비자, 시장, 사회가 겪는 불편함과 문제점을 구체적으로 제시한다.
  - 경쟁사 또는 대체재 현황은 회사 기술의 필요성을 설명하는 범위에서 제시한다.
  - 재확인 기업인 경우 기존 기술의 개선 사항 또는 신규 개발 기술의 개발 배경을 제시한다.
  - 배경의 원인은 소비자·시장·산업/기술·규제 측면으로 나누어 입체적으로 제시한다.
  - 자료에 있는 정량 통계(민원·사고 빈도, 유실률, 시장 비중 등)와 규제·정책·트렌드 트리거를 문제의 심각성·시의성 근거로 활용한다. 민원 건수·사고 빈도·유실률처럼 출처가 있어야 하는 사실 통계는 자료에 없으면 만들지 않는다(시장 규모·성장률처럼 추정 가능한 값은 작문 규칙 파일의 `## 작문 공통 규칙`의 `### 수치·근거`대로 추정치로 제시한다).

### solution

- 출력 항목: 솔루션과 경쟁력 확보 방안
- 반환 내용: 솔루션과 경쟁력 확보 방안 본문 초안
- 항목 작성요령:
  - 문제 해결 방법으로서 제품·서비스를 소개한다.
  - 개발 배경에서 제시한 문제를 회사 보유 기술·제품·서비스로 어떻게 해결하는지 구체적으로 제시한다.
  - 사업아이템의 핵심 기능, 비즈니스 모델, 경쟁력 확보 방안을 설명한다.
  - 기존 제품·서비스 대비 우위성과 차이점을 특허, 인증, 기술자료, 시험·성능 인증 내용(계획 포함), 산업재산권 확보 또는 확보 계획 등 구체적 근거와 연결해 설명한다.
  - 단순히 '기능이 더 좋다', '더 편리하다'는 표현은 지양하고, 시장에서 고객의 구매 형태를 변화시킬 차별화 요소를 명확히 제시한다.
  - 핵심기능 → 비즈니스 모델 → 경쟁 우위 순으로 구성하고, 각 기능은 개발 배경에서 제시한 문제와 1:1로 대응시켜 설명한다.
  - 우위성은 가능하면 자사 vs 기존 방식의 항목별 대조(성능·비용·운영 등)로 구체화한다.

### tech_progress

- 출력 항목: 기술개발 추진 경과
- 반환 내용: 기술개발 추진 경과 본문 초안
- 항목 작성요령:
  - 제품·서비스 관련 기술개발 추진 경과를 작성한다.
  - 목표 기능 구현을 위한 기술 개발 노력을 설명한다.
  - 기술 확보, R&D, 상용화 여부, 인증 확보, 인력, 예산 확보 관점에서 현재까지의 추진과정을 단계적으로 작성한다.
  - 확인된 특허, 인증, 기술자료를 현재까지 축적된 기술개발 성과로 연결한다.
  - 개발 이력, 인력, 예산, 상용화 실적은 확인된 내용은 실적으로, 목표와 예정 사항은 계획 표현으로 구분해 작성한다.
  - 시간 흐름(연도/단계)에 따라 배열하고 특허·인증 확보 시점을 연월로 명시한다.
  - 실증·PoC·납품·계약 실적이 있으면 추진경과의 핵심 근거로 우선 배치한다.

### tech_plan

- 출력 항목: 향후 3년간 기술개발 계획
- 반환 내용: 향후 3년간 기술개발 계획 본문 초안
- 항목 작성요령:
  - 그간의 기술개발을 바탕으로 앞으로 발전시키고자 하는 기술 목표를 제시한다.
  - 기술 목표 달성을 위한 추가 기술 확보, 자체개발, 외주, 기술이전, 인력, 연구개발 예산 확보 계획을 향후 3년 관점에서 작성한다.
  - 세부 숫자가 제한적이어도 연차별 예산·인력 규모와 정량 목표를 추정·목표 표기(`약`, `예상`, `목표`)로 제시하고, 표준화·문서화 항목만으로 연차를 채우지 않는다.
  - 기술 고도화 방향·표준화·적용 확대·품질관리는 위 예산·인력·정량 목표와 함께 배치하며, 그것만으로 연차를 대체하지 않는다.
  - 투자·채용·계약 계획은 확정 사항과 추진 예정 사항이 구분되도록 작성한다.

## 검사 sub-agent 제공 내용

- 검사 규칙: 작문 규칙 파일의 `## 작문 검사 규칙` 전문
- 메인 에이전트가 정리한 공통 키포인트
- 작성 sub-agent가 반환한 4개 초안
- 초안 확인에 필요한 `distillation.md` 내용
- 초안 확인에 필요한 `values.md` 내용

## 검사 sub-agent 작업

- 4개 초안이 문제 → 해결 → 경과 → 계획 흐름으로 연결되는지 점검한다.
- 항목 사이에 같은 문장이나 같은 논리가 과도하게 반복되는지 점검한다.
- 항목 사이에 기술, 성과, 계획, 신청기업 상태가 서로 모순되는지 점검한다.
- 심각한 사실 오류, 명백한 창작, 벤처인증 제출문에 어울리지 않는 작성자 방어식 표현을 점검한다.
- 최종 권장 문구 4개를 반환한다.

## 출력 내용

- 출력 파일:
  - `companies/<회사>/texts/problem_background.md`
  - `companies/<회사>/texts/solution.md`
  - `companies/<회사>/texts/tech_progress.md`
  - `companies/<회사>/texts/tech_plan.md`
- 각 파일의 `char_count`는 프론트매터와 제목을 제외한 본문 글자수만 기록한다.
- 각 파일의 `source`에는 실제 사용한 근거 파일을 기록한다.
- 각 출력 파일은 아래 형식을 따른다.

```markdown
---
field_id: <field_id>
status: ready
char_count: 000
source:
  - distillation.md
  - values.md
notes:
  - 필요 시 작성 기준 또는 확인 필요 사항
---

# <항목 제목>

본문
```

## 사후 처리

- `README.md`의 자료 위치에 아래 경로를 추가한다.
  - `problem_background: texts/problem_background.md`
  - `solution: texts/solution.md`
  - `tech_progress: texts/tech_progress.md`
  - `tech_plan: texts/tech_plan.md`
- `README.md`의 진행 상태를 `venture-phase6-market`으로 바꾼다.
- 한글 깨짐이 없는지 확인한다.
- 글자수는 작성 sub-agent의 `char_count` 자기보고를 신뢰하지 말고, `uv run python scripts/check_charcount.py <회사명> problem_background solution tech_progress tech_plan`으로 실측 검증한다.
- 900자 미만이면 보강, 1000자 이상이면 압축해 재저장하고, 각 파일의 `char_count`에는 실측값을 기록한 뒤 스크립트가 전부 OK가 될 때까지 반복한다.
