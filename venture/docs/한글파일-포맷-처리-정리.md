# 한글파일 포맷 처리 정리

## 결론

현재 시스템은 이력서 원본 중 `.hwp`와 `.hwpx`를 처리 대상으로 인정하고, Google Drive에서 파일을 임시로 내려받은 뒤 본문 텍스트만 추출해서 DB 처리 흐름으로 넘깁니다.

핵심은 원본 한글 파일을 그대로 DB에 저장하는 것이 아니라, 사람이 읽는 본문을 텍스트로 뽑아 `FileData.extracted_text`와 표준 텍스트 캐시에 남기는 것입니다. 이후 이 텍스트가 단일 후보자 이력서로 판정되면 LLM 구조화 추출과 후보자 DB 저장 단계로 이어집니다.

## 지원 범위

지원하는 한글 파일은 두 종류입니다.

| 포맷 | 의미 | 현재 처리 |
|---|---|---|
| `.hwp` | 오래된 한글 문서 포맷입니다. 내부 구조가 복잡한 바이너리 문서입니다. | `kordoc`으로 먼저 변환하고, 실패하면 `hwp5txt`를 보조 수단으로 시도합니다. |
| `.hwpx` | 비교적 최신 한글 문서 포맷입니다. 압축 파일 안에 문서 내용을 담는 방식입니다. | `kordoc`으로 Markdown 텍스트 변환을 시도합니다. |

지원 대상 여부는 `data_extraction/services/supported_formats.py`의 `TEXT_SOURCE_EXTENSIONS`와 `TEXT_SOURCE_MIME_TYPES`가 기준입니다. 여기에는 `.hwp`, `.hwpx`, `application/haansofthwp`, `application/hwp`, `application/vnd.hancom.hwp`가 포함되어 있습니다.

## 전체 처리 흐름

1. Google Drive 변경분이나 인벤토리에서 파일을 발견합니다.
2. 확장자와 MIME 타입을 보고 한글 파일이 처리 대상인지 판단합니다.
3. `extract_drive_texts`가 원본 파일을 임시 위치로 다운로드합니다.
4. 다운로드된 파일의 앞부분을 읽어 실제 컨테이너가 맞는지 빠르게 검사합니다.
5. `.hwp` 또는 `.hwpx`이면 한글 변환기로 본문을 추출합니다.
6. 추출된 본문에서 중복 줄, 빈 줄, 사무용 프로그램 잡음을 줄입니다.
7. 본문 품질을 검사합니다. 너무 짧거나 깨진 텍스트면 실패로 기록합니다.
8. 문서가 단일 후보자 이력서인지 판정합니다.
9. 단일 이력서이면 표준 텍스트 캐시와 DB의 `FileData.extracted_text`에 저장하고 다음 구조화 단계로 넘깁니다.

## 실제 코드 위치

| 역할 | 위치 |
|---|---|
| 지원 확장자와 MIME 타입 기준 | `data_extraction/services/supported_formats.py` |
| 한글 파일 본문 추출 분기 | `data_extraction/services/text.py` |
| `kordoc` 실행과 `hwp5txt` 보조 처리 | `data_extraction/services/text.py` |

| 텍스트 추출 단위 테스트 | `tests/test_de_text.py`, `tests/test_text_extraction_hwp.py` |
| Drive 인벤토리 지원 포맷 테스트 | `tests/test_inventory_01db_drive_tree.py` |

## 한글 파일 추출 방식

### 1. 기본 변환기: `kordoc`

시스템은 `.hwp`와 `.hwpx` 모두 먼저 `kordoc`을 사용합니다. `kordoc`은 한글 문서를 Markdown 파일로 바꿔주고, 시스템은 그 Markdown 결과를 다시 일반 텍스트처럼 읽습니다.

실행 우선순위는 다음과 같습니다.

1. 프로젝트 안의 `node_modules/.bin/kordoc`
2. 서버 PATH에 설치된 `kordoc`
3. `npx -y kordoc`

현재 `package.json`에는 `kordoc`이 의존성으로 들어 있습니다. 따라서 일반적으로는 프로젝트 안의 `node_modules/.bin/kordoc`이 사용됩니다.

### 2. 보조 변환기: `hwp5txt`

`kordoc`이 실패하면 `.hwp` 문서에 대해 `hwp5txt`를 보조 수단으로 시도합니다. `hwp5txt`는 다음 순서로 찾습니다.

1. `.venv/bin/hwp5txt`
2. 서버 PATH의 `hwp5txt`

둘 다 없으면 `hwp5txt not found. Run: uv pip install pyhwp six` 오류로 처리됩니다.

## 파일 형식 사전 검사

변환기를 실행하기 전에, 다운로드된 파일이 실제로 해당 포맷처럼 보이는지 앞부분만 검사합니다. 의미는 “확장자만 `.hwp`인데 실제 파일은 다른 형식인 경우”를 빨리 걸러내는 것입니다.

| 확장자 | 통과 조건 | 실패 코드 |
|---|---|---|
| `.hwp` | 오래된 OLE 문서 헤더이거나 ZIP 헤더 | `invalid_hwp_container` |
| `.hwpx` | ZIP 헤더 | `invalid_hwpx_container` |

이 검사는 비싼 변환기를 돌리기 전에 명백히 잘못된 파일을 막기 위한 장치입니다.

## 실패 처리 기준

한글 파일 처리 실패는 크게 네 갈래로 나뉩니다.

| 상황 | 의미 | 기록되는 상태 |
|---|---|---|
| Drive 다운로드 권한 차단 | 파일은 보이지만 내려받을 권한이 없습니다. | `download_permission_failed` |
| 일반 다운로드 실패 | 일시적 네트워크 문제나 Drive 오류입니다. | `download_failed` |
| 변환기 실패 또는 시간 초과 | 파일은 내려받았지만 텍스트로 바꾸지 못했습니다. | `text_extract_failed` |
| 텍스트가 너무 짧거나 깨짐 | 변환은 됐지만 이력서 본문으로 쓰기 어렵습니다. | `empty_text` |

운영 판단에서는 파일 산출물보다 DB의 `FileData` 상태가 우선입니다. 텍스트 파일이 있더라도 DB에 반영되지 않았다면 아직 다음 단계로 완료된 것이 아닙니다.

## 시간 제한과 병렬 처리

`extract_drive_texts`는 한 파일의 텍스트 추출을 별도 프로세스로 실행합니다. 기본 시간 제한은 120초입니다. 한글 변환기가 오래 걸리거나 멈춰도 전체 작업자가 계속 묶이지 않게 하기 위한 장치입니다.

대량 처리에서는 여러 파일을 병렬로 처리합니다. 다만 한글 변환이나 LibreOffice 변환처럼 무거운 문서가 많으면 평균 처리 시간이 길어질 수 있으므로, 작업 시간이 느려지면 다음 묶음의 작업자 수를 줄이는 자동 조절이 들어갑니다.

## 운영 명령

기본 Drive 텍스트 추출은 아래 명령이 담당합니다.

```bash
uv run python manage.py extract_drive_texts --workers 8
```

운영 흐름에서는 보통 아래 wrapper 안에서 실행됩니다.

```bash
scripts/drive_realtime_filedata_pipeline.sh
```

이 wrapper는 Drive 변경분 확인, 처리 대상 분류, 텍스트 추출, 구조화 추출, DB 저장 흐름을 이어줍니다.

## 검증 방법

한글 파일 추출 로직만 빠르게 확인하려면 아래 테스트를 돌립니다.

```bash
uv run pytest tests/test_de_text.py::TestTextExtraction::test_hwp_extraction_uses_kordoc tests/test_text_extraction_hwp.py -q
```

지원 포맷 판정까지 같이 확인하려면 아래 테스트를 추가합니다.

```bash
uv run pytest tests/test_inventory_01db_drive_tree.py::test_build_file_row_marks_new_supported_formats -q
```

## 현재 한계

현재 방식은 문서 안의 텍스트를 뽑는 방식입니다. 그래서 아래 경우는 실패하거나 품질이 낮을 수 있습니다.

- 스캔 이미지처럼 글자가 이미지로만 들어간 한글 파일
- 비밀번호가 걸린 파일
- 손상된 한글 파일
- 확장자는 `.hwp`지만 실제 내용이 다른 파일
- 표나 도형 안에 복잡하게 들어간 텍스트
- 변환기가 지원하지 않는 일부 오래된 한글 문서 구조

이 경우 현재 파이프라인은 억지로 후보자 DB에 저장하지 않고, 실패 상태와 이유를 남기는 쪽이 맞습니다.

## 개선 후보

추후 품질을 올리려면 아래 방향을 검토할 수 있습니다.

1. 실패한 `.hwp` 파일만 모아 샘플별 실패 사유를 집계합니다.
2. 이미지형 한글 문서에 OCR 경로를 추가합니다.
3. `kordoc`과 `hwp5txt` 결과를 둘 다 얻을 수 있는 경우 더 풍부한 텍스트를 선택합니다.
4. 표 중심 이력서에 맞춘 후처리 규칙을 보강합니다.
5. 실패 상태별 운영 리포트를 만들어 권한 문제, 손상 파일, 변환기 문제를 분리해서 봅니다.

## 한 줄 요약

한글 파일 처리는 “Drive에서 `.hwp`/`.hwpx`를 찾는다 → 임시 다운로드한다 → 실제 파일 형식을 확인한다 → `kordoc` 중심으로 텍스트를 뽑는다 → 품질과 이력서 여부를 검사한다 → DB의 `FileData.extracted_text`에 남긴다”는 흐름입니다.
