## GBrain (장기 기억)

- 쓰기 위치: 기본 `note`/`put`은 `venture` 소스의 `agents/venture/private/`다. 공용 조회·쓰기는 카드와 현재 `policy`에 따라 `--source default`로 명시한다.
- 읽기: `query`·`query-all`은 공용과 venture만 검색한다. venture 기록만 볼 때는 `query-private`를 쓴다.
- 세션 시작 또는 작업 전 필수 실행:
  - `gbrain-venture get agents/venture/private/project-venture-writing-guide`
  - `gbrain-venture get agents/venture/private/project-venture-companies-path`
- 위를 읽은 뒤, 작업 주제의 회사명·화면명·스킬명·오류명으로 `gbrain-venture query`를 추가 실행한다.
- GBrain이 안 되면:
  - 프로젝트 판단이 필요한 작업은 멈추고 실패를 보고한다.
  - 단순 파일 확인, 명확한 사용자 지시, 상태 확인, 테스트 실행은 진행하되, GBrain을 읽지 못했다는 사실을 함께 보고한다.
- 코드와 GBrain이 다르면 **코드가 기준**. 검증 후 GBrain을 갱신한다.
- 작업, 대화 중 재사용 가치가 있는 규칙, 구조, 발견, 결정, 프로젝트 지식은 별도 지시가 없어도 판단 즉시 GBrain에 저장한다. 특히 디버깅으로 좁혀진 SSP는 반드시 저장한다.
- 기록은 대화 단위가 아니라 기능·도메인·규칙 단위로 짧게 저장한다. 슬러그는 `feedback-*`(사용자 지시·교정), `project-*`(프로젝트 구조·정본 경로·목표), `reference-*`(외부 자원·자격증명 위치) 접두어를 쓴다.
- 일반 작업 규칙은 GBrain이 아니라 이 문서 수정으로 반영한다.
- 저장 후 어느 슬러그에 반영했는지 답변에 짧게 남긴다.
- 단순 실행 로그, 일회성 결과, 코드·git 이력으로 바로 확인 가능한 내용은 저장하지 않는다.
- 세션 시작 시 자동 로드되는 로컬 `memory/MEMORY.md`는 **GBrain 슬러그 색인**일 뿐이다. 내용은 GBrain에만 두고, 로컬 memory 폴더에 본문 파일을 새로 만들지 않는다.

## 작업 전
- 사용자 변경은 되돌리지 않는다. 되돌려야 할 이유를 발견하면 되돌리지 말고 보고 후 지시를 기다린다.
- 사용자가 요청하지 않은 리팩터링·기능 확장은 하지 않는다.
- 코드/UI 수정 전 아래 5항목을 먼저 잠근다. 잠금 = 선언한 뒤 사용자 승인 없이 바꾸지 않는 것.

  **작업 목적**:
  - <작업 목적1>

  **허용 변경**:
  - <허용 변경1>

  **금지 변경**:
  - <금지 변경1>

  **검증 방법**:
  - <검증 방법1>

  **최소 코드 게이트**:
  - 기존 파일·함수·클래스 안에서 해결 가능한가?
  - 새 파일·새 클래스·새 helper가 실제 복잡도를 줄이는가?
  - 테스트용·진단용·임시 방어 코드가 최종 경로에 남지 않는가?
  - 수정 후 실행 순서가 더 복잡해지지 않고 한눈에 읽히는가?
  - 하나라도 아니면 코드를 작성하지 말고 더 작은 수정으로 다시 설계한다.

## 게이트 공통 규칙
- 용어: 최종 경로(SSP, Single Success Path) = 작업물이 실제로 실행되는 단 하나의 공식 경로. 이 문서의 「최종 경로」는 모두 같은 뜻이다.
- 게이트 조합: 모든 코드/UI 수정은 「작업 전」의 5항목 잠금을 기본으로 한다. 최종 경로가 있는 작업물(스크립트·스킬·워크플로우·프롬프트·지침)을 다루면 「최종 경로 하드 게이트」를, 에러·실패 대응이면 「문제 해결 원칙」을 겹쳐 적용한다. 겹칠 때 같은 항목은 한 번만 선언한다.
- 검증 방법: 수정한 최종 경로만 실행해 통과를 판단한다. 별도 runner·임시 스크립트·수동 보정·사후 보정·우회 경로로 얻은 성공은 통과가 아니다.
- 자명한 수정: 원인과 수정이 관측값으로 즉시 확인되는 단순 수정은 게이트 선언을 근거 한 줄로 갈음한다.
- 무폴백: 목적에 필수인 값을 못 만들면 지어내지 말고 `raise`한다. try/except·기본값·캐스팅·폴백·삼키기로 실패를 정상 결과처럼 만들지 않는다.
- 임시 코드: 조사·진단용 임시 코드·파일은 결과를 최종 경로에 병합하고 삭제하기 전까지 미완료다.
- 실패 복구: 검증이 실패하면 병합한 미검증 수정을 즉시 병합 전 상태로 되돌린다.

## 문제 해결 원칙

- 순차 강제: 게이트 1 → 2 → 3을 순서대로 통과한다. 앞 게이트의 통과 기준을 충족하기 전에는 다음 게이트로 진입하지 않는다. 게이트 3 전에는 새 패치, 방어 코드, 우회 경로, 폴백을 만들지 않는다.
- 원인 규명 산출물은 과정 중계가 아니라 수정 진입 조건이다. `### 출력 형식 및 설명 방식`의 과정 중계 금지보다 우선한다.
- 예외: 「게이트 공통 규칙」의 자명한 수정에 해당하면 게이트 1~2를 현상, 관측값, 수정 대상, 자명한 이유 네 항목 한 줄씩으로 갈음한다.

### 게이트 1 — 현상·원인 분리
- 아래 제목을 빠짐없이 작성한다. 작성하지 않은 항목은 완료로 보지 않는다.
  1. **현상**: 추정·해석 없이 실제 관측값만 쓴다.
  2. **원하는 동작**: 사용자가 기대하는 최종 상태를 한 문장으로 쓴다.
  3. **원인 후보**: 현상과 분리해 따로 쓴다.
- 통과 기준: 현상과 원인이 구분돼 있다. 원인 칸이 현상의 나열·재서술이면 미통과다.

### 게이트 2 — 근본 원인 규명
- 아래 제목을 빠짐없이 작성한다. 작성하지 않은 항목은 완료로 보지 않는다.
  1. **Why 단계 수**: `3 Whys` 또는 `5 Whys`로 선언하고 선택 근거를 쓴다.
  2. **원인 사슬**: 게이트 1의 원인 후보에서 시작해 `### 3 Whys/5 Whys` 형식으로 원인의 원인을 파 내려간다.
  3. **관련 사실**: 원인 사슬에 넣지 않은 병렬 사실, 영향, 방어책, 다른 증상을 분리한다.
  4. **줌아웃 여부**: 트리거 해당 여부와 판단 근거를 쓴다. 해당하면 `### 줌아웃/줌인 리셋`을 수행한 뒤 원인 사슬을 다시 잇는다.
- `5 Whys` 필수 조건: 같은 실패 반복, 최종 경로 수정, 브라우저 자동화, LLM·프롬프트·스킬·워크플로우 동작 변경, 여러 단계의 입력·출력 계약이 얽힌 문제, 다음 행동이 또 다른 패치인 경우.
- `3 Whys` 허용 조건: 실패 경계가 한 단계이고, 관측값이 직접적이며, 원인 후보가 하나의 입력·출력 계약 안에 있는 경우.
- 판단이 애매하면 `5 Whys`를 선택한다.
- 통과 기준: 증거로 확인된 근본 원인 하나에 도달했다. 도달 전에는 해결책을 고르지 않는다.

### 게이트 3 — SSP 수정
1. **대상 SSP 선언**: 수정할 최종 경로를 먼저 정하고, 「최종 경로 하드 게이트」의 수정 전 4항목 선언을 완료한다.
2. **해결책**: 게이트 2의 근본 원인을 제거하는 최소 변경만 선택한다. 패치를 더할 때도 우회 경로가 아니라 최종 경로에 병합한다.
3. **금지**: 「게이트 공통 규칙」의 무폴백 규칙을 따른다.
4. **검증**: 「게이트 공통 규칙」의 검증 방법을 따르되, 같은 실패의 재발 여부까지 확인한다.
5. **완료 보고**: 근본 원인, 원인을 제거한 변경, 재발하지 않는 이유, 단일 원인 사슬 여부, 검증 방법과 결과를 포함한다.

### 3 Whys/5 Whys
- 각 Why는 아래 네 칸을 모두 채운다.
  - **주어**: 직전 답에서 나온 핵심 원인만 쓴다.
  - **질문**: `왜 <주어>가 발생했나?` 형식으로 쓴다.
  - **답**: 직전 단계의 원인이 발생한 직접 메커니즘만 쓴다.
  - **증거**: 로그, DB row, 실행 기록, 입력 데이터, 외부 유입 경로 중 하나 이상을 쓴다.
- 증거가 없는 Why는 카운트하지 않는다. `미검증`으로 표시하고 게이트 2 통과 판정 전에 추가 조사한다.
- 최종 Why의 답이 제거 가능한 근본 원인으로 끝나지 않으면 원인 사슬 실패로 본다.
- 병렬 사실, 영향, 방어책, 다른 증상은 원인 사슬에 넣지 말고 `관련 사실`로 분리한다.
- 다음 Why의 주어가 새 증상·영향·해결책으로 바뀌면 원인 사슬이 끊긴 것으로 보고 줌아웃한다.

### 줌아웃/줌인 리셋
- 트리거: 원인 사슬이 병렬 사실 목록으로 흐르거나, 다음 Why의 주어가 없거나, 같은 실패가 반복되거나, 다음 행동이 또 다른 패치일 때 수행한다.
- 목적: 해결책을 고르지 말고, 원인 사슬을 다시 시작할 정확한 경계를 찾는다.
- 수행 시 아래 제목을 빠짐없이 작성한다.
  1. **큰 그림**: 보호할 목적, 최종 경로 순서, 각 단계의 입력·출력·계약, 기준 증거, 증상 발생 단계, 미검증 가정을 쓴다.
  2. **다시 줌인**: 큰 그림에서 한 단계나 경계를 고르고, 그 경계를 다음 Why의 주어로 삼는다.
  3. **재작성 원인 사슬**: 선택한 경계에서 증상을 만드는 단일 메커니즘을 증거로 확인한다.
- 금지: 검증된 근본 원인에 도달하기 전에는 규칙·분기·폴백·우회 경로를 추가하지 않는다.


## 브라우저 조작 게이트
- 적용: 모든 브라우저 작업. 작업을 「조사」·「실행」·「반영」으로 나눠 판정한다.
- 판정 강제: 브라우저 작업을 하기 전에 반드시 이번 동작이 「조사」인지 「실행」인지 「반영」인지 먼저 밝힌다.
- **조사(직접 조작 허용)**: 디버깅, 화면 관찰, selector·좌표·marker 확인, 재현 실험은 직접 조작(브라우저 툴, 인라인 실행)으로 할 수 있다.
- **실행(직접 조작 금지)**: 실제 산출물을 만드는 조작(데이터 수집, 다운로드, 제출, 게시)은 직접 조작으로 하지 않는다. 최종 경로 스크립트의 명령어 호출로만 수행한다.
- **반영(즉흥 확정 금지)**: 조사에서 관찰한 것이나 대충 해본 1회 실행 결과만 근거로 브라우저 실행 코드를 수정해 확정하지 않는다. 이유: 손으로 재현한 성공은 코드의 성공이 아니고, 관찰 직후의 즉흥 수정이 검증된 최종 경로를 누더기로 만들기 때문.
- **반영 절차**: 조사 결과는 ① 게이트 조합에 따른 게이트를 거쳐 최종 경로 함수로 작성·병합하고 → ② 그 명령어를 코드로 실행해 테스트해서 통과해야 검증이다. 브라우저 수동 재현 성공은 통과가 아니다.
- **조사 후 정지**: 직접 조작으로 원인을 확인했더라도 곧바로 코드나 스킬을 고치지 않는다. 관측값, 수정 대상, 병합 단계, 검증 명령을 먼저 분리해 잠근 뒤 반영한다.
- **실패 시 복구**: 「게이트 공통 규칙」의 실패 복구를 따른다. 검증 안 된 수정을 최종 경로에 남겨두지 않는다.
- **보호 대상**: 이미 성공했던 최종 경로 함수와 배포 파일은 조사 중 임의로 바꾸지 않는다. 변경이 필요하면 기존 성공 근거와 충돌 여부를 먼저 확인한다.
- 최종 경로 함수가 실패하면 임시 우회 스크립트를 만들지 말고 **그 함수 자체를 수정**한다. 함수가 진화해야 도구가 누적 성장하고 재활용된다.
- 상세 기준: 이 섹션이 정본이고, `$web-automation` 스킬은 이 섹션을 보조한다. 둘이 다르면 이 섹션이 우선한다. 관련 GBrain: `agents/venture/private/feedback-step-by-step-approval`, `.../feedback-save-temp-only`, `.../reference-smes-login`.

## 최종 경로 하드 게이트 (SSP)
- 용어: 고아 패치 = 최종 경로의 어느 단계에도 병합되지 않는 변경. 순증가 = 대체·병합·삭제할 기존 요소 없이 최종 경로의 파일·분기·LLM 호출·프롬프트 블록·코드량을 늘리는 변경.
- 적용: 최종 경로가 있는 작업물(스크립트·스킬·워크플로우·프롬프트·지침)의 작성·분석·테스트·수정에 적용한다.
- 목적: 개별 사례 성공이 아니라, 하나의 최종 경로가 여러 사례에서 품질·속도·단순성·재현성을 높이도록 개선한다. 새 우회 경로를 붙이지 않고, 기존 경로를 교체·삭제·압축해 더 작고 정확하게 만든다.
- 모드: 현재 단계를 분석, 테스트, 수정 중 하나로 선언한다. 분석·테스트 단계에서는 최종 경로를 변경하지 않는다. 진단용 임시 코드와 검증 실패는 「게이트 공통 규칙」의 임시 코드·실패 복구를 따르고, 복구 후 분석 단계로 돌아간다.
- 사례값 금지: 특정 사례에만 존재하는 값·표현·산출물은 최종 지침·코드에 넣지 않는다. 구조·계약·역할 경계에서 생긴 반복 가능하고 기존 규칙과 충돌하지 않는 문제만 반영한다.
- 최소 코드: 「작업 전」의 최소 코드 게이트를 따른다.
- 수정 전 4항목 선언: 수정 단계에 들어가기 전에 다음 네 가지를 구체적으로 선언한다. 하나라도 선언하지 못하면 수정하지 않는다.
  - ① 최종 경로의 실행 단계: 주요 파일·함수, LLM 호출 단계, 검증 방법을 실행 순서대로 선언한다. 선언 밖의 새 단계·분기·runner·보정 흐름은 사용자 승인 없이 만들지 않는다.
  - ② 변경이 병합될 단계: 없으면 고아 패치이므로 추가하지 않는다.
  - ③ 최종 경로 안에서 대체·병합·삭제할 기존 요소: 없으면 순증가다. 순증가는 같은 변경 안에서 기존 요소를 제거·병합·압축해 최종 경로가 더 작거나 명확해질 때만 반영하고, 상쇄할 수 없으면 사용자 승인을 받는다.
  - ④ 병합 후 최종 경로만 실행하는 검증 방법: 「게이트 공통 규칙」의 검증 방법을 따른다.
- 신규 작성: 기존 경로가 없는 작업은 ①의 경로 선언이 초기 최종 경로가 되고, 이후 변경부터 ②~④를 적용한다.
- 자명한 수정: 「게이트 공통 규칙」의 자명한 수정 기준을 따른다. 이때 4항목 선언을 근거 한 줄로 갈음한다.
- 진화 인정: 변경 후 같은 원인에서 나온 실패가 검증 대상에서 재발하지 않고, 기존 통과 사례도 같은 최종 경로로 계속 통과할 때만 진화로 인정한다. 한 사례 통과나 임시 성공은 진화가 아니다.

## 작업 후
- 코드 변경 후, 완료 보고 전에 코드리뷰를 실행한다.
- 코드 리뷰는 리뷰만 한다. 테스트·수정·다른 LLM 호출은 하지 않고, 수정은 SSP 하드 게이트를 거쳐 수행한다.
- 완료 보고 전, 이번 작업에서 생긴 재사용 가능한 성공 방법·실패 원인·검증된 규칙을 GBrain 또는 스킬에 저장했는지 확인한다. 특히 디버깅으로 좁혀진 SSP는 반드시 저장한다.
