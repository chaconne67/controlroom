## 검은 화면 사고와 폐기한 경로

14:00에 에이전트가 추가한 `iros_hidden_manual_login.py`는 `SwitchDesktop`으로 사용자 입력 데스크톱을 `Default`에서 `ceoloan-iros-registry`로 전환했다. 돌아오는 동작은 같은 프로세스의 로그인 성공 또는 600초 대기 종료 뒤 `finally`에만 있었다. 사용자는 검은 화면으로 작업이 불가능해 14:06에 PC를 재시작했다고 보고했다. 코드와 직전 실행 기록이 이 화면 전환을 확인한다. 별도의 그래픽 드라이버 고장이나 Windows 파일 손상은 확인하지 않았다.

이것은 9월 13일/17일에 성공한 공식 경로의 요구사항이 아니다. 숨은 데스크톱은 사용자가 쓰는 입력 데스크톱을 그대로 두고 전용 Chrome만 분리하는 방식이다. Playwright와 함께 쓰며, 사용자 화면을 그 데스크톱으로 전환하지 않는다.

- 재부팅 후 관련 수집 프로세스와 해당 보조 파일을 실행하는 예약 작업이 없음을 확인했다.
- 기존 `shared-browser-verification.json`은 정적 검사와 모의 검사 기록이다. 실제 화면 안전성을 검증하지 못했으며, 이를 실행 안전성의 근거로 사용하지 않는다.
- 이 보조 경로를 복구하거나 `SwitchDesktop`을 다시 호출하지 않는다. 공식 공용 브라우저 실행층을 재사용한다.

## 로그인 복구의 실제 증거

GBrain `project/ceoloan-iros-registry-path`와 실제 `20260913_pay_001`, `20260917_model_c01_pre` 결과에서 저장 자격정보 자동 로그인과 결제/PDF 수령 성공을 확인했다. 이번에는 일반 로그인 화면의 숫자 입력칸이 비어 있어 사이트가 자동입력방지 문자 입력을 요구했다. 자격정보가 없는 상태가 아니었다.

주인님이 숫자를 화면에서 읽어 입력하도록 명시적으로 지시했다. 에이전트가 같은 전용 Chrome에서 숫자 이미지 영역만 캡처해 읽고, 저장 자격정보와 함께 화면 입력칸에 넣었다. 로그인된 홈 화면과 보이는 로그아웃 링크를 확인했다. 인증번호·자격정보 값은 이 문서나 GBrain에 기록하지 않는다.

그 뒤 공용 `stop()`으로 전용 Chrome을 닫고 공식 `dom_registry(..., until='home')`를 실행했다. `20260919_login_recovery_official_summary.json`은 `ok=true`, `authentication=already_authenticated`였다. 입력 데스크톱 `Default` 유지, 전경 변경 0회, 호출 종료 후 전용 Chrome 잔여 0개를 확인했다. 따라서 “창을 닫으면 세션이 반드시 없어져 사람이 다시 로그인해야 한다”는 앞선 안내는 이 실제 검증으로 정정한다.

같은 프로필의 정상 로그인 복구와 공식 명령 검증을 우선한다. 다른 추가 인증은 실제 종류를 확인하며, 보안문자라는 문구만 보고 새로운 데스크톱 전환이나 수동 로그인 절차를 만들지 않는다.
