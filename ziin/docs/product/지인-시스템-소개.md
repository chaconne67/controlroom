# 지인(G-in) 시스템 소개

2026-08-31 · 근거: X-Dime(Exdigm) 운영 코드 `main` @ `e84b9d1f`

X-Dime에서 실제 운영 중인 헤드헌팅 업무 시스템을 다른 헤드헌팅 회사가 쓸 수 있도록 범용화한 것이 지인이다. 이 문서는 그 시스템이 무엇이고 무엇을 하는지 사실 위주로 정리한 것이다. 광고 문구는 `카피액기스.md`와 `랜딩-문구.md`에 따로 있다.

---

## 1. 무엇인가

고객사의 채용 의뢰 한 건을 프로젝트로 만들고, 후보자를 찾고, 진행을 관리하고, 고객사 제출 서류와 채용공고를 만들어 내보내는 과정을 하나의 시스템에서 처리한다.

이력서를 보관하는 것이 아니라 **구조화된 후보자 데이터로 바꿔 두고, 그 데이터를 프로젝트 업무에 계속 쓰는 것**이 설계의 축이다.

웹 화면과 텔레그램 대화, 음성 지시가 같은 데이터와 같은 권한 위에서 돈다.

---

## 2. 시스템 구성

여섯 개의 업무 영역과 두 개의 에이전트 기반 구성으로 나뉜다.

| 영역 | 다루는 것 |
|---|---|
| `accounts` | 사용자, 권한 범위, 근태, 회사 이메일 계정, 외부 사이트 인증, 에이전트 프로필, 알림 설정 |
| `candidates` | 후보자와 그 학력·경력·자격·어학, 검색 세션, 임베딩, 블랙리스트, 평판 |
| `clients` | 고객사, 산업 분류, 계약, 제출 양식, 회사 프로필, 대학 티어, 우대 자격 |
| `projects` | 프로젝트, JD, 지원 진행, 액션, 제출물, 면접, 미팅 기록, 알림, 자동 게시, 뉴스 |
| `data_extraction` | 이력서 파일 수집·추출·저장, 구글 드라이브 동기화, 메일 점검, 품질 검증 |
| `auto_posting` | 채용 사이트별 게시 실행과 후보자 수집 |
| `hermes_integration` | 직원별 텔레그램 에이전트 연결 (선택 활성화) |
| `agent_infrastructure` | 에이전트 컨테이너 프로비저닝, 텔레그램 연결, LLM 게이트웨이 |

`projects`가 가장 크다. 모델 정의만 2,796줄이고 서비스 모듈이 37개다.

## 3. 기능

### 3.1 이력서 수집과 데이터화

이력서가 시스템에 들어오는 통로가 셋이다.

- 직접 업로드
- 회사 메일함 점검 — 첨부와 본문 링크를 함께 본다
- 구글 드라이브 동기화

들어온 파일은 원본을 드라이브에 두고, 내용을 이름·연락처·경력·학력·자격·어학 항목으로 추출해 후보자 레코드로 만든다. 추출 결과에는 품질 진단이 붙고, 항목별 점수와 불일치 보고를 남긴다.

같은 사람이 여러 이력서를 보내면 후보자를 하나로 묶고 이력서 버전을 함께 관리한다. 사람이 직접 고친 값은 자동 추출값보다 우선한다.

관련 모델: `Resume`, `FileData`, `ResumeUploadLedger`, `DataExtractionExecution`, `DiscrepancyReport`, `ValidationDiagnosis`, `DriveSyncCursor`, `MailplugMessageCheck`

### 3.2 후보자 검색

음성과 텍스트가 같은 경로로 들어간다. 언어모델이 헤드헌팅 표현을 해석해 검색 조건을 만들고, Django가 후보자 원본 필드에 그 조건을 적용해 조회한다.

용어집은 표현 해석만 돕는다. 후보자에게 분류값이나 태그를 새로 붙이지 않는다. 검색 결과는 실제 조회된 것이고 추정치가 아니다.

임베딩 기반 의미 검색도 함께 있다.

관련: ADR-0024, `candidates/services/search.py`, `search_glossary.py`, `embedding.py`

### 3.3 프로젝트 후보 발굴

전역 후보자 검색과 별개 기능이다. **조회하기 전에 계획을 세우고 사용자 승인을 받는다.**

에이전트가 프로젝트와 JD를 읽고 무엇을 찾을지, 어떤 조건으로, 어떤 방식으로 조회할지를 설명한다. 조회 방식 대안과 권장안, 누락 가능성까지 제시한다. 사용자가 승인해야 실행한다. 조건이나 원천이 바뀌면 다시 승인받는다.

내부 DB와 외부 채용 사이트에 같은 절차를 쓴다. 각 원천의 검색 형식으로 옮기는 것은 마지막 어댑터가 한다.

**점수, 순위, 자동 탈락을 만들지 않는다.** 후보 적합성의 최종 판단은 사용자에게 남긴다.

관련: ADR-0026 (2026-08-29). 언어모델이 적합도를 판단·정렬하던 이전 방식(ADR-0025)은 폐기됐다.

### 3.4 프로젝트와 진행 관리

프로젝트 하나가 고객사 의뢰 한 건이다. 국면은 서칭과 심사로, 상태는 진행중과 종료로, 결과는 성공과 실패로 나뉜다.

후보자 한 명의 진행은 다섯 단계를 지난다.

```
연락 → 사전 미팅 → 이력서 → 면접 → Closing
```

단계는 건너뛰거나 되돌릴 수 있고, 그 사실이 기록에 남는다. 탈락 사유를 남기고 나중에 복원할 수 있다.

진행은 액션 단위로 쌓인다. 액션에는 채널(대면·화상·전화·카톡·문자·이메일·링크드인)과 상태(대기·진행중·완료·건너뜀·취소)가 붙는다. 일부 액션은 산출물(서류 패키지·면접·사전미팅)과 연결된다.

관련: `projects/services/application_lifecycle.py`, `action_lifecycle.py`

### 3.5 고객사 제출 서류

후보자 데이터와 원본 이력서로 제출용 문서를 만든다. 표준 양식과 고객사별 양식을 쓸 수 있고, 출력 언어와 형식을 고를 수 있다.

초안 생성 → 변환 → 검토 → 확정의 단계를 거치며, 각 단계가 별도 서비스로 분리돼 있다. 완성된 문서는 다운로드 링크와 알림으로 전달된다.

관련: `recommendation_resume_ssp.py`, `draft_generator.py`, `draft_converter.py`, `draft_finalizer.py`, `draft_pipeline.py`, `submission.py`

### 3.6 채용공고 생성과 자동 게시

프로젝트 JD에서 외부 공개용 공고문을 만들고, 사이트별 게시 자료로 변환한 뒤 실제로 게시한다.

지원 사이트는 여섯 곳이다.

| 사이트 | 도메인 |
|---|---|
| BusinessPeople | bzpp.co.kr, businesspeople.co.kr |
| 자사 채용 사이트 | exdigm.com |
| 인크루트 | incruit.com |
| 잡코리아 | jobkorea.co.kr |
| PeopleNJob | peoplenjob.com |
| 사람인 | saramin.co.kr |

사이트마다 별도 구현이 있고 입력 항목과 공개 규칙이 다르다. 게시 상태는 게시 전·대기·진행중·성공·실패·건너뜀으로 추적하며, 사이트별 지원자 수를 기록한다. 운영 설정으로 사이트를 켜고 끈다.

같은 사이트 접속 경로를 후보자 수집에도 쓴다.

관련: `auto_posting/sites/`, `site_registry.py`, `projects/services/posting.py`, `auto_posting_workflow.py`

### 3.7 음성 업무 지시

음성을 받아 의도를 해석하고, 실행 전에 내용을 미리 보여준 뒤 확인을 받아 실행한다.

```
전사 → 의도 해석 → 미리보기 → 확인 → 실행
```

현재 해석하는 의도는 정해져 있다.

- 후보자 검색
- 프로젝트 생성
- 제출 서류 생성
- 면접 일정
- 현황 조회 · 할 일 조회
- 화면 이동
- 검증 요청 · 재실행 · 결과 조회

미팅 녹음을 올리면 전사하고 분석해 기록에 붙인다.

관련: `projects/services/voice/`

### 3.8 직원별 텔레그램 에이전트

직원 한 명당 텔레그램 봇 하나를 둔다. 에이전트는 그 직원의 계정 권한을 그대로 적용받는다.

에이전트가 별도의 업무 로직을 갖지 않는 것이 핵심이다. 사람이 쓰는 Django 화면이 같은 URL에서 HTML과 JSON을 함께 제공하고, 에이전트는 그 JSON 계약을 호출한다. 에이전트 전용 ORM 실행기나 화면별 전용 엔드포인트를 만들지 않는다.

```
직원 텔레그램 요청
→ 업무 용어 해석
→ OpenAPI에서 필요한 기능 하나 확인
→ 계약 검증 후 요청
→ 기존 화면 뷰의 JSON 응답
→ 직원 권한 안의 결과
```

관련: ADR-0002, ADR-0023, ADR-0010

### 3.9 그 밖의 기능

- **면접·미팅** — 일정, 결과, 사전 미팅 체크리스트, 녹음 분석
- **액션과 리마인더** — 할 일, 자동 액션, 알림벨, 텔레그램 알림
- **검증** — 지원 건별 검증 요청·재실행·결과 보고
- **뉴스** — 수집, 번역, 이슈 클러스터링, 키워드, 헤드라인 선정, 사용자 반응 기록
- **대시보드** — 프로젝트와 일정 현황
- **고객사 관리** — 등록, 계약, 로고 수집, 회사 정보 자동 채움
- **레퍼런스 데이터** — 대학 티어, 회사 프로필, 산업 분류, 우대 자격
- **브라우저 확장** — 채용 사이트에서 후보자 수집
- **후보자 부가 정보** — 블랙리스트, 평판, 급여 파싱, 프로필 사진

## 4. 설계 원칙

이 시스템의 성격을 결정하는 규칙들이다.

### 4.1 사람이 결정한다

- 후보 발굴은 계획을 승인받은 뒤에만 조회한다
- 후보에게 점수나 순위를 매기지 않고 자동으로 탈락시키지 않는다
- 결과가 너무 많거나 적어도 시스템이 조건을 바꿔 다시 조회하지 않는다. 조정안을 제안하고 기다린다
- 음성 지시는 미리보기와 확인을 거쳐 실행한다
- 생성된 서류는 사람이 검토한 뒤 사용한다

### 4.2 경로를 하나로 유지한다

같은 일을 하는 방법이 둘 이상 생기지 않게 한다. 후보자 검색은 음성이든 텍스트든 같은 경로를 쓰고, 텔레그램 에이전트는 사람이 쓰는 화면과 같은 경로를 쓴다. 단계 변경은 반드시 lifecycle 서비스를 지난다.

### 4.3 사람이 넣은 값이 우선한다

자동 추출이 사람의 수정을 덮어쓰지 않는다.

### 4.4 조회 결과는 실제값이다

검색 인원수를 추정하지 않는다.

## 5. 다른 제품과 다른 점

Bullhorn, Loxo, Recruit CRM 같은 제품도 ATS·CRM, 이력서 파싱, AI 매칭, 자동화, 다중 게시를 제공한다. 기능 보유 여부로는 구분되지 않는다. 실제 차이는 네 군데다.

| 구분 | 지인 |
|---|---|
| **국내 채용 채널** | 국내 사이트 여섯 곳의 실제 입력 항목·공개 규칙·게시 결과를 사이트별로 구현했다. 글로벌 job board 연동은 하지 않는다 |
| **AI의 위치** | 판단자가 아니라 준비자다. 점수·순위·자동 탈락이 설계에서 빠져 있다. 승인 절차가 코드에 들어 있다 |
| **대화 업무의 구조** | 에이전트가 별도 시스템이 아니라 사람용 화면의 API 표현을 쓴다. 직원별 권한이 그대로 적용된다 |
| **출발점** | 20년 운영된 헤드헌팅 회사의 내부 업무 체계에서 나왔다. 채용 시장을 밖에서 본 개발사의 범용 도구가 아니다 |

## 6. 경계 — 하지 않는 것

| 항목 | 내용 |
|---|---|
| 자동 채용 결정 | AI가 후보자를 최종 선택하지 않는다 |
| 자동 발송 | 고객사에 서류를 자동으로 보내지 않는다 |
| 점수·순위 | 후보 적합도를 수치화하지 않는다 |
| 글로벌 job board | 해외 채용 채널 연동이 없다 |
| 후보자·고객사 화면 | 외부인이 직접 쓰는 화면이 없다. 접점은 이메일과 문서다 |
| 음성 전 업무 지원 | 음성으로 실행할 수 있는 업무는 정해진 의도 목록 안이다 |

## 8. 범용화할 때 손봐야 할 곳

X-Dime 전용으로 박혀 있어 다른 회사에 팔려면 확인이 필요한 부분이다.

- **자사 채용 사이트 게시** — `exdigm.com` 도메인이 게시 대상 여섯 곳 중 하나로 들어가 있다. 도입 회사의 자사 사이트로 바꿀 수 있어야 한다
- **메일 연동** — Mailplug 기준이다. 다른 메일 서비스를 쓰는 회사는 연동을 추가해야 한다
- **레퍼런스 데이터** — 대학 티어표와 우대 자격 기준이 들어 있다. 회사마다 기준이 다를 수 있다
- **고객사 제출 양식** — 고객사별 템플릿이 데이터로 들어 있다. 도입 시 새로 채워야 한다
- **외부 사이트 인증** — 채용 사이트 계정을 회사별로 등록해야 한다
- **에이전트 인프라** — 직원 수만큼 컨테이너가 필요하다. 도입 회사 규모에 따라 비용이 달라진다
