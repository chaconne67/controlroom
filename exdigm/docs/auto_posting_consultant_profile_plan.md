# 자동게시 담당자 정보 자동 생산 통합 계획

## 1. 목표

- 프로젝트 배정과 무관하게 전체 활성 사용자 중 담당자를 선택할 수 있다.
- 선택한 담당자의 자동게시 연락 정보가 자동으로 완성된다.
- 사용자는 사이트별 이름·직책·이메일을 미리 입력하지 않는다.
- 자동게시 실행 이력은 게시 당시 담당자 정보를 snapshot으로 보존한다.
- 잡코리아의 등록 헤드헌터는 공개 담당자 프로필과 분리된 사이트 계정 자격으로 취급한다.
- 화면의 준비 상태는 실제 게시 가능 상태와 일치한다.

## 2. 사용자 계약

1. 사용자는 전체 활성 사용자 중 사이트별 담당자와 게시 사이트를 선택한다.
2. 시스템은 담당자의 `User.display_name`과 `User.email`을 사용한다.
3. 직책은 게시 필수값으로 요구하지 않는다.
4. 게시를 누르면 별도 설정 이동 없이 큐가 생성된다.
5. 외부 사이트가 강제하는 자격만 사이트 실행 계약에서 검증한다.

## 3. 최종 경로(SSP)

1. 프로젝트 등록·수정 화면이 게시 사이트와 프로젝트 담당자를 제출한다.
2. `PostingSettingsForm`은 사이트 선택과 활성 사용자 선택만 검증한다.
3. `enqueue_posting_workflow()`가 선택 담당자를 확정한다.
4. 큐 생성 시 담당자의 계정 이름·이메일을 `AutoPostingSiteRun.profile_snapshot`에 저장한다.
5. `build_auto_posting_payload()`가 snapshot으로 공통 footer와 사이트 payload를 조립한다.
6. `manage.py autoposting --site <site> --mode dry`가 기존 사이트별 단일 실행 클래스를 호출한다.

별도 프로필 생성·보정·fallback runner는 두지 않는다.

## 4. 구현 범위

### 4.1 데이터와 서버

- `ConsultantPostingProfile` 의존을 큐·폼·payload 경로에서 제거한다.
- snapshot 생산자는 `User`로 단일화한다.
- snapshot 필수값은 활성 사용자, 표시 이름, 이메일이다.
- 직책 필드와 직책 필수 검증을 제거한다.
- 기존 실행 이력의 `profile_snapshot`은 변경하지 않는다.
- 기존 사이트별 프로필 테이블은 데이터 존재 여부를 확인한 뒤 제거한다.

### 4.2 잡코리아 자격 분리

- 공고 footer의 이름·이메일은 다른 사이트와 동일하게 프로젝트 담당자 계정에서 만든다.
- 잡코리아의 `담당 헤드헌터` 선택값은 내부 사용자와 연결된 사이트 등록 신원으로 분리한다.
- 선택 담당자의 `User.jobkorea_headhunter_name`이 잡코리아 등록 목록에 있으면 해당 이름을 snapshot에 저장한다.
- 연결이 없거나 등록 목록에 없으면 `ceo@exdigm.com` 사용자의 잡코리아 등록 이름을 snapshot에 저장한다.
- CEO 연결도 등록 목록과 일치하지 않으면 임의값을 만들지 않고 큐 생성을 차단한다.
- 프로젝트 화면에서 일반 프로필 누락 오류는 표시하지 않는다.

### 4.3 화면

- 계정 설정에서 `자동게시 담당자 프로필` section을 제거한다.
- 프로젝트 자동 게시 표는 사이트와 전체 활성 사용자 선택만 유지한다.
- `Ready`는 기본값으로 만들지 않는다.
- 게시 전에는 업무 의미가 분명한 `게시 전`을 표시한다.
- 실제 외부 사이트 제약으로 게시할 수 없을 때만 해당 제약을 사이트 행에 표시한다.

## 5. 교체·정리 대상

- 제거: 계정 설정의 사이트별 프로필 6개 폼과 저장 처리
- 제거: `PostingSettingsForm`의 사이트별 프로필 완성 검증
- 제거: `ConsultantPostingProfile.is_complete`와 직책 강제 계약
- 교체: `_posting_profile_snapshot()`의 사이트별 DB 조회 → 선택한 `User` snapshot
- 분리: 잡코리아 헤드헌터 선택 → 사이트 계정 자격
- 보존: `PostingSite.consultant`, `AutoPostingSiteRun.profile_snapshot`, footer 중복 제거, 게시 실행 이력

변경 후 입력·분기·중복 데이터가 줄어들므로 최종 경로 엔트로피는 감소한다.

## 6. 인터랙션 수용 계약

- **Given**: 현재 공고문이 있고 프로젝트 담당자의 이름·이메일이 유효함
- **When**: 사용자가 사이트와 담당자를 선택하고 `게시` 또는 `재게시`를 누름
- **Then**: 같은 화면 입력으로 큐가 생성되고 사이트 상태가 게시 진행 상태로 바뀜
- **성공 상태**: `게시 전 → 대기 → 게시 중 → 완료`
- **실패 상태**: 외부 사이트의 실제 제약과 재시도 가능한 다음 행동을 해당 사이트 행에 표시
- **보존**: 프로젝트 입력, 사이트 선택, 담당자 선택, URL, 스크롤
- **금지**: 자동게시 프로필 설정 이동 요구, 전체 폼 교체, 임의 담당자·이메일 생성

## 7. 검증

1. 모델·폼·workflow 집중 테스트를 먼저 실패시킨 뒤 구현한다.
2. 선택한 담당자의 실제 이름·이메일이 snapshot과 payload에 들어가는지 검증한다.
3. 직책 없이 5개 일반 사이트 payload가 생성되는지 검증한다.
4. 잡코리아 공개 담당자와 사이트 헤드헌터 자격이 분리되는지 검증한다.
5. 기존 snapshot 이력과 footer 중복 제거 회귀를 검증한다.
6. 공용 pytest 잠금 명령으로 관련 테스트와 회귀 테스트를 실행한다.
7. `uv run --locked python manage.py check`를 실행한다.
8. 개발 서버 `go`의 실제 프로젝트 화면에서 클릭 전·처리 중·결과 후를 캡처한다.
9. 6개 사이트를 공식 `manage.py autoposting --site <site> --mode dry` 경로로 검증한다.
10. `code-review-loop`를 finding이 없을 때까지 실행한다.
11. GBrain 정본을 최종 구현과 일치시킨다.

## 8. 제외 범위

- 실제 운영 게시
- 프로젝트 담당자 배정 규칙 변경
- 공고문 생성 프롬프트 변경
- 외부 사이트 로그인 자격증명 변경
- 사이트별 별도 runner 또는 보정 경로 추가

## 9. 승인 후 진행

이 문서 승인 후 구현·검증·리뷰·문서화·커밋까지 같은 범위에서 추가 승인 없이 진행한다. 잡코리아의 권위 있는 게시 자격을 확인할 수 없거나 승인 범위 밖 변경이 필요할 때만 중단한다.
