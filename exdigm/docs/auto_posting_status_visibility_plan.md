# 프로젝트 저장·자동게시 상태 가시성 통합 계획

> 상태: 2026-08-12 저장·자동게시 독립 계약으로 갱신

## 1. 목표

- `저장하기`는 자동게시 이력·상태와 관계없이 프로젝트 값만 저장한다.
- 값이 변경된 뒤 저장되지 않은 채 화면을 떠날 때만 미저장 경고를 표시한다.
- 프로젝트 저장과 자동게시 시작을 독립된 행동으로 유지한다.
- 사용자에게 미게시, 게시 진행, 게시 완료, 게시 실패를 구분해 표시한다.
- 자동게시 실행 중에는 프로젝트 목록 카드의 상태가 완료 또는 실패까지 자동 갱신된다.

## 2. 2026-07-17 당시 확인 상태

- 2026-07-17 `개발팀장` 프로젝트는 저장됐지만 `AutoPostingRun`과 `PostingSite`가 모두 0건이다.
- 따라서 현재 게시 중이 아니며 실제 게시도 시작되지 않았다.
- `저장하기`는 자동게시를 enqueue하지 않지만 성공 후 편집 화면으로 다시 이동한다.
- 실행 이력이 없는 사이트도 `게시 전`으로 표시한다.
- 기존 프로젝트라는 이유만으로 첫 실행 버튼도 `재게시`로 표시한다.
- worker가 상태를 갱신해도 상세 화면은 자동으로 다시 읽지 않는다.

## 3. 최종 경로(SSP)

### 프로젝트 저장

1. 사용자가 `저장하기`를 누른다.
2. 서버가 현재 프로젝트 값과 담당자를 검증한다.
3. 유효하면 프로젝트 값을 저장하고 프로젝트 목록으로 이동한다.
4. 유효하지 않으면 같은 화면에 오류와 입력값을 유지한다.
5. 자동게시 run의 존재·상태·선택 사이트는 저장 판단에 사용하지 않는다.

### 미저장 변경 확인

1. 마지막 저장값과 현재 화면 값을 비교한다.
2. 값이 다르고 아직 저장하지 않은 상태에서 화면을 떠날 때만 경고한다.
3. 값이 같거나 저장이 완료됐으면 경고하지 않는다.
4. 자동게시 상태는 미저장 판단에 사용하지 않는다.

### 게시

1. 프로젝트 생성의 다중 사이트 게시는 저장 후 `enqueue_posting_workflow()`를 호출하고 목록으로 이동한다.
2. 프로젝트 수정의 사이트별 `게시`는 선택한 한 사이트만 접수한다.
3. 수정 화면은 그대로 유지하고 접수한 사이트 행만 `처리 중…`으로 교체한다.
4. 실행 중인 행만 상태 endpoint를 주기적으로 다시 읽는다.
5. `대기 → 진행중 → 성공/실패` 중 terminal 상태가 되면 polling을 멈춘다.

별도 runner, 상태 테이블, 보정 경로는 만들지 않는다.

## 4. 상태 표현 계약

| 저장된 상태 | 사용자 문구 |
|---|---|
| run 없음 | 미게시 |
| dry/test queued/running | 처리 중… |
| dry/test terminal | 미게시 |
| publish queued/running | 처리 중… |
| publish succeeded | 게시 완료 |
| publish failed | 게시 실패 |
| publish partial_failed | 일부 게시 실패 |
| skipped | 미게시 |

- 사이트 행과 프로젝트 카드는 `last_run.run.mode`와 실제 상태를 함께 사용한다.
- 모든 실행 중 상태는 `처리 중…`으로 표시한다.
- dry/test 종료는 실제 `게시 완료`로 표시하지 않고 `미게시`로 표시한다.
- 실패 사이트에는 기존 `last_error`를 유지한다.
- 모든 상태 문구는 한 줄로 표시한다.

## 5. 화면 변경

- 프로젝트 생성·수정의 저장 성공 redirect를 프로젝트 목록으로 통일한다.
- `자동게시 없이 저장` 확인 modal과 확인용 hidden 상태를 제거한다.
- 저장 버튼은 프로젝트 값 저장만 수행한다.
- 미저장 경고는 기존 단일 폼 값 비교 경로만 사용한다.
- 프로젝트 목록 카드에 최신 자동게시 상태를 작은 업무 상태로 표시한다.
- 첫 실행은 `게시 시작`, 실행 이력이 있으면 `재게시`로 표시한다.
- 프로젝트 생성의 다중 사이트 게시만 성공 후 목록으로 이동한다.
- 프로젝트 수정의 사이트별 게시는 같은 화면과 스크롤을 유지한다.
- 실행 중인 프로젝트 카드의 게시 상태 영역만 terminal 상태까지 갱신한다.
- 페이지·카드 전체 polling이나 전체 swap은 하지 않는다.

## 6. 인터랙션 수용 계약(IAC)

### 저장하기

- Given: 프로젝트 입력과 사용자의 저장 권한
- When: `저장하기` 클릭, `action=save` 제출
- Then: 유효한 프로젝트 값을 저장하고 목록으로 이동
- 실패: 같은 편집 화면에 오류와 입력 유지
- 불변조건: 자동게시 run을 생성·취소·변경하지 않음

### 화면 이탈

- Given: 마지막 저장값과 현재 폼 값
- When: 메뉴 이동·브라우저 이탈·히스토리 이동
- Then: 값이 다르고 제출 중이 아닐 때만 미저장 경고 표시
- 불변조건: 자동게시 이력과 상태는 판정에 관여하지 않음

### 게시 시작·재게시

- Given: 현재 공고문, 선택 사이트, 담당자
- When: 프로젝트 생성의 다중 사이트 게시 또는 수정 화면의 사이트별 게시
- Then: 선택한 사이트 run 생성, 생성 화면은 목록 이동, 수정 화면은 해당 행만 갱신
- 상태 전이: 요청 없음 → 대기 → 진행중 → 성공/일부 실패/실패
- 변경 경계: 목록의 프로젝트 상태 또는 수정 화면의 해당 사이트 행만 교체
- 불변조건: 수정 화면의 다른 입력·URL·스크롤·사이트 행 유지

## 7. 교체·정리 대상

- 유지: 저장 성공의 프로젝트 목록 redirect
- 삭제: 저장 확인 modal, 확인 hidden 값, 자동게시 이력 기반 서버·클라이언트 분기
- 유지: 기존 단일 미저장 폼 감시기
- 교체: 상태 없는 fallback `게시 요청 없음` → `미게시`
- 교체: `is_edit` 기준 버튼 이름 → 실제 실행 이력 기준 이름
- 병합: 기존 게시 상태 endpoint → 프로젝트 카드용 작은 상태 partial
- 확장: 기존 프로젝트 카드 데이터에 최신 run 상태만 병합

새 상태 모델이나 별도 실행 경로 없이 기존 장부를 소비하므로 엔트로피 증가는 최소다.

## 8. 검증

1. 자동게시 이력이 없는 생성·수정 저장이 바로 완료되는지 테스트한다.
2. 유효하지 않은 저장은 같은 화면에 오류와 입력을 유지하는지 테스트한다.
3. 저장 화면에 자동게시 확인 modal과 확인 상태가 없는지 테스트한다.
4. 변경 없음·변경 후 취소·변경 후 저장의 미저장 경고를 확인한다.
5. 저장이 AutoPostingRun을 만들거나 변경하지 않는지 테스트한다.
6. run 없음과 dry/test/publish 상태 문구를 테스트한다.
7. 공용 pytest 잠금 명령으로 관련 회귀 테스트를 실행한다.
8. `uv run --locked python manage.py check`와 정적 검사를 실행한다.
9. 실제 개발 URL에서 저장과 미저장 이탈 경고를 확인한다.
10. 외부 실제 게시 없이 dry 경로를 검증한다.
11. `code-review-loop`를 finding이 없을 때까지 실행한다.
12. GBrain에 저장·자동게시 독립 계약을 기록한다.
