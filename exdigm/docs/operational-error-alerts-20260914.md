# 운영 오류·작업 실패 DB 기록

현재는 Exdigm의 오류 hook이 임시 파일에 기록하고, 기존 알림 워커 `deliver_notification_dispatches`가 약 5초마다 파일과 업무 실패 상태를 읽어 `OperationalError`에 저장한다. 워커는 실제 서비스 `Exdigm_exdigm_notification_dispatcher`이며 오류 전용 신규 워커가 아니다. 아래 운영 증거는 이 현재 수집 구조의 이력이다.

## Mailplug 계정 접속 실패 직접 기록 — 2026-09-23 개발 완료·운영 미배포

- 요청 배경: Mailplug에서 회사메일 앱 비밀번호가 바뀐 뒤 Outlook은 새 비밀번호로 복구됐지만, Exdigm의 저장값이 이전 값이면 계정 접속이 반복 실패한다. 2026-09-22 실제 장애에서는 `553 sorry, that password allowed relay (#5.7.5)`가 약 1분마다 발생했으나 `CompanyEmailAccount.last_error`에만 잠시 남고 `OperationalError`에는 기록되지 않았다.
- 확인된 누락 원인: `MailChecker`가 계정별 예외를 잡아 `last_error`만 저장하고 전체 작업은 다른 계정을 계속 처리한 뒤 정상 종료했다. 따라서 미처리 예외·ERROR 로그 수집 경로가 이 실패를 볼 수 없었다.
- 개발 변경: 기존 `_record_account_failure`에서 계정 상태 저장 직후 같은 DB 트랜잭션으로 `record_operation_failure`를 호출한다. 오류 종류는 `mailplug_account_check_failed`, 원본 모델과 계정 번호·계정 주소·실제 오류문구·예외 호출 위치를 남긴다. 앱 비밀번호 값은 전달하거나 기록하지 않는다.
- 중복 계약: 같은 계정의 반복 접속 실패는 5분 구간마다 대표 1건만 만들고, 서로 다른 계정은 각각 기록한다. 한 계정의 실패가 다른 계정 수집을 중단하지 않는 기존 동작과 드라이런 무기록을 유지한다. 오류장부 기록 실패 시 계정 실패 상태만 단독 확정되지 않도록 둘을 함께 되돌린다.
- 개발 커밋: 원격 디버깅 worktree의 detached HEAD `2b28b98b3538b7be63ffee7f8f5a6a580e18cfa9` (`Record Mailplug account check failures`). `origin/main`과 운영 checkout에는 아직 반영하지 않았다.
- 검증: 신규 검사는 구현 전 오류장부 0건으로 실패하고 구현 후 통과했다. Mailplug 관련 11개, 오류장부 70개, Django `check`, Ruff, diff 검사, 코드 지식 색인 검사가 모두 통과했다. 최종 직접 코드 리뷰의 승인 finding과 열린 계약 질문은 없다.
- 운영 경계: 이 변경은 배포 뒤 새로 발생하는 실패부터 기록한다. 2026-09-22의 과거 실패를 소급해 오류장부에 만들지 않았고, 운영 DB·계정 비밀번호·메일 데이터·일반 알림·Hermes·배포 인프라는 변경하지 않았다. 운영 반영은 별도 배포 승인 후 공식 `scripts/deploy/deploy.sh prod` 경로로 진행한다.

### 변경안과 기준선 잠금

- 원하는 결과: 운영 Python 오류와 작업 기록의 확정 실패를 `projects.OperationalError`(DB `projects_operationalerror`)에 남긴다. 오류 기록으로 웹·Telegram·메일 배달 요청을 만들지 않는다.
- 기록: 발생 시각, 간단한 제목, 쉬운 설명, 발생 위치, 오류 종류·원문, 호출 경로, 관련 작업을 찾을 최소 문맥. 확인하지 않은 원인은 단정하지 않는다.
- 감지 순서: 기존 운영 로그·미처리 예외 기록 또는 기존 업무의 확정 실패 → 기존 수집 작업자 → 오류 기록 테이블. 수집과 기록은 Hermes 활성 여부나 직원 profile에 의존하지 않는다.
- 재사용: 기존 로컬 오류 감지, 확정 실패 조회, 중복 식별, 기존 배달 작업자의 수집 주기. 업무를 방해하지 않도록 원래 로그·예외 처리와 기록 실패 대응을 유지한다.
- 추가: Django 오류 기록 모델·마이그레이션 하나와 기록 연결. 기존 공용 ORM 읽기에서 관리자 에이전트가 조회할 수 있도록 연결하고, 별도 API를 만들지 않는다.
- 제거: 이번 운영 오류의 Hermes 전송 처리자와 등록. 기존 직원 봇·인증·기억·세션·네트워크 및 일반 업무 알림은 변경하지 않는다.
- 최소 구현 게이트: 감지·수집·조회는 2단계에서 재사용한다. 기록 그릇은 4단계 Django 모델에서 멈춘다. `class .*Log|Error|Event|Notification` 검색에서 `ExtractionLog`는 후보자 이력이고 `Notification`은 업무 알림이라 전체 운영 오류 기록 책임과 맞지 않았다. 표준 라이브러리의 별도 DB를 만들지 않는다.
- 변경 범위: 운영 오류 감지 모듈, 기존 오류 수집 모듈의 core 이동, projects 모델·앱 등록·마이그레이션, 운영 설정, 기존 수집 호출자, 공용 ORM 읽기의 새 오류 모델 범위, 직접 관련 검사·코드 카탈로그.
- 보호: 기존 사용자 수정 없음; 일반 알림·직원 lifecycle·Hermes 선택형 비활성 웹 시작·업무 데이터·기존 보호 계약은 보존한다. 정상 취소·진행 중·재시도 중 상태를 새 오류로 만들지 않는다.
- 검증: 기존 오류/알림/ORM 기준선 → 오류 DB 기록과 전송 요청 0건 → 상세 설명·작업 번호·코드 위치 → bulk update·일부 실패·중복·정상 처리 → Hermes 비활성 시작 → 공용 ORM 관리자 조회 → check·보호 contracts·직접 코드 리뷰.
- 이전 Telegram 인증·재전송 검사는 새 DB 전용 계약으로 의도적으로 바뀐다. 감지·중복·일반 알림·정상 상태·비밀값 보호 검사는 삭제하거나 완화하지 않는다.

- 코드 수정 전 공식 격리 검사: 기존 오류·알림·runtime·provisioning·선택형 경계 109개 통과.

- 쉬운 설명은 작업명·실패 단계·실제 오류·관련 기록·조사 시작점을 구분한다. 미확인 근본 원인을 자동으로 만들어 쓰지 않는다. 추가 언어모델 호출 없이 확인된 업무명과 오류 정보를 전달한다.

## 공식 경로와 변경 위치

`운영 오류 로그 또는 확정된 작업 실패 → 오류 신호 수집 → 기존 Notification/NotificationDispatch에 저장 → 기존 배달 작업자 → 해당 profile의 HMAC webhook → 지정 Telegram 봇 → 기존 개인 대화방`

- 오류 로그 수집기는 업무 처리를 막지 않도록 짧은 로컬 기록만 한다.
- 로컬 기록은 이미 앱·운영 작업자가 사용하는 runtime 경계 안에 둔다.
- 배달 작업자가 이 기록과 작업의 실패 상태를 읽고 알림을 확정한다.
- 실패 상태는 실제 저장 경로를 조사해 읽는다. save signal에만 의존하지 않는다.
- 활성화 기준 시각과 로컬 기록의 처리 위치를 보존한다.
- 작업 실패는 조회 시각을 앞으로 넘기지 않고, 동일 신호의 알림 기본키가 이미 존재하는지 대조한다.
- 먼저 발생했지만 늦게 저장된 실패도 잡고, 재시작 뒤 같은 실패를 다시 알리지 않는다.
- 기존 알림의 UUID 기본키·채널별 유일성 계약을 사용해 동일 신호의 중복을 차단한다.
- Telegram 전송 처리자는 기존 채널 확장 지점에 연결한다.
- 이 전송 처리자는 이번 운영 오류 알림만 처리한다. 일반 직원 알림을 모두 Telegram으로 바꾸지 않는다.
- 필요 변경 위치는 운영 settings, 기존 배달 명령, Hermes 앱의 채널 등록, 최소 수집·전송 모듈과 관련 테스트다.
- 공유 runtime의 경로·권한과 host/container 실행 사용자를 잠근 뒤 새 기록 파일을 만든다.
- 새 수집·전송 모듈의 정확한 위치는 구현 전 SSP 기록에서 현재 호출 관계와 함께 확정한다.

## 메시지와 보안

- 알림에는 운영 구분, 발생 시각, 업무 종류, 실패 코드 또는 안전한 설명, 해당 기록을 찾을 식별자를 담는다.
- 이력서·메일·요청의 원문과 입력값, 로그 인자, 비밀값, 전체 traceback은 전달하지 않는다.
- 원래 자세한 오류 기록은 기존 서버의 기록 경로에 남긴다.
- 로컬 수집 파일과 처리 위치 파일에는 필요한 최소 정보만 둔다.
- webhook 본문은 UTF-8 JSON으로 보내고 기존 HMAC V2 계약을 따른다.
- `delivered` 응답만 신규 전송 성공으로 인정한다. 이미 DB에 확인 완료가 저장된 경우만 그 확인을 재사용한다.
- 현재 Hermes는 전달 전에 요청 번호를 기억한다. 전달 실패 후의 `duplicate`는 전달 증거가 아니다.
- 요청 제한(429)·연결 거절·DNS 실패처럼 전달 전 실패가 확실한 경우만 대기 후 재시도한다.
- 재시도는 총 8회까지다. 대기 시간은 5초부터 늘고 최대 300초다. 한도를 넘으면 실패를 명시한다.
- 시간 초과·확인 없는 중복 응답·5xx는 `delivery_outcome_unknown`으로 보존한다. 성공으로 기록하거나 자동으로 다시 보내지 않는다.
- 5xx는 Telegram 쪽 시간 초과를 감쌀 수 있다. 주인님의 대화방에 이미 도착했을 가능성을 배제할 수 없어 새 요청 번호로 재전송하지 않는다.

## 구현 결과와 잠근 경로

- 코드 수정은 원격 디버깅 worktree에서만 했다. 운영 체크아웃은 시작 상태를 유지한다.
- `main/settings/deploy.py`의 운영 설정 → `common/operational_errors.py`의 로그·미처리 예외 수집 → 기존 runtime의 최소 JSONL 기록으로 연결한다.
- `hermes_integration/apps.py`의 준비 단계 → 기존 `notification_extensions.py`의 수집기·채널 등록 → 기존 배달 명령으로 연결한다.
- 배달 명령 → `hermes_integration/operational_alerts.py`의 기록·확정 실패 조회 → 기존 알림·Telegram 배달 요청 저장으로 연결한다.
- 배달 명령 → `hermes_integration/notification_delivery.py` → 기존 관리형 Hermes의 인증된 webhook → 기존 Telegram 개인 대화방으로 연결한다.
- 핵심 웹 코드에서는 선택형 Hermes 구현을 직접 import하지 않는다. Hermes 비활성 상태의 웹 시작·알림 경로를 보존한다.
- 정상 직원 알림에 Telegram 요청을 추가하는 creator는 등록하지 않는다. 이번 오류 알림만 Telegram 요청을 만든다.
- 같은 위치·예외 종류의 오류 로그와 같은 코드의 파일 실패는 5분 단위로 묶는다.
- 상위 자동 게시 실패와 실패한 사이트 기록이 동시에 있으면 사이트 기록을 우선한다.
- 한 번의 배달 묶음에서 기존 웹 알림을 먼저 처리하고, Telegram 네트워크 전송은 최대 한 건이다.
- 조작하지 않은 정상 취소·진행 중 검색·재시도 가능한 파일 실패·과거 실패는 발송 대상이 아니다.
- 신호 기본키는 Python과 PostgreSQL에서 같은 결정적 UUID로 계산한다. PostgreSQL의 기존 MD5 함수는 식별자 계산에만 사용한다. 인증은 기존 HMAC-SHA256을 유지한다.
- 작업 실패 조회는 이미 있는 알림 기본키와 대조한다. 처리 시각을 건너뛰는 방식이 아니므로 먼저 발생했지만 늦게 저장된 실패를 놓치지 않는다.
- 알림 화면의 무시 동작은 기존대로 읽음 처리만 한다. 확인 기록이 없어져 같은 실패를 다시 만드는 동작으로 바꾸지 않는다.
- 로그 처리 위치는 알림·배달 요청 저장 뒤 원자적으로 교체한다. 처리 위치 저장이 실패해도 같은 신호가 중복 생성되지 않는다.
- 완성되지 않은 마지막 로그 줄은 다음 조회까지 기다린다. 손상된 완성 줄은 원본을 보존하고 안전한 손상 알림을 만든 뒤 다른 신호를 처리한다.

### 파일 경로·권한과 최소 구현

- 기준 경로는 기존 host `runtime`과 컨테이너 `/app/runtime`의 공유 mount다.
- host 작업자는 chaconne(uid/gid 1001), 기존 앱·배달 컨테이너는 root다.
- `/home`은 root 755, `/home/chaconne`은 chaconne 750, 운영 폴더·runtime은 chaconne 775다.
- 프로세스별 기록·처리 위치는 600, 공용 활성화 시각은 644다. host 기록을 root 배달 작업자가 읽고 host도 활성화 시각을 읽을 수 있다.
- 활성화 시각은 완성된 임시 파일을 원자적으로 공개한다. 여러 프로세스가 동시에 시작해도 빈 시각 파일을 읽지 않는다.
- 최소 구현 게이트: 알림 저장·채널·등록·배달 작업자는 2단계에서 재사용했다.
- 확인 근거는 `NotificationDispatch`, `register_notification_dispatch_handler`, `notification_dispatch_handler`, `send_notification`, `LOGGING`과 관련 파일 검색이다.
- 누락된 로그 수집·인증 HTTP 연결은 3단계의 `logging`, `threading`, `urllib`, `hmac`, `hashlib`, `json`, `tempfile`로 구현했다.
- DB 조회·기본키 대조는 설치된 Django의 `Q`, `Exists`, `Cast`, `Concat`, `MD5`와 PostgreSQL 기본 함수로 표현했다. 새 DB 확장·의존성·서버·작업자는 없다.
- 운영 SELECT 전용 경로에서 새 파일 실패 조회의 EXPLAIN을 확인했다. 기존 `file_statuses_retryable_c502799a`와 `projects_notification_pkey` 인덱스를 사용한다.
- 두 파일 조회의 추정 비용은 329.34·334.96, 추정 결과는 각 1건이다. EXPLAIN은 실행 시간 측정이나 실전송 증거가 아니다.

- 선택형 연결 결함: 새 배달 명령이 Hermes를 직접 import해서 Hermes 비활성 환경의 웹 URL 로딩을 실패시켰다.

- 실제 운영 Telegram 메시지를 보내지 않았다. 실제 전달 완료는 아직 검증되지 않았다.

## 최종 실제 통신 검사에서 추가 확인한 차단점

- 개발 검사·첫 코드 리뷰·커밋 뒤, 실제 운영 알림 작업자에서 대상의 `/health`를 GET했다. Telegram 메시지는 보내지 않았다.
- 알림 작업자의 실제 Python은 `/usr/local/bin/python`이다. 최초에 추측한 `/app/.venv/bin/python`은 없었고, 실행 경로를 조회해 수정했다.
- 관리형 Docker 컨테이너 이름은 65자다. Python의 DNS 주소 변환은 한 칸의 최대 길이 63자를 넘겨 `UnicodeEncodeError: label too long`을 냈다.
- 실패 원인은 전송 코드가 Docker 자원 이름을 그대로 DNS 주소로 사용한 것이다. 요청은 전송 전에 거절됐으며 HMAC 인증 실패나 Telegram 메시지 거절로 확인된 것이 아니다.
- 현재 target과 알림 작업자는 같은 `Exdigm_net`에 있다. target의 짧은 컨테이너 번호 DNS로 GET하면 `status=ok`다.
- 네트워크 격리나 봇 정지는 이 관측의 원인이 아니다. 봇 자체·개인 대화방·같은 네트워크의 실제 접근은 정상이다.
- 짧은 컨테이너 번호는 재생성 시 바뀐다. 숫자나 현재 IP를 코드에 고정하는 우회는 적용하지 않았다.
- 새 리뷰 결함: 입력 profile → Docker 이름 helper(65자) → 어댑터 HTTP hostname → IDNA 길이 거절 → 모든 실제 메시지 전달 실패.
- 리뷰 계약 4·5·6번 위반이며 원인이 새 어댑터의 주소 선택 줄에 있다. 직접 호출자에서 재현돼 변경 경계 안의 실제 결함으로 승인했다.
- 기존 개발 73개·보호 194개 통과는 그대로지만, 가짜 HTTP 응답만으로 실제 주소 계약을 검증하지 못했다. 앞선 ‘최종 finding 없음’은 이 통신 검사 전의 결과다.

### 추가 승인된 범위

- 원하는 결과: 지정 봇이 재시작·재생성돼도 사용할 짧은 고정 전송 주소를 마련한다.
- 추가 코드 범위: 전송 어댑터의 DNS 주소 선택과, 필요할 때 기존 생성·배포 경로의 짧은 별칭 유지 책임만 수정한다.
- 추가 운영 범위: 지정 봇의 네트워크 연결에 짧은 고정 별칭을 추가한다. 연결 갱신 중 해당 봇의 통신이 잠깐 끊길 수 있다.
- 기존 IP·network·실행 프로세스·비밀값·모델·기억·세션·MCP 설정은 보존한다. 전체 fleet 재생성과 세션 초기화는 여전히 제외한다.
- 검증: 실제 알림 작업자에서 고정 주소 GET, DNS 길이 계약, 재생성 때 주소 유지 책임, 같은 핵심·보호·기준선 검사, 수정된 diff 리뷰.
- 승인된 수정 커밋을 보고한 뒤 공식 운영 배포와 정상 수집 경로의 '테스트' 신호 1회로 실제 전달 확인을 수행한다.
- 아직 실행하지 않은 것: 네트워크 별칭 추가·연결 갱신·봇 재생성·코드 push·운영 배포·실제 Telegram 발송.

### 추가 변경 기준선 잠금

- 승인 원천: 위 추가 범위 요청에 대한 주인님의 `승인` 응답.
- 재확인한 시작 상태: debug detached clean `53b5d2e5273624c772fd802539a40f788cd0bca4`, 운영 clean main `16a6c115b8ff6b9abde36127ddb0b4e12c968a8f`.
- 지정 컨테이너와 network는 이전 기록과 일치한다. 실행 PID·시작 시각은 그대로이며 현재 별칭이 없다.
- 추가 코드 경로: 기존 runtime helper의 짧은 고정 주소 → 기존 DockerRuntime의 `--network-alias` → 전송 어댑터가 동일 helper 사용.
- Docker 자원 이름과 DNS 주소를 분리한다. 기존 lifecycle·profile 이름·컨테이너 이름은 바꾸지 않는다.
- 최소 구현 게이트: 생성·전송 책임은 2단계 재사용, 주소 계산은 3단계 표준 hashlib. 실제 검색에서 기존 별칭/helper가 없음을 확인했다. 새 서비스·API·DB·의존성은 없다.
- 수정 전 공식 핵심 검사에 provisioning을 포함한 7개 파일 101개가 통과했다.
- 추가 성공조건: 유효한 짧은 IDNA 주소, 생성·재생성에서 같은 별칭, 실제 dispatcher의 별칭 GET 성공, 지정 봇만 연결 갱신, 같은 기존 보호 검사 결과, 배포 후 테스트 신호 1건의 전달 확인.
- 일반 Django 배포는 기존대로 Hermes 인프라·fleet을 재생성하지 않는다. 현재 봇의 별칭은 승인된 네트워크 연결 갱신으로 추가한다. 향후 공식 Hermes 배포는 새 인프라 코드를 먼저 설치한 뒤 그 코드로 fleet을 만들므로 생성 시에도 별칭이 유지된다.
- 현재 프로비저닝 서비스·다른 봇은 재시작하지 않는다. 현재 프로비저닝 이미지 자체를 이번 배포로 교체했다고 보고하지 않는다.
