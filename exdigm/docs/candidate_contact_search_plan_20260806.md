# 후보자 이메일·전화번호 검색 통합 계획

> 상태: 2026-08-06 구현·브라우저 검증·코드 리뷰 완료

## 1. 목표

- 후보자 조회의 기존 음성·텍스트 검색창에서 이메일로 후보자를 찾는다.
- 같은 검색창에서 전화번호 표기 형식과 관계없이 후보자를 찾는다.
- 기존 이름·회사·직군 검색과 검색 결과 표시 방식은 유지한다.

## 2. 확인된 변경 전 상태

- 공식 검색 경로는 `자연어 입력 → 검색 조건 해석 → 원본 후보자 필드 ORM 조회 → 결과 표시` 하나다.
- 허용된 검색축에는 이메일과 전화번호가 없다.
- 전체 필드 검색축에도 이메일과 전화번호가 포함되지 않는다.
- 후보자 전화번호는 저장할 때 숫자 중심의 `phone_normalized` 값이 함께 유지된다.
- 검색창 안내 문구는 이름·회사·직군만 검색 예시로 보여준다.

## 3. 최소 구현 게이트

`최소 구현 게이트: 2단계에서 멈춤 — candidates.models.Candidate의 email·phone·phone_normalized와 candidates.services.candidate_identity.normalize_phone_for_matching이 이미 있어 이를 재사용하며, 새 모델·필드·의존성·검색 경로를 만들지 않는다.`

확인 근거:

- 검색어: `email`, `phone`, `phone_normalized`, `normalize_phone_for_matching`
- 확인 파일: `candidates/models.py`, `candidates/services/candidate_identity.py`, `candidates/services/search.py`
- 패키지 확인: `pyproject.toml`, `uv.lock`; 새 의존성은 필요하지 않다.

## 4. 최종 경로(SSP)

1. 사용자가 후보자 조회의 기존 검색창에 이름·이메일·전화번호 또는 자연어 조건을 입력한다.
2. 기존 검색 조건 해석 호출이 이메일은 `email`, 전화번호는 `phone` 검색축으로 변환한다.
3. 이메일 검색축은 후보자 원본 `email` 필드에 적용한다.
4. 전화번호 검색축은 기존 정규화 함수를 거쳐 `phone_normalized`에 적용한다.
5. 기존 후보자 공개 범위, 정렬, 건수 계산, 20명 우선 표시를 그대로 적용한다.
6. 기존 검색 결과 영역만 로딩 상태를 거쳐 교체한다.

별도 검색 endpoint, 별도 연락처 검색 form, 직접 파싱 우회 분기, 새 DB 필드는 만들지 않는다.

## 5. 병합 위치와 정리 대상

- 병합 위치: `candidates/services/search.py`의 기존 허용 검색축, 검색축-원본 필드 대응, group ORM 조건 생성 단계
- 교체 대상: 검색창 placeholder의 기존 예시 문구
- 테스트 위치: `tests/test_search_service.py`의 검색 계약·원본 필드 조회 테스트, 기존 프런트 템플릿 테스트
- 문서 위치: 이 계획과 GBrain의 후보자 검색 단일 경로 문서

기존 검색 경로 안에서 축 두 개만 추가하므로 실행 경로 수는 늘지 않는다.

## 6. 인터랙션 수용 계약(IAC)

| 항목 | 계약 |
|---|---|
| 사용자 의도 | 기존 후보자 검색창에 이메일 또는 전화번호를 입력해 해당 후보자를 조회한다. |
| Given | 로그인한 후보자 조회 권한, 저장된 후보자 이메일 또는 전화번호, 유효한 검색 입력 |
| 입력 / SSOT | `#sb-input`의 `message`; 후보자 연락처의 SSOT는 `Candidate.email`, `Candidate.phone_normalized` |
| When | 전송 버튼·Enter·음성 전사 → `POST /candidates/search/` → `search_chat()` → `parse_and_search()` → `build_search_queryset()` |
| Then | 실제 일치 후보자 수를 대화창에 표시하고 `#search-area`에 기존 후보자 목록을 렌더링한다. |
| 상태 전이 | 준비 → 검색 중 → 결과 표시, 또는 준비 → 검색 중 → 기존 오류 문구 표시 |
| 변경 경계 | 검색 중인 control과 `#search-area`만 바뀐다. 검색창 DOM, URL, 스크롤 소유자, 기존 검색 세션 계약을 유지한다. |
| 렌더링 | 기존 JSON 응답과 `htmx.ajax(... target: '#search-area', swap: 'innerHTML')`를 유지한다. |
| 시각 | 기존 form-control과 검색 버튼을 유지하고 placeholder에 이메일·전화번호를 추가한다. |
| 불변조건 | 권한, 후보자 가시성, 결과 정렬, 페이지당 우선 표시 수, 음성·텍스트 단일 경로를 유지한다. |
| 실패 | 기존 대화창 오류와 재입력 경로를 유지하며 검색 결과를 성공처럼 바꾸지 않는다. |

## 7. UX 적용

- 목표 행동: 검색창 한 곳에서 알고 있는 후보자 식별값으로 바로 조회한다.
- 마찰 감소: 별도 연락처 필터를 추가하지 않고 익숙한 검색 입력을 유지한다.
- 유연한 입력: 전화번호의 하이픈·공백·국가번호 표기 차이는 기존 정규화 값으로 흡수한다.
- 접근성: 기존 텍스트 input, 키보드 Enter 전송, 검색·로딩·오류의 보이는 상태를 유지한다.
- 개인정보: 검색 결과에 연락처를 새로 노출하지 않고 기존 권한과 후보자 카드 표시를 유지한다.

## 8. 검증

1. 이메일 대소문자 차이에도 같은 후보자를 찾는 검색 서비스 테스트를 추가한다.
2. 전화번호의 하이픈·공백·`+82` 표기 차이에도 같은 후보자를 찾는 검색 서비스 테스트를 추가한다.
3. 이메일과 전화번호 축이 검색 조건 정규화에서 보존되는지 테스트한다.
4. 기존 이름·회사·직군 검색 테스트를 함께 실행한다.
5. 검색창 안내 문구에 이메일·전화번호가 보이는지 테스트한다.
6. 공용 pytest 잠금 명령으로 관련 테스트를 실행한다.
7. `uv run --locked python manage.py check`와 관련 정적 검사를 실행한다.
8. `uv run --locked python -m tools.code_knowledge catalog_update`를 실행한다.
9. 실제 개발 URL에서 이메일과 전화번호를 각각 입력해 검색 중·성공 결과와 console/network를 확인한다.
10. `code-review-loop`를 finding이 없을 때까지 실행한다.
11. 후보자 검색 단일 경로의 지원 검색축을 GBrain에 기록한다.

## 9. 제외 범위

- 후보자 연락처 등록·수정·삭제
- 후보자 카드나 상세 화면에 연락처 추가 노출
- 권한과 가시성 정책 변경
- 연락처 존재 여부만으로 후보자 수를 세는 별도 필터
- 새 DB index, migration, 외부 검색 서비스, 새 의존성
- 운영 배포

## 10. 승인 후 진행

- 승인 후 구현·집중 테스트·개발 화면 검증·코드 리뷰·GBrain·목차 갱신·커밋까지 같은 범위에서 추가 승인 없이 진행한다.
- 목표나 부작용 범위가 달라질 때만 다시 승인받는다.

## 11. 구현 결과

- 기존 후보자 검색축에 `email`과 `phone`을 추가했다.
- 이메일은 대소문자 차이와 관계없이 원본 후보자 이메일에서 검색한다.
- 전화번호는 저장 때 쓰는 정규화 함수를 재사용해 하이픈·공백·`+82` 표기 차이를 흡수한다.
- 검색창의 한국어·영어 안내 문구에 이메일과 전화번호를 추가했다.
- 검색 input에 기존 번역을 사용한 접근성 이름을 추가했다.
- 후보자 검색 서비스·뷰·UI 관련 테스트 80건이 통과했다.
- Django system check, Ruff, diff check가 통과했다.
- 코드 목차 갱신 결과 깨진 참조 없이 최신 상태였다.
- 실제 개발 URL에서 이메일과 `+82` 전화번호가 각각 같은 후보자 1명으로 조회됐다.
- 검색 중·성공·네트워크 실패 화면과 결과 영역 변경 경계를 확인했다.
- 마지막 `code-review-loop`에서 승인 finding과 열린 계약 질문이 없었다.
