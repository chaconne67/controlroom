# 평판 검토 LLM 문맥 판정 통합 계획

## 1. 목표

- 파일명과 이력서 본문의 문맥·의미는 기존 구조화 추출 LLM이 판단한다.
- 스크립트는 LLM 호출, 출력 계약, 근거 원문 존재만 기계적으로 검사한다.
- LLM 결과는 `평판 검토 신호`이며 후보자의 평판을 확정하지 않는다.
- 사람의 수동 `블랙리스트` 등록과 해제는 현재 계약을 유지한다.

## 2. 확정 원인

- 현재 평판 서비스가 파일명과 추출 본문을 정규식 키워드로 검색한다.
- `블랙리스트` 같은 단어가 후보자 평가인지 업무 경력인지 해석하지 않는다.
- 키워드 탐지 결과가 후보자 카드의 `평판 주의`와 프로젝트 진행 확인으로 직접 연결된다.

## 3. 현재 최종 경로

1. 실시간·배치 유입이 이력서 원문과 파일명을 기존 Step 1 구조화 추출 LLM에 전달한다.
2. LLM 출력이 `FileData.structured_json`, `Resume.structured_json`, `Candidate.raw_extracted_json`과 현재 이력서 참조에 저장된다.
3. 후보자 카드·프로젝트 바구니가 현재 대표 파일의 파일명과 추출 본문을 다시 읽는다.
4. 평판 서비스가 정규식 키워드를 찾는다.
5. 키워드가 하나라도 있으면 `평판 주의`를 표시하고 진행 후보 승격 시 확인을 요구한다.

## 4. 변경 후 최종 경로

1. 기존 Step 1 구조화 추출 LLM이 파일명과 본문을 함께 읽는다.
2. 같은 LLM 응답에 `reputation_review`를 필수로 반환한다.
3. 스크립트가 상태 enum, 근거 배열, 원문 인용 존재를 검사한다.
4. 계약 위반이면 실제 오류를 피드백해 한 번만 재요청한다.
5. 재요청도 실패하면 구조화 추출 실패로 중단하고 불완전한 결과를 저장하지 않는다.
6. 정상 결과는 기존 구조화 JSON과 후보자 현재 프로필에 함께 저장한다.
7. 후보자·프로젝트 화면은 저장된 LLM 결과만 읽는다.
8. `needs_human_review`와 원문 근거가 있을 때만 `평판 검토`를 표시한다.
9. 사용자가 근거를 읽고 진행 여부 또는 수동 블랙리스트 등록을 결정한다.

## 5. LLM·스크립트·사람 역할

| 주체 | 책임 |
|---|---|
| LLM | 후보자에 대한 부정적 평가·추천 배제 메모인지, 업무 경험·일반 문서 문맥인지 의미 분류 |
| 스크립트 | 입력 전달, 출력 형식 검사, 인용문이 파일명·본문에 실제 존재하는지 검사, 저장·화면 전달 |
| 사람 | `평판 검토` 근거 확인, 진행 여부 판단, 실제 블랙리스트 등록·해제 |

## 6. 출력 계약

```json
{
  "reputation_review": {
    "status": "clear | needs_human_review",
    "evidence": [
      {
        "source": "file_name | resume_text",
        "quote": "원문 그대로의 짧은 인용",
        "reason": "후보자 평가 또는 추천 배제 문맥으로 분류한 이유"
      }
    ]
  }
}
```

- `clear`이면 `evidence`는 빈 배열이다.
- `needs_human_review`이면 근거가 1개 이상이어야 한다.
- `quote`는 지정한 원천에 실제로 존재해야 한다.
- 업무 성과, 기술, 제재 대상 명단, 거래 통제 등 후보자 평가가 아닌 문맥은 `clear`다.
- 불확실한 후보자 평가 메모는 확정하지 않고 `needs_human_review`로 사람에게 넘긴다.

## 7. 병합 위치

- 추출 프롬프트·스키마: 기존 Step 1 단일 LLM 응답
- 계약 검사: 기존 Step 1 검증과 실시간·배치 1회 피드백 재요청
- 저장: 기존 구조화 JSON과 후보자 현재 프로필 transaction
- 소비: 기존 평판 서비스의 단일 함수
- 화면: 후보자 카드, 평판 근거 모달, 프로젝트 바구니, 진행 후보 승격 확인

## 8. 대체·정리 대상

- 파일명·본문 키워드 정규식 목록 제거
- 키워드 주변 문자열을 잘라 판정 근거로 만드는 로직 제거
- `평판 주의` 자동 확정형 문구를 `평판 검토`로 변경
- 기존 키워드 전용 테스트를 LLM 출력 계약·저장 결과·화면 소비 테스트로 교체
- 새 LLM 호출, 새 DB 필드, 별도 사후 보정 단계는 추가하지 않는다.

변경 후 공식 경로는 기존 추출 LLM 1회와 기존 구조화 JSON 1개를 유지한다. 정규식 판정 경로가 제거되므로 전체 엔트로피는 감소한다.

## 9. 기존 데이터 영향

- `reputation_review`가 없는 기존 구조화 JSON은 `평판 검토 미실행`으로 취급한다.
- 기존 키워드만으로 붙던 자동 `평판 주의`는 표시하지 않는다.
- 기존 수동 블랙리스트 상태와 사유는 변경하지 않는다.
- 기존 데이터를 일괄 재추출하거나 운영 DB를 백필하지 않는다.

## 10. 화면·상호작용 계약

- 사용자 의도: 자동 판정을 믿는 것이 아니라 원문 근거를 확인하고 직접 결정한다.
- 입력 SSOT: `Candidate.raw_extracted_json.reputation_review`
- 표시:
  - 수동 확정 상태는 `블랙리스트`
  - LLM 검토 신호는 `평판 검토`
  - 신호가 없거나 과거 미실행 데이터면 배지 없음
- 모달: 원문 인용과 LLM의 문맥 분류 이유를 함께 표시한다.
- 진행 후보 승격: `평판 검토` 또는 수동 블랙리스트가 있으면 근거 확인 후 명시적으로 진행한다.
- 변경 경계: 기존 HTMX target, modal container, URL, 스크롤, 입력 보존 계약을 유지한다.
- 실패: 추출 계약 실패를 정상 또는 `clear`로 보정하지 않고 기존 추출 실패 경로에 남긴다.

## 11. 검증

1. 프롬프트·출력 계약 테스트
   - 파일명과 본문이 모두 LLM 입력에 포함됨
   - `reputation_review` 필수 스키마와 의미 경계가 포함됨
2. 기계 검증 테스트
   - 정상 `clear`
   - 정상 `needs_human_review`
   - 근거 없는 검토 신호
   - 원문에 없는 인용
   - 잘못된 상태·출처
   - 첫 실패 후 정상 재요청
   - 두 번째 실패 후 명시적 중단
3. 소비·화면 테스트
   - 업무상 블랙리스트 문맥은 배지 없음
   - 후보자 평가 메모는 `평판 검토`
   - 과거 미실행 데이터는 배지 없음
   - 수동 블랙리스트는 계속 우선 표시
   - 프로젝트 진행 확인은 LLM 검토 신호와 수동 블랙리스트에만 적용
4. 같은 최종 경로 실행
   - 실제 구조화 추출 LLM에 일반화된 업무 문맥과 후보자 평가 문맥을 각각 입력
   - 음성 사례는 `clear`, 양성 사례는 근거 포함 `needs_human_review`
5. 집중 테스트
   - 공용 pytest 잠금으로 평판·추출·프로젝트 관련 테스트 실행
6. UI 검수
   - 개발 URL의 후보자 카드, 근거 모달, 프로젝트 바구니에서 클릭 전·모달·진행 확인 상태 캡처
   - 새 콘솔·네트워크 오류와 HTMX 범위 이탈 없음
7. 완료 게이트
   - 코드 목차 갱신
   - `code-review-loop` 수행
   - 사건 GBrain 페이지의 수정·재발 판정 갱신

## 12. 재발 판정 기준

- 닫힘 조건:
  - 키워드 정규식 판정 경로가 제거됨
  - 문맥 판정이 기존 추출 LLM까지 추적됨
  - 근거 없는 LLM 결과가 저장되지 않음
  - 업무 문맥과 후보자 평가 문맥의 실제 LLM 대조가 통과함
- 열림 조건:
  - 어느 화면이나 진행 경로가 원문 키워드를 직접 다시 판정함
  - LLM 계약 누락을 `clear`로 보정함
  - 사람의 확정 없이 자동 `평판 주의`로 표현함
