# 프로젝트 적합 후보 외부 검색 UX 개선 제안

작성일: 2026-09-08. 사용자 승인 후 구현·검증 중입니다. 아래 제안 당시의 진단과 현재 실행 결과를 구분합니다.

## 목표

사용자가 검색이 끝나기 전부터 찾은 후보를 검토하고, 필요한 사이트만 재시도하며, 검색을 중단하거나 조건을 바꿔도 이전 결과를 잃지 않게 합니다.

## 확인된 사실

- 제공 화면과 같은 검색 세션 `04080a9c-4a40-4ce8-a800-cf109d05ea19`: 2026-09-07 22:21:40~22:32:59 KST, 약 11분 19초, 총 196건.
- BusinessPeople 50, 인크루트 59, 잡코리아 58, 링크드인 29. 사람인 실패.
- 링크드인은 본인 계정 auth_required, CEO 계정 ok. 한 계정이 성공하면 사이트 전체는 ok라 현재 경고에서 개인 인증 실패가 잘 드러나지 않습니다.
- 사람인은 검색 입력이 존재하지만 `div#dimmed`가 클릭을 가로막아 60초 제한에 도달했습니다. 해당 덮개의 소유 팝업은 아직 확인하지 못했습니다. 로그인 실패가 현재 사건의 확정 원인은 아닙니다.
- 사람인의 세션 만료 자동 로그인·2FA 복구는 이미 구현되어 있습니다. 입력을 찾지 못한 경우에 복구하지만, 입력이 있으면서 가려진 경우는 그 분기로 들어가지 않습니다.
- 후보검색은 사이트를 순서대로 실행합니다. 진행 콜백은 숫자를 저장하지만 최종 후보 데이터는 전체 실행 반환 후 저장합니다. 완료된 사이트 후보를 즉시 검토하려면 화면뿐 아니라 결과 저장 시점도 바꿔야 합니다.
- 현재 목록은 20건씩 추가 조회합니다. ‘전체 196명 · 현재 80명’은 196명을 동시에 렌더한다는 뜻이 아닙니다. 의미 불분명한 숫자와 긴 혼합 목록이 검토 부담을 만듭니다.
- 재검색 중 기존 행과 스크롤 보존은 이미 있습니다. 외부 재검색은 미저장 결과에 저장/버림 선택을 요구합니다. 기존 저장 모델을 활용하는 방향이 우선입니다.
- Gemini 키는 운영 `.env`에 있으며 개발 integrations에는 없습니다. 위치만 로컬 DEVELOPMENT-ACCESS.md에 기록했습니다.

## 권장 화면

기존 프로젝트 작업공간 모달을 유지합니다. 초기 입력은 음성·텍스트를 유지하고 결과가 생기면 조건 영역을 축소해 결과에 대부분의 폭을 줍니다. 조건은 상단 요약과 ‘조건 변경’으로 접근하고, 대화 이력은 펼쳐서 봅니다.

```text
적합 후보 찾기                       검색 기록     검색 중지
화장품·뷰티 영업 / 경력 8년 이상         조건 변경

BusinessPeople 50 | 인크루트 59 | 잡코리아 58 | LinkedIn 검색 중 | 사람인 확인 필요

선택한 사이트의 결과 · 표시 1–20 / 수집 50건
이름 / 최근 직무·회사 / 경력·지역 / 조건과 맞는 근거 / 상세 보기
...
이전                         1 / 3                         다음
```

숫자는 관측한 사이트별 집계이며 예시의 검색 진행 상태는 제안 화면 표현입니다. 서로 다른 사이트의 동명이인을 자동으로 합치지 않습니다. ‘196명’이 검증된 고유 인원 수인지 보장하지 못하므로 전체 합계는 우선 ‘수집 196건’으로 표현합니다.

### 사이트 탭

- 탭은 검색 실행 버튼이 아니라 수집 결과 보기 전환입니다. 탭 클릭으로 유료 외부 검색을 재실행하지 않습니다.
- 탭마다 수집 건수와 대기·검색 중·완료·일부 실패·중지·0건을 구별합니다.
- 먼저 준비된 사이트를 최초 표시하되, 이후에는 현재 읽는 탭을 자동으로 바꾸지 않습니다.
- 탭별 페이지와 스크롤을 보존합니다. 전역 경고로 정상 결과 영역을 밀어내지 않습니다.
- 20건 단위 조회를 재사용하고 명시적인 페이지 이동을 권장합니다. ‘현재 80명’은 ‘표시 61–80 / 수집 196건’처럼 명확히 씁니다.
- 링크드인 탭은 본인·CEO 계정 상태를 각각 보이며 CEO 전용 프로필 비공개 계약을 유지합니다.

### 검색 중 검토와 중지

- 사이트·검색어 단위의 수집 완료 결과를 저장하고 즉시 표시합니다. 진행 이벤트만 보내는 것으로는 부족합니다.
- 읽고 있는 목록을 매번 교체하지 않고 새 결과 수를 알려 사용자가 반영할 수 있게 합니다. 후보 식별은 변하는 배열 위치에 의존하지 않도록 기존 소비자까지 검증합니다.
- 검색 중지는 ‘중지 요청됨 → 중지됨’으로 구별합니다. 현재 외부 호출이 끝난 뒤 다음 동작으로 넘어가지 않으며, 모든 사이트·계정·검색어·후보 반복 경계에서 중지를 확인합니다.
- 중지 시 실제 확보한 후보를 보존하고 아직 실행하지 않은 사이트는 ‘미실행’으로 남깁니다. 즉시 종료를 보장하지 않는 동안에는 그렇게 표시하지 않습니다.
- 창 닫기와 검색 중지는 별개입니다. 계속 검색을 허용한다면 닫을 때 이를 알리고 같은 프로젝트에서 다시 진행 상태에 접근할 수 있어야 합니다.
- 진행 표시는 사이트, 계정, 검색어 순번, 실제 확보 건수, 경과 시간을 사용합니다. 근거 없는 완료율·예상 시간은 만들지 않습니다.

## 재검색 계약

| 행동 | 외부 접속 | 결과 처리 |
|---|---|---|
| 현재 결과에서 좁히기 | 없음 | 기존 수집 결과의 보기만 변경. 원본 유지 |
| 실패한 사이트 재시도 | 그 사이트만 | 같은 조건으로 재시도. 성공한 다른 사이트 결과 유지. 다시 실패해도 기존 데이터 유지 |
| 조건을 바꿔 새 검색 | 선택한 사이트 | 새 검색 회차로 분리. 이전 회차 보존. 다른 조건의 결과를 말없이 혼합하지 않음 |

현재의 수동 ‘검색 결과 저장’을 기존 저장 모델 기반의 자동 검색 이력 보존으로 바꾸는 안을 권장합니다. ‘검색 기록’에서 조건·실행 시각·사이트 상태로 구별합니다. 이는 저장 정책 변경이므로 보존 기간·삭제 정책을 정한 뒤 구현합니다. 사이트 탭과 ‘현재 결과에서 좁히기’의 범위가 다르면 실행 전 적용 범위를 표시합니다.

## 실제 지연 개선

1. 승인된 링크드인 목록 href 수집: 후보별 프로필 탭 열기·로딩·닫기를 제거합니다. 실제 목록 링크 구조와 기존 후보 좌표의 연결은 아직 검증 전입니다. URL 검증·계정 격리·중복 제거는 유지합니다.
2. 시간 측정: 로그인, 필터 선택, 화면 판독, URL 수집 시간을 분리합니다. 새 탭 제거로 전체 검색 시간이 얼마나 줄어드는지는 실행 후 측정합니다.
3. 사이트 결과의 조기 공개: 링크드인이 오래 걸려도 먼저 찾은 후보를 검토할 수 있게 합니다.
4. 기존 별도 링크드인 브라우저를 활용한 다른 사이트와의 제한적 동시 실행은 후속 후보입니다. 작업자·잠금·API 사용량을 먼저 확인하고, 모든 사이트를 무제한 병렬 실행하지 않습니다.

## 사람인 안정화

현재 사건의 인과관계: 검색창이 존재함 → 기존 준비 검사가 통과함 → 덮개에 가려 클릭이 전달되지 않음 → 60초 재시도 후 사이트 실패 → 화면이 포괄적인 로그인 안내를 표시함.

- 인재풀 준비 완료를 입력 존재뿐 아니라 정상 사용 가능 상태로 확인합니다.
- 덮개를 만든 실제 팝업의 화면·닫기 컨트롤을 확인합니다. 확인된 일반 안내만 정상 닫기 흐름으로 처리합니다. DOM에서 덮개 삭제나 강제 클릭으로 우회하지 않습니다.
- 세션 만료는 기존 로그인 복구를 재사용합니다. 팝업 차단·추가 인증·네트워크 장애와 구별하며 무조건 재로그인하지 않습니다.
- 복구 뒤 같은 검색창에서 성공을 확인하고 제한된 재시도를 합니다. 인증 코드 무한 재발송이나 무한 재시도는 하지 않습니다.
- 최종 실패에는 사이트·단계·소요 시간·오류 종류·제한된 화면 증거를 남깁니다. 사용자에게는 원인에 맞는 다음 행동만 보입니다.
- 예: ‘화면 안내창 때문에 검색을 진행하지 못했습니다. 다른 사이트 결과는 유지됩니다.’ / ‘추가 인증이 필요합니다.’

이전 2026-08-28 사건은 세션 만료 복구였고 이번은 클릭 차단입니다. 동일 원인 재발로 확정하지 않습니다. 덮개 소유자와 재현 빈도는 미검증이며 아직 해결·재발 차단으로 보고할 수 없습니다.

## 구현 순서와 수용 기준

1. 링크드인 URL 수집과 사람인 준비 상태를 고치고, 기존 성공 사례·실패 재현을 같은 공식 경로에서 검증합니다.
2. 부분 결과 저장·검색 중지·사이트 단위 재시도를 기존 SearchSession/작업자 경로에 통합합니다.
3. 사이트 탭·결과 중심 레이아웃·명확한 건수 표시·재검색 구분을 연결합니다.
4. 검색 이력 자동 보존은 보존·삭제 정책 합의 후 적용합니다.

검수 시 사이트 탭 전환으로 검색이 재실행되지 않는지, 느린 사이트를 기다리지 않고 완료 결과를 보는지, 중지가 이후 외부 호출을 막는지, 재시도·실패·재검색에서 기존 결과가 유지되는지 확인합니다. 키보드 탭 전환과 포커스, 스크롤·페이지 보존, 계정별 인증 경고, CEO 링크 비공개도 검증합니다. 운영 코드·서비스는 이번 문서 작성으로 변경하지 않았습니다.

## 구현 및 리뷰 계약 — 2026-09-08

- 원천: 이 문서와 사용자의 “승인, 구현 진행해”. 기존 저장 모델의 무기한 보존을 재사용하며 자동 삭제는 추가하지 않습니다.
- 기준: 디버깅 detached HEAD `f6f8736f93f36fe63895cfcbb23aa286ed66dcaa`. 시작 시 운영·디버깅 모두 clean. 현재 diff만 검토합니다.
- 역할: 기존 프로젝트 검색 세션 → 기존 후보검색 작업자 → 사이트 검색 → 부분 결과·최종 기록 → 기존 결과 API·모달의 단일 경로.
- 입력: 본인 소유이며 접근 가능한 프로젝트 검색 세션, 기존 검색 계획, 지원하는 5개 사이트. 탭·페이지는 조회만 수행합니다.
- 절차: queued → running → succeeded/failed/cancelled. 중지는 현재 호출 이후 체크포인트에서 종료합니다. 재시도는 선택 사이트만 실행하고 실패 계정·다른 사이트 후보를 보존합니다.
- 출력: 부분 결과 조회, 사이트별 20건 페이지, 실제 사이트·계정 상태, 종료된 검색의 영구 기록. 현재 결과 좁히기는 외부 재검색을 서버에서 차단합니다.
- 보호: 기존 내부 검색·후보 선택 계약, 프로젝트·사용자 권한, LinkedIn 본인/CEO 계정 격리 및 CEO URL 비공개, 기존 운영 자료·사용자 수정, 영속 브라우저 수명.
- 비목표: 자동 후보 추천·탈락, 유료 연락처 열람, 자동 게시·이력서 추출, DB 인프라·Hermes 변경, 사이트 무제한 병렬화.
- 검증: 기존 후보검색·검색서비스 검사와 중지/부분 보존/재시도/권한/페이지/AI 경계 회귀 검사. 실제 개발 모달 조작, 실제 LinkedIn·사람인 검색 진입점, 배포 후 운영 화면.
- 검토 관점: diff의 상태 전이가 보존 계약을 깨는지, 직접 소비자인 결과 API·모달·저장 기록에서 데이터나 권한이 바뀌는지.
- 최소 구현 게이트: 2단계에서 멈춤 — 기존 SearchSession, SavedCandidateSearchResult, 작업자, 결과 action API, 20건 페이지 및 인증 복구를 재사용합니다. 새 의존성·작업자·별도 수집 경로는 없습니다.

### 현재 확인 결과
