# 샘의 Exdigm 운영 오류 관리

## 책임

샘은 Exdigm의 `projects.OperationalError`를 직접 조회하고, 새 오류나 처리 내용이 바뀐 오류를 직접 조사해 주인님께 쉽게 보고한다. 별도의 main Codex 작업자에게 조사·수정·배포를 넘기지 않는다.

정기 실행은 **조회·조사·보고만** 한다. 소스·Git·운영 DB·서비스·배포 상태를 바꾸지 않는다. 수정·커밋·배포·운영 데이터 재처리는 주인님의 명시적 지시를 받은 대화에서 샘이 직접 수행한다. 수정 지시가 있으면 `~/controlroom/exdigm/AGENTS.md`의 원격 debug worktree, 검증, 리뷰, 커밋 경계를 따르고, 배포는 별도 명시가 있을 때만 공식 배포 경로로 실행한다.

## 최소 코드·SSP 필수 게이트

오류 장부의 조사·재현·수정·재처리·종결 전에 매번 적용한다. 아래 근거를 확인하지 못하면 코드나 운영 데이터를 바꾸지 않고 오류를 성공 종결하지 않는다.

1. **정본 경로 잠금**: 현재 코드와 실제 호출자에서 `입력 → 공식 진입점 → 오케스트레이터·계약 → 상태 저장 → read-back 검증`을 확인해 짧게 기록한다. 과거 처리 이력이나 함수 이름만으로 정본을 추측하지 않는다.
2. **진단과 처리 분리**: 내부 함수·개별 LLM 프롬프트·중간 단계의 직접 호출은 원인 격리에만 쓴다. 그 결과로 업무 결과를 판정하거나 재처리 성공·오류 종결을 선언하지 않는다. 최종 처리는 잠근 공식 진입점에서 다시 실행하고 저장 결과를 읽어 검증한다.
3. **SSP 위반 시 중단**: 진입 경로마다 최종 분류·검증·저장 판단이 다르거나 두 경로가 같은 입력에 다른 결과를 내면 SSP가 열린 상태다. 편한 경로 하나로 운영 데이터를 처리하거나 새 예외 규칙·병렬 경로를 추가하지 않는다. 현재 승인 범위에서 정본 경로를 복구할 수 없으면 원인과 필요한 범위 변경을 보고하고 실행을 보류한다.
4. **최소 코드 잠금**: 기존 공식 진입점·오케스트레이터·계약을 재사용해 책임 위치를 고치는 최소 변경만 허용한다. 오류를 통과시키기 위한 새 진입점·분류기·재시도·저장 경로·파일·사례별 분기를 만들지 않는다. 코드 변경 전 `최소 구현 게이트: N단계에서 멈춤 — <검색·재사용 근거>`를 남긴다.
5. **종결 증거**: 공식 경로의 종료 상태, 필수 업무 객체와 부작용, 새 오류 유무를 read-back한 경우에만 처리 성공을 기록한다. 직접 진단만 성공했거나 SSP가 열려 있으면 `미검증` 또는 `수정 필요`로 남긴다.

정기 읽기 전용 점검도 이 게이트를 적용한다. 150초 안에 정본 경로를 확인하지 못하면 내부 단계를 직접 실행해 결론을 만들지 말고 SSP 위험과 대화형 재개 지점만 보고한다.

## 정기 조회

main에서 10분마다 실행되는 Hermes cron이 이 스킬의 정기 진입점이다. cron의 `workdir`는 `~/controlroom/exdigm`이다. **150초 안에 최종 응답을 만들고**, 시간이 부족하면 확인한 사실과 정확한 재개 지점만 보고한다.

1. 먼저 `~/.hermes/state/exdigm-error-control.json`을 읽는다. 파일이 없으면 빈 상태로 시작한다.
2. SSH 대상 `chaconne@49.247.202.197`, debug worktree `/home/chaconne/exdigm-debug`에서 `scripts/debug_workspace.sh shell-readonly`를 사용해 `projects.OperationalError`를 SELECT만 한다. ORM 필드는 현재 모델에서 확인하며 이름을 추측하지 않는다.
3. 오류별 마지막 보고 `handling_revision`과 비교한다. 다음 항목만 새 조사 대상으로 삼는다.
   - 상태 파일에 없는 `next_action=investigate` 오류
   - `handling_revision`이 마지막 보고보다 증가한 오류
   - 마지막 보고 뒤 새로 생긴 오류 중 조사나 주인님의 판단이 필요한 오류
   과거 `next_action=none`, 성공 완료, 시험용 오류는 새 증거가 없으면 다시 보고하지 않는다.
4. 조사 대상이 없으면 다른 문서·GBrain·Git·코드를 조회하지 말고 최종 응답을 정확히 `NO_REPLY`로 끝낸다.
5. 조사 대상이 있을 때만 프로젝트 `AGENTS.md`, 관련 진행 문서와 GBrain을 최소 범위로 확인한다. hostname이 `main`이면 GBrain DB는 로컬이다. SSH나 `gbrain-remote-proxy`를 사용하지 말고 `/srv/consolidation/infra/gbrain-host get project/exdigm-operating-context --source default`와 같은 로컬 명령을 실행한다. PC·노트북에서만 `~/.gbrain-agent.md`가 지정한 main SSH 프록시를 사용한다.

상태 파일은 알림 중복 방지용이며 Exdigm DB의 처리 상태를 대신하지 않는다.

## 정기 조사

오류 문구를 원인으로 단정하지 않는다. 정기 실행은 읽기 전용 증거 확인을 **최대 네 번의 도구 호출 묶음**으로 제한한다.

- 오류 행의 `summary`, `description`, `context`, `traceback`, `processing_history`, `handling_context`와 연결된 업무 객체
- 오류가 난 현재 코드와 실제 호출자·입력 흐름
- 운영·debug Git 상태와 관련 최근 변경
- 같은 유형의 기존 성공 사례와 관련 진행 문서

정기 실행에서는 전체 테스트, 장시간 재현, 브라우저 확인, 새 진단 자료 생성을 수행하지 않는다. 제한 안에 근본 원인을 확정할 수 없으면 원인 후보와 다음 대화형 조사 단계를 보고한다. 주인님이 후속 조사를 지시한 대화에서는 `systematic-debugging` 절차를 완전히 적용한다.

고객 원문·인증값·개인정보는 보고나 공유 문서에 복제하지 않는다.

## 보고와 체크포인트

보고에는 오류별로 다음만 담는다.

- 오류 ID와 발생 시각
- 무엇이 실패했는지 쉬운 설명
- 사용자 업무에 미친 영향
- 확인한 근본 원인, 또는 아직 원인 후보인 이유
- 권장 해결 방향과 수정·배포 여부
- 주인님이 결정하거나 제공해야 할 것이 있을 때만 구체적인 다음 행동

정기 실행은 수정이나 배포 승인을 전제로 묻지 않는다. 조사 결과 수정이 필요하면 “수정 필요, 미실행”으로 알린다. 이미 검증된 수정이 있어도 주인님의 명시적 배포 지시 전에는 배포하지 않는다.

최종 보고문을 완성한 뒤, 응답을 반환하기 직전에 해당 오류의 `handling_revision`, 보고 시각, 조사 결과 요약 해시를 상태 파일에 원자적으로 저장한다. 상태 저장에 실패하면 보고문에 체크포인트 실패를 밝힌다. 조사 자체가 실패해 유효한 보고문을 만들지 못하면 성공한 체크포인트로 기록하지 않는다.

## 대화형 운영 진단의 오류 기록 경계

주인님 지시로 운영 자격증명이 필요한 읽기 진단을 수행하더라도, 조사 자체의 예상 실패를 새 운영 장애로 기록하지 않는다.

- 가능한 조사는 항상 debug worktree의 `shell-readonly`와 개발 테스트 DB에서 한다.
- 운영 체크아웃의 기존 자격증명이 꼭 필요한 읽기 진단에서 실패를 의도적으로 관찰할 때는 기존 Django command 또는 함수를 `manage.py shell` 안에서 호출하고, 예상 예외를 프로세스 안에서 잡아 오류 종류와 안전한 요약만 출력한다. 예외를 `manage.py` 최상위까지 탈출시키면 운영 오류 hook이 실제 장애처럼 `OperationalError`를 만든다.
- `OPERATIONAL_ERRORS_ENABLED`를 서비스 전역에서 끄거나 운영 설정·`.env`를 바꾸지 않는다. 성공해야 하는 최종 공식 경로 검증은 정상 명령으로 실행하며, 여기서 난 실패는 숨기지 않는다.
- 조사 명령이 실수로 오류 행을 만들면 삭제·수정하지 않는다. 해당 ID를 조사 산출물로 명시하고 실제 고객 업무 오류와 구분해 체크포인트와 장기 기록에 남긴다.

## 주인님 지시 후 실행

주인님이 특정 오류의 조사·수정·검증·배포를 지시하면 샘이 현재 대화에서 직접 수행한다. DB의 과거 `next_action`, 자동화 예약, 이전 승인 기록을 현재 지시로 간주하지 않는다. 작업이 끝나면 실제 검증 결과와 남은 위험을 보고하며, 필요할 때 Exdigm의 기존 오류 기록 API로 처리 결과를 남긴다. 기록을 위해 운영 DB를 임의 SQL로 수정하지 않는다.
