# CRETOP 로컬 정본·원격 복제 설계

## 목적

CRETOP 수집 SSP와 데이터 정본을 로컬에 두고, Windows 원격 서버는 브라우저 실행과 결과 파일 생성만 담당한다. 로컬이 결과 파일을 회수·검증해 로컬 DB에 먼저 확정한 뒤, 로컬 동기화 장치가 ceoloan 서버의 수집 데이터 복제본을 같은 내용으로 만든다.

## 확정 계약

1. SSP 기준 소스는 로컬 Git 파일 `scripts/cretop_agent.py`다.
2. 브라우저 수집은 기존 Windows 원격 세션에서 배포된 SSP로 실행한다.
3. 결과 JSON과 증거 파일은 로컬로 모두 회수한 뒤 `rndnote-db-prod`의 `ceo_loan` DB에 먼저 저장한다.
4. 로컬 저장이 커밋된 뒤에만 로컬 동기화 장치가 `49.247.205.170`의 `ceo_loan` DB에 복제한다.
5. 동기화 실패는 이미 커밋된 로컬 데이터나 회수 파일을 되돌리지 않는다.
6. 같은 run ID의 `remote-batch-fetch`를 재실행하면 재추출 없이 로컬 파일과 로컬 DB를 이용해 미완료 동기화를 복구한다.

## DB 역할

| 역할 | 접속점 | 쓰기 책임 |
|---|---|---|
| 로컬 정본 | `rndnote-db-prod`, `ceo_loan`, 로컬 5433 | 대상 선정, 원문 저장, 구조화 저장 |
| 원격 복제본 | `49.247.205.170`의 `ceoloan-db`, `ceo_loan`, SSH 터널 15433 | 로컬 동기화 장치가 확정 행 복제 |
| 로컬 개발 DB | `ceoloan-db`, 로컬 5434 | 이번 작업에서 사용하지 않음 |

`CretopBatchStore`는 로컬 정본에만 접속한다. 원격 접속 정보는 복제 전용 구성으로 분리하며, 두 접속점이 같으면 실행을 거부한다.

## 데이터 소유권

동기화 대상은 `public.leads`와 `cretop` 스키마다. `cretop`의 조회 원문, 상세 섹션, 구조화 회사·재무·인증·신용 데이터, 기준 정의와 보고서 파생 테이블을 로컬 정본 기준으로 복제한다.

다음 원격 운영 데이터는 동기화하지 않는다.

- `public.funding_*`
- `public.users`와 인증·세션 테이블
- SMS 캠페인·발송 테이블

## 최종 데이터 흐름

`batch-script-only-collect`는 로컬 DB에서 미처리 회사를 선정하고 payload를 만든다. 로컬 SSP를 Windows에 배포해 SHA-256 일치를 확인한 뒤 Windows가 `collect-batch`를 실행한다.

`remote-batch-fetch`는 다음 순서를 한 경로로 수행한다.

1. Windows outbox 결과 JSON과 증거 파일을 로컬 run 디렉터리에 회수한다.
2. 기존 품질검사로 저장 가능 항목과 보류 항목을 구분한다.
3. 저장 가능 항목을 로컬 `CretopBatchStore.save_result()` 트랜잭션으로 확정한다.
4. 로컬에서 확정된 기본키와 행을 `CretopReplicaSynchronizer`가 원격 트랜잭션에 복제한다.
5. 해당 조회·회사 범위의 로컬·원격 행을 비교한다.
6. 모든 저장 가능 항목의 복제 검증이 끝난 뒤에만 Windows 작업을 정리한다.

## 복제 방식

원격에서 원문을 다시 파싱하거나 `save_result()`를 재실행하지 않는다. 재실행하면 UUID 기본키와 파생 행이 달라지므로, 로컬에 커밋된 행을 기본키와 값 그대로 복제한다.

한 항목의 원격 트랜잭션은 다음 순서를 사용한다.

1. `public.leads`
2. 조회 실행·후보·상세 snapshot·상세 section·재무 원문 파일
3. 구조화 회사
4. 기존 원격 회사별 파생 행 삭제
5. 로컬 회사별 파생 행 삽입
6. 조회 상태
7. 로컬·원격 행 비교 후 커밋

기본키 충돌은 같은 로컬 값으로 갱신한다. 사업자번호가 같은데 기본키가 다른 충돌이나 로컬에 없는 원격 전용 행은 데이터 드리프트로 보고 실패한다.

## 장애와 재실행

- 로컬 저장 실패: 원격 복제를 시작하지 않는다.
- 원격 복제 실패: 로컬 저장과 회수 파일을 보존하고 Windows 작업을 정리하지 않는다.
- 중간 종료 후 재실행: 로컬 결과 파일을 우선 재사용하고, `save_result()`의 기존 결과를 해석해 같은 기본키를 다시 복제한다.
- 품질검사 보류: 로컬과 원격 어느 DB에도 저장하지 않고 기존 `deferred_items`에 남긴다.
- 복제 검증 실패: 원격 트랜잭션을 롤백하고 로컬 정본은 유지한다.

## 최초 데이터 복구

현재 원격 `cretop`은 로컬보다 2,484,622행 많고, 검사한 공유 주요 행은 동일하며 로컬 전용 주요 기본키는 없다. 최초 전환은 다음 순서로 수행한다.

1. 로컬 `cretop` 스키마를 복구 가능한 custom-format dump로 백업한다.
2. 원격 `cretop` 스키마를 같은 형식으로 덤프한다.
3. 원격 스냅샷을 로컬 `cretop` 스키마에 기본키 그대로 복원한다.
4. 34개 테이블의 스키마, 행 수, 주요 기본키와 공유 행을 대조한다.
5. `public.leads` 14,084행은 이미 동일하므로 교체하지 않고 검증만 한다.
