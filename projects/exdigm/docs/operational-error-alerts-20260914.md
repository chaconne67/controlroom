## 기존 구현과 부족한 부분

- `projects/services/notification.py`는 알림과 웹 배달 요청을 만든다.
- 같은 파일의 `send_notification()`은 현재 외부 알림을 보내지 않고 `False`를 반환한다.
- `projects/services/notification_extensions.py`에 채널 등록 확장 지점이 이미 있다.
- `deliver_notification_dispatches`는 등록된 채널을 처리하는 기존 운영 작업자다.
- 현재 Telegram 채널의 전송 처리자는 등록돼 있지 않다.
- `agent_infrastructure/hermes_runtime.py`에 인증된 `exdigm-notifications` webhook 경로가 있다.
- 이 경로는 `deliver_only`로 Telegram에 전달한다. 새 LLM 판단이나 봇 token 복사는 필요 없다.
- 일부 실패 기록은 `QuerySet.update()`로 저장된다. `post_save`만 관찰하면 놓친다.
- 후보자 검색 실패는 단순 status 열이 아니라 기존 작업 상태 JSON에도 남는다.
- 일반 업무의 탈락·거절·건너뜀과 프로그램 실행 실패를 동일시하지 않는다.

| 발생 신호 | 알림 조건 | 처리 원칙 |
|---|---|---|
| 웹·작업자의 Python 오류 로그 | 운영의 ERROR·CRITICAL·예외 로그 | 원래 로그는 보존하고 별도로 수집한다 |

| 후보자 검색·임베딩·미팅 처리 | 현재 작업 상태에 확정된 실패 | 후보자 탈락이나 정상 취소는 오류로 알리지 않는다 |

- 기능 활성화 이전의 과거 실패를 한꺼번에 발송하지 않는다.
- 정상 완료·일반 진행 로그는 보내지 않는다.
- 알림의 실패는 새 운영 알림을 끝없이 만드는 입력으로 다시 사용하지 않는다.
- 외부 시스템이 자체 복구한 일시 재시도 신호와 확정 실패를 구분한다.

## 공식 경로와 변경 위치

`운영 오류 로그 또는 확정된 작업 실패 → 오류 신호 수집 → 기존 Notification/NotificationDispatch에 저장 → 기존 배달 작업자 → 해당 profile의 HMAC webhook → 지정 Telegram 봇 → 기존 개인 대화방`

- 오류 로그 수집기는 업무 처리를 막지 않도록 짧은 로컬 기록만 한다.
- 로컬 기록은 이미 앱·운영 작업자가 사용하는 runtime 경계 안에 둔다.
- 배달 작업자가 이 기록과 작업의 실패 상태를 읽고 알림을 확정한다.
- 실패 상태는 실제 저장 경로를 조사해 읽는다. save signal에만 의존하지 않는다.
- 활성화 기준 시각과 로컬 기록의 처리 위치를 보존한다.
- 작업 실패는 조회 시각을 앞으로 넘기지 않고, 동일 신호의 알림 기본키가 이미 존재하는지 대조한다.
- 먼저 발생했지만 늦게 저장된 실패도 잡고, 재시작 뒤 같은 실패를 다시 알리지 않는다.
- 기존 알림의 UUID 기본키·채널별 유일성 계약을 사용해 동일 신호의 중복을 차단한다.
- Telegram 전송 처리자는 기존 채널 확장 지점에 연결한다.
- 이 전송 처리자는 이번 운영 오류 알림만 처리한다. 일반 직원 알림을 모두 Telegram으로 바꾸지 않는다.
- 필요 변경 위치는 운영 settings, 기존 배달 명령, Hermes 앱의 채널 등록, 최소 수집·전송 모듈과 관련 테스트다.
- 공유 runtime의 경로·권한과 host/container 실행 사용자를 잠근 뒤 새 기록 파일을 만든다.
- 새 수집·전송 모듈의 정확한 위치는 구현 전 SSP 기록에서 현재 호출 관계와 함께 확정한다.

## 재사용과 최소 구현

- 새 알림 DB·별도 알림 서버·새 systemd 감시 작업자를 만들지 않는다.
- 직원 봇 token을 Django나 개발 환경에 복사하지 않는다.
- 기존 profile·개인 대화방·암호화된 webhook secret·Hermes route를 재사용한다.
- 기존 알림 테이블·Telegram 채널·채널 확장 지점·배달 작업자를 재사용한다.
- 서명·JSON·로컬 기록·HTTP는 표준 기능을 사용한다. 새 의존성은 추가하지 않았다.
- 기존 구현에 없는 오류 신호 수집과 Telegram 채널 연결에 필요한 최소 코드만 추가한다.
- 구현 직전 최소 구현 게이트에서 검색 근거와 멈추는 단계를 별도로 밝힌다.

## 메시지와 보안

- 알림에는 운영 구분, 발생 시각, 업무 종류, 실패 코드 또는 안전한 설명, 해당 기록을 찾을 식별자를 담는다.
- 이력서·메일·요청의 원문과 입력값, 로그 인자, 비밀값, 전체 traceback은 전달하지 않는다.
- 원래 자세한 오류 기록은 기존 서버의 기록 경로에 남긴다.
- 로컬 수집 파일과 처리 위치 파일에는 필요한 최소 정보만 둔다.
- webhook 본문은 UTF-8 JSON으로 보내고 기존 HMAC V2 계약을 따른다.
- `delivered` 응답만 신규 전송 성공으로 인정한다. 이미 DB에 확인 완료가 저장된 경우만 그 확인을 재사용한다.
- 현재 Hermes는 전달 전에 요청 번호를 기억한다. 전달 실패 후의 `duplicate`는 전달 증거가 아니다.
- 요청 제한(429)·연결 거절·DNS 실패처럼 전달 전 실패가 확실한 경우만 대기 후 재시도한다.
- 재시도는 총 8회까지다. 대기 시간은 5초부터 늘고 최대 300초다. 한도를 넘으면 실패를 명시한다.
- 시간 초과·확인 없는 중복 응답·5xx는 `delivery_outcome_unknown`으로 보존한다. 성공으로 기록하거나 자동으로 다시 보내지 않는다.
- 5xx는 Telegram 쪽 시간 초과를 감쌀 수 있다. 주인님의 대화방에 이미 도착했을 가능성을 배제할 수 없어 새 요청 번호로 재전송하지 않는다.

- 외부 사이트의 실제 게시·수정·마감·삭제와 실고객 메일 발송.

- 위 기준선을 변경 후 같은 명령으로 다시 실행한다.
- 기존 웹 알림의 생성·중복 방지·전송 실패 기록·수명주기 처리를 보존한다.
- 실제 운영 설정의 오류 로그가 수집·저장·배달 입력으로 연결되는지 확인한다.
- 작업 실패는 개별 save, 일괄 update, 일부 실패, 중단, 재시작, 같은 오류 반복을 검사한다.
- 정상 완료·정상 취소·활성화 이전 기록·일반 직원 알림은 전송하지 않는지 검사한다.
- Telegram의 정상 전달·중복 응답·일시 실패·영구 실패·잘못된 인증을 검사한다.
- 알림 장애와 기록 실패가 원래 업무를 실패시키거나 로그를 재귀적으로 폭증시키지 않는지 검사한다.
- 비밀값·입력 원문이 수집·알림·전송 실패 기록에 남지 않는지 검사한다.
- 공식 Django check, 고정 보호 contracts, catalog_update와 필요한 직접 소비자 검사를 실행한다.
- 실행 코드 변경은 `code-review-loop`를 통과하고 주 에이전트가 확인한 결함만 수정한다.
- 개발 검증에서는 실제 운영 Telegram 인증을 가져오지 않는다.
- 검증 커밋을 보고하고 별도 운영 배포 승인 뒤 공식 `scripts/deploy/deploy.sh prod`로 반영한다.
- 배포 후 ‘테스트’임을 명시한 오류 신호를 정상 수집 경로에 한 번 넣는다.
- 해당 알림의 실제 Telegram 전달 응답과 저장된 전송 완료 상태를 확인한다.
- 주인님의 실제 운영 작업을 일부러 실패시키거나 외부 업무를 재실행하지 않는다.
- 구현·검증·운영 반영·실제 전달은 각각 구분해 보고한다.

## 한계

- 전체 서버 정지·네트워크 단절은 같은 서버 안의 알림 경로로 즉시 감지·전달할 수 없다.
- DB가 중단되면 로컬 오류 기록은 남겨도 기존 DB 기반 배달은 복구 뒤 이어서 처리한다.
- 서버 외부의 장애 감시와 별도 전송 경로는 이번 계획에 포함하지 않는다. 필요하면 별도로 승인받는다.

## 구현 결과와 잠근 경로

- 코드 수정은 원격 디버깅 worktree에서만 했다. 운영 체크아웃은 시작 상태를 유지한다.
- `main/settings/deploy.py`의 운영 설정 → `common/operational_errors.py`의 로그·미처리 예외 수집 → 기존 runtime의 최소 JSONL 기록으로 연결한다.
- `hermes_integration/apps.py`의 준비 단계 → 기존 `notification_extensions.py`의 수집기·채널 등록 → 기존 배달 명령으로 연결한다.
- 배달 명령 → `hermes_integration/operational_alerts.py`의 기록·확정 실패 조회 → 기존 알림·Telegram 배달 요청 저장으로 연결한다.
- 배달 명령 → `hermes_integration/notification_delivery.py` → 기존 관리형 Hermes의 인증된 webhook → 기존 Telegram 개인 대화방으로 연결한다.
- 핵심 웹 코드에서는 선택형 Hermes 구현을 직접 import하지 않는다. Hermes 비활성 상태의 웹 시작·알림 경로를 보존한다.
- 정상 직원 알림에 Telegram 요청을 추가하는 creator는 등록하지 않는다. 이번 오류 알림만 Telegram 요청을 만든다.
- 같은 위치·예외 종류의 오류 로그와 같은 코드의 파일 실패는 5분 단위로 묶는다.
- 상위 자동 게시 실패와 실패한 사이트 기록이 동시에 있으면 사이트 기록을 우선한다.
- 한 번의 배달 묶음에서 기존 웹 알림을 먼저 처리하고, Telegram 네트워크 전송은 최대 한 건이다.
- 조작하지 않은 정상 취소·진행 중 검색·재시도 가능한 파일 실패·과거 실패는 발송 대상이 아니다.
- 신호 기본키는 Python과 PostgreSQL에서 같은 결정적 UUID로 계산한다. PostgreSQL의 기존 MD5 함수는 식별자 계산에만 사용한다. 인증은 기존 HMAC-SHA256을 유지한다.
- 작업 실패 조회는 이미 있는 알림 기본키와 대조한다. 처리 시각을 건너뛰는 방식이 아니므로 먼저 발생했지만 늦게 저장된 실패를 놓치지 않는다.
- 알림 화면의 무시 동작은 기존대로 읽음 처리만 한다. 확인 기록이 없어져 같은 실패를 다시 만드는 동작으로 바꾸지 않는다.
- 로그 처리 위치는 알림·배달 요청 저장 뒤 원자적으로 교체한다. 처리 위치 저장이 실패해도 같은 신호가 중복 생성되지 않는다.
- 완성되지 않은 마지막 로그 줄은 다음 조회까지 기다린다. 손상된 완성 줄은 원본을 보존하고 안전한 손상 알림을 만든 뒤 다른 신호를 처리한다.

### 파일 경로·권한과 최소 구현

- 기준 경로는 기존 host `runtime`과 컨테이너 `/app/runtime`의 공유 mount다.
- host 작업자는 chaconne(uid/gid 1001), 기존 앱·배달 컨테이너는 root다.
- `/home`은 root 755, `/home/chaconne`은 chaconne 750, 운영 폴더·runtime은 chaconne 775다.
- 프로세스별 기록·처리 위치는 600, 공용 활성화 시각은 644다. host 기록을 root 배달 작업자가 읽고 host도 활성화 시각을 읽을 수 있다.
- 활성화 시각은 완성된 임시 파일을 원자적으로 공개한다. 여러 프로세스가 동시에 시작해도 빈 시각 파일을 읽지 않는다.
- 최소 구현 게이트: 알림 저장·채널·등록·배달 작업자는 2단계에서 재사용했다.
- 확인 근거는 `NotificationDispatch`, `register_notification_dispatch_handler`, `notification_dispatch_handler`, `send_notification`, `LOGGING`과 관련 파일 검색이다.
- 누락된 로그 수집·인증 HTTP 연결은 3단계의 `logging`, `threading`, `urllib`, `hmac`, `hashlib`, `json`, `tempfile`로 구현했다.
- DB 조회·기본키 대조는 설치된 Django의 `Q`, `Exists`, `Cast`, `Concat`, `MD5`와 PostgreSQL 기본 함수로 표현했다. 새 DB 확장·의존성·서버·작업자는 없다.
- 운영 SELECT 전용 경로에서 새 파일 실패 조회의 EXPLAIN을 확인했다. 기존 `file_statuses_retryable_c502799a`와 `projects_notification_pkey` 인덱스를 사용한다.
- 두 파일 조회의 추정 비용은 329.34·334.96, 추정 결과는 각 1건이다. EXPLAIN은 실행 시간 측정이나 실전송 증거가 아니다.
