# Hermes MCP 조회 개선안

작성일: 2026-09-16 · 상태: 재검토·개발 구현·리뷰·실제 모델 24회 검증 완료, 운영 미반영

## 1. 원하는 결과

직원은 짧은 업무 질문을 하고, 비서는 그 질문에 필요한 데이터만 조회해 근거와 함께 답한다. 결과가 없으면 확인한 범위에서 없다고 답하고, 결과가 많으면 먼저 작은 목록을 보여준다. 긴 대화에서도 질문의 기간·대상·조회 범위를 유지한다.

이번 개선의 중심은 **모델에 큰 결과를 준 다음 요약시키는 것이 아니라, 기존 MCP가 처음부터 작고 완전성이 분명한 결과를 주게 만드는 것**이다. 모델 교체는 이 변경의 효과를 같은 모델로 확인한 뒤 판단한다.

최종 답변 한 페이지와 내부 조회 한 페이지는 구분한다. 답은 짧아도 여러 자료를 확인해야 할 수 있으므로 내부 조회를 한 번으로 제한하지 않는다. 각 조회가 작고 필요한 이유가 분명해야 한다.

## 3. 범위와 보호할 조건

개선 대상은 기존 `code_query → orm_read / exdigm_request → Hermes 답변` 경로다.

- 기존 세 MCP 도구, 직원별 인증·행 권한·비밀 필드 차단, 읽기 전용 ORM 경계를 유지한다.
- Exdigm 업무의 기본 조회 범위를 명확히 하되, 사용자가 요청한 개인 메일·일반 도구 업무는 계속 허용한다.
- Hermes의 메모리·개인화·학습 스킬·작업공간을 보존한다. 설치된 Hermes 본체를 직접 패치하지 않는다.
- 업무별 조회 API, 별도 검색 스크립트, 두 번째 조회 에이전트, LLM 요약 서버, 캐시·벡터 DB는 추가하지 않는다.
- 현재 모델과 압축 임계치는 먼저 유지한다. 임계치를 올려 큰 컨텍스트를 감추는 방법으로 통과시키지 않는다.
- 현재 진행 중인 LinkedIn·잡코리아·추천 이력서 변경은 이 작업에 포함하지 않는다.

주인님의 “개선안 재 검토 후 진행해”에 따라 아래 개발 구현·검증·리뷰·문서화·검증된 범위의 커밋을 진행한다. 운영 배포는 이 계획의 별도 단계이며 아직 수행하지 않았다.

## 4. 개선할 네 가지 책임

### A. MCP 전송: 같은 결과는 한 번만 전달

수정 위치는 `agent_infrastructure/exdigm_mcp/server.py`의 기존 도구 등록부다. 세 도구의 반환값 내용과 오류 계약은 유지하고, 설치된 FastMCP의 `structured_output=False` 옵션으로 텍스트 한 경로만 사용한다. SDK의 자동 들여쓰기에도 증가 요인이 있어 기존 함수의 값을 공백 없는 JSON 문자열로 전달하는 공통 래퍼를 사용한다. `functools.wraps`로 기존 입력 계약을 유지하며 실제 SDK의 입력 스키마도 검증한다.

현재 설치된 `mcp==1.26.0`으로 기존 입력 스키마와 반환값을 확인했다. 기본 등록은 텍스트와 구조화 결과를 함께 생성했고, 수정한 등록은 같은 데이터를 텍스트로만 반환하며 `outputSchema`도 제거됐다. 공식 Hermes의 보안 안내문을 포함한 최종 메시지까지 검증했으며, 실제 에이전트 24회 평가 결과는 아래에 별도로 기록했다. 운영에는 아직 반영하지 않았다.

- `status_code`, 데이터, 오류, 페이지 정보가 이전과 같아야 한다.
- 실제 SDK와 Hermes의 결과 직렬화까지 통과한 문자열에서 업무 데이터가 한 번만 있어야 한다.
- 구조화 출력에 의존하는 다른 소비자가 있는지 확인한다. 있다면 그 소비자 계약을 먼저 해결한다.
- 단위 테스트의 가짜 FastMCP만으로 검증을 대신하지 않는다.

MCP는 구조화 결과와 호환용 텍스트의 동시 제공을 허용한다. 이번 변경은 전용 Hermes 연결에서 같은 정보를 두 번 읽는 낭비를 제거하는 것이다. [MCP 도구 결과 명세](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

### B. ORM 응답: 행 수와 실제 크기를 함께 제한

수정 위치는 `hermes_integration/orm_read.py`의 기존 조회·페이지·크기 검사다. 이미 있는 `fields`, `filters`, `aggregates`, `limit`, `offset`, `page`를 재사용한다.

| 질문 형태 | 첫 조회 | 종료·추가 조회 기준 |
|---|---|---|
| 있는지·몇 건인지 | 모든 조건을 적용한 기존 `count` 집계 또는 최소 필드 1행 | 성공 응답과 전체 건수로 답할 수 있으면 종료 |
| 어떤 내용인지 | 필요한 제목·일시·상태·식별자 중심의 작은 목록 | 작은 결과는 그대로 답하고, 더 있으면 전체 건수와 표시 범위를 알림 |
| 특정 건의 상세 | 먼저 확보한 식별자로 해당 건의 필요한 필드만 조회 | 질문의 근거가 확보되면 종료 |
| 긴 원문·전체 자료 요청 | 작은 목록으로 대상을 확정한 뒤 필요한 부분을 순서대로 조회 | 명시된 작업에 필요한 범위만 계속 읽고 부분 조회임을 유지 |

개발 검증을 거쳐 확정한 값은 다음과 같다. 숫자는 모델 자체의 성능 한계가 아니라 이번 공통 조회의 응답 계약이다.

- 일반 목록의 기본 `limit`은 20에서 10으로 줄인다. 기존 최대 100행은 상한으로 유지하되 바이트 예산이 먼저 적용된다.
- 일반 행 조회의 전체 업무 JSON 응답은 UTF-8 **7.5 KiB(7,680바이트)**를 예산으로 한다. `result`뿐 아니라 모델명·페이지 정보도 포함한다. 처음의 8 KiB에서 512바이트를 남기는 이유는 Hermes의 문자열 이스케이프와 347바이트 보안 안내문까지 최종 크기에 포함하기 위해서다. 8 KiB 이하의 따옴표 본문이 최종 16,631바이트가 되는 반례를 재현한 뒤 보완했다.
- 실제 SDK와 Hermes를 거쳐 모델에 들어가는 일반 행 조회 결과는 **16 KiB 이하**를 인수 기준으로 측정한다. 7.5 KiB 업무 응답과 최종 직렬화 크기를 같은 값이라고 보고하지 않는다. 따옴표가 많은 경계 사례의 최종 결과는 15,631바이트로 이 기준을 통과했다.
- 기존 64 KiB의 최종 방어 한도는 유지한다. schema·코드 조회·실행 계약은 행 목록처럼 잘라 의미를 바꾸지 않는다. 해당 응답은 별도로 크기를 측정하고 기존 선택 조회·소스 부분 읽기를 사용한다.

행이 예산을 넘으면 **완전한 행 단위**로 이번 페이지를 줄인다. `total`은 권한과 조건을 적용한 전체 건수, `returned`는 실제 반환 건수, `next_offset`은 실제 반환한 다음 위치다. `has_more`와 함께 잘림 여부가 드러나야 한다. 반환하지 않은 행을 반환했다고 세거나 일부 데이터로 전체 완료를 선언하지 않는다.

작은 페이지가 누락·중복을 만들지 않도록 정렬도 함께 고친다. 기존 사용자 정렬의 우선순위를 유지하면서 반환 결과의 의미에 맞는 마지막 정렬 기준을 보강한다. 기본키가 포함된 레코드 목록은 기본키, 집계는 그룹 키, 선택 필드의 값으로 중복을 제거한 목록은 해당 선택 필드를 기준으로 삼는다. 숨은 기본키를 무조건 추가해 기존 `distinct`의 의미와 건수를 바꾸지 않는다. 지원 필드별 정렬 가능성은 구현 전 계약과 테스트에서 확인한다. 정적인 데이터의 페이지 안정성을 검증하며, 조회 사이의 실시간 수정까지 고정하는 스냅샷 기능은 추가하지 않는다.

**한 행의 긴 본문 문제도 처리한다.** 예산보다 큰 행에서 빈 페이지와 같은 `next_offset`을 계속 반환하면 안 된다. 일반 조회는 큰 필드와 더 좁힐 방법을 짧은 오류로 알려준다. 원문이 정말 필요한 경우에는 같은 `orm_read`의 선택적인 텍스트 범위 읽기로 처리한다.

- 기존 모델·필드 권한 검사와 직원 범위를 그대로 통과해야 한다.
- 정확한 한 레코드와 허용된 텍스트 필드 하나, 시작 위치·길이로 범위를 지정한다.
- 원문 전체 길이, 실제 반환 범위, 다음 시작 위치, 미완료 여부를 돌려준다. 문자를 임의 요약하거나 완전한 필드 값처럼 가장하지 않는다.
- 텍스트 위치는 문자 기준, 응답 예산은 UTF-8 바이트 기준으로 구분한다. 한글·이모지가 있어도 문자를 손상하지 않고 실제 반환 위치만큼 진행한다.
- 일반 조회에서 긴 필드를 요청했을 때의 기존 413 계약은 유지한다. 범위 읽기는 명시적으로 요청했을 때만 동작한다.
- 임의 JSON 탐색 언어·파일 내보내기·새 엔드포인트로 확장하지 않는다. 구체적인 입력 필드 이름과 오류 형식은 구현 전 작은 계약으로 확정한다.

### C. 업무 해석: 질문의 조건을 한 번에 적용

수정 위치는 업무 카탈로그 원본과 `agent_infrastructure/hermes_runtime.py`의 관리형 `exdigm-work` 지침이다. 원칙은 짧게 정리하고, 해당 업무만의 의미는 카탈로그에 둔다.

스킬에서 실제로 행동을 바꿀 내용은 다음 네 가지다.

1. 질문의 업무 대상·기간·상태·출처를 유지하고, 확인된 조건을 같은 조회에 함께 적용한다. 필요한 조건을 모르면 schema나 카탈로그로 먼저 해결한다.
2. 목록에는 긴 본문을 포함하지 않는다. 건수·짧은 목록·선택한 상세 순서 중 질문에 필요한 단계만 사용한다. 건수와 목록을 매번 기계적으로 두 번 읽지 않는다.
3. 조건이 맞는 정상 조회의 0건은 유효한 답이다. `ambiguous`, 권한 오류, 413, 부분 페이지와 구분하며 다른 출처로 자동 확대하지 않는다.
4. 확인된 출처와 기간, 실제 읽은 범위만 답한다. 업무 DB만 확인했다면 개인 메일·캘린더까지 확인했다고 말하지 않는다.

면접 일정의 카탈로그 연결은 실제 모델 정의에 맞춰 보완한다. 일정 질문이 `Interview` 기록에만 연결되지 않고 `ActionItem`과 일정 설정 업무 유형으로 이어져야 한다.

- `schedule_pre_meet`, `schedule_interview`의 `done`은 일정 설정 작업 완료를 뜻한다. 면접 자체가 끝났다는 뜻과 혼동하지 않는다.
- `pre_meeting`, `interview_round`의 진행 기록과 일정 설정 기록을 구분한다.
- “현재 잡혀 있는 일정”과 “기간 중 일정을 잡은 이력”은 다를 수 있다. 현재 상태는 최신 일정·변경·취소를 포함한 실제 모델 규칙을 따른다.
- 과거 9월 일정이 최신 기록에서 10월로 변경된 경우, 과거 기록에 9월 필터만 적용해 현재 9월 일정으로 답하면 안 된다. 최신 상태 판정에 필요한 관계 조회는 작은 단계로 추가하고 마지막 판정까지 같은 질문 조건을 유지한다.
- 식별자와 특정 월을 스킬에 고정하지 않는다. 유형·필드는 조회하고 기간은 사용자 표현과 업무 시간대에서 구한다.
- 월 범위는 현지 시간대의 월 시작 이상, 다음 달 시작 미만으로 표현한다.

### D. 긴 대화: 범위와 근거를 다시 확인할 수 있게 함

SOUL에는 다음 짧은 행동 기준만 남긴다. 상세 조회법과 업무 용어를 모두 복사해 시스템 지침을 키우지 않는다.

- Exdigm 업무 질문은 Exdigm을 기본 근거로 삼고, 다른 출처는 사용자가 요청했거나 현재 과업에 포함된 경우에 사용한다.
- 성공한 조회의 0건과 조회 실패를 구분한다.
- 현재 문맥에서 질문 조건이나 확인 근거가 빠졌으면 업무 스킬과 필요한 소량의 조회를 다시 확인한다. 기억나지 않는 확인을 완료 사실로 만들지 않는다.

Hermes 압축기의 내부 동작이나 자동 재주입 기능은 이번에 새로 만들지 않는다. 짧은 상시 지침과 작은 응답으로 개선되는지 실제 긴 세션에서 확인한다. 압축 뒤에도 범위를 잃는다면 해당 경로는 미해결로 남기고, 압축기·모델에 대한 다음 조사 대상으로 분리한다.

## 5. 최소 구현 판단과 공식 실행 경로

현재 경로는 `Telegram 질문 → Hermes/SOUL → exdigm-work → code_query → orm_read → /agent/orm/read/ → 직원 권한 적용 DB 조회 → FastMCP 응답 → Hermes 답변`이다. 업무 동작은 기존 `exdigm_request` 계약 실행 분기를 유지한다.

| 대상 | 재사용·추가 | 최소 구현 판단 |
|---|---|---|
| 중복 전송 | 기존 도구 등록의 SDK 옵션 사용 | 5단계에서 멈춤 — 설치된 MCP 1.26.0의 `structured_output` 동작 확인 |
| 목록 크기·페이지 | 기존 ORM 조회와 `_page_payload`, `MAX_RESULT_BYTES` 보강 | 2단계에서 멈춤 — 현재 공통 조회에 동일 책임이 있음 |
| 건수 확인 | 기존 `aggregates`의 `count` | 2단계에서 멈춤 — 별도 count 도구 불필요 |
| 긴 텍스트 범위 | 같은 권한 경로에 선택 입력과 범위 메타데이터만 추가 | 기존 ORM에는 없음. `code_query`의 부분 읽기 형태를 참고하되 DB 조회는 기존 ORM 내부에 둠. 범용 텍스트 범위 기능만 최소 추가 |
| 업무 의미·지침 | 기존 카탈로그, 관리형 스킬·SOUL 생성기 수정 | 2단계에서 멈춤 — 중복 문서·독립 프롬프트 저장소 불필요 |

확인한 파일은 `agent_infrastructure/exdigm_mcp/server.py`, `agent_infrastructure/hermes_runtime.py`, `hermes_integration/orm_read.py`, `projects/models.py`, 기존 code_knowledge 카탈로그·테스트다. 구현 전 최신 코드에서 입력 키·호출자·기존 테스트를 다시 확인한다. 긴 텍스트 범위 기능은 기존 해결책 부재와 SDK·표준 기능의 책임 범위를 확인한 작은 계약 검토 후에만 작성한다.

## 6. 순서와 통과 기준

| 단계 | 결과물 | 다음 단계로 가는 기준 |
|---|---|---|
| 1. 기준선 고정 | 같은 모델·질문·권한으로 원래 실패 경로와 정상 조회를 재현할 평가 사례 | 기대 건수·출처·권한과 도구 출력 측정 위치가 확정됨 |
| 2. 응답 수정 | 한 번만 전달되는 MCP 결과, 크기로 나뉘는 ORM 페이지, 명시적 긴 본문 읽기 | 기존 권한·집계·오류 계약과 새로운 크기·페이지 검증 통과 |
| 3. 의미·지침 수정 | 카탈로그 연결과 짧은 업무 조회·종료 기준 | 스킬 리뷰, 상위 지침 변경 검토, 생성물 반영 검증 통과 |
| 4. 실제 에이전트 검증 | 새 세션·긴 대화·압축 이후의 같은 업무 답변 | 아래 사례와 기준을 같은 모델로 충족 |
| 5. 운영 반영 | 승인된 하나의 커밋과 공식 앱·Hermes 배포 | 운영의 실제 질문에서 응답·권한·보존 상태 확인 |

코드 검증은 기존 `tests/test_hermes_orm_read.py`, `tests/test_new_hermes_runtime.py`, 관련 code_knowledge 테스트를 보강한다. 원격 공식 테스트 진입점을 사용하고 `HERMES_INTEGRATION_ENABLED=true`를 적용한다. 기존 긴 필드 413 검사는 삭제하거나 느슨하게 바꾸지 않는다. 실제 SDK 전송 시험을 추가하고 코드 변경은 `code-review-loop`를 거친다. 운영 DB에는 테스트 데이터를 쓰지 않는다.

실제 에이전트 평가는 기존 제품 런타임과 개발 전용 데이터·프로필을 사용한다. 운영 Agent key·Telegram 봇·개인 메일 자격증명을 개발 평가에 복사하지 않는다. 모델 접속 등 필수 시험 조건을 확보할 수 없으면 단위 검사 통과와 실제 에이전트 미검증을 나누어 보고한다.

| 평가 사례 | 반드시 확인할 결과 |
|---|---|
| 원래 질문과 표현을 바꾼 질문 | 같은 기간·업무 의미로 조회하고 실제 0건을 정확히 설명 |
| 일정 1건·여러 건 | 대상·시각·상태를 작은 목록으로 정확히 전달 |
| 진행 기록·상태 되돌림·미확정·취소·일정 변경 | 현행 모델 규칙에 따라 실제 일정과 구분 |
| 월 경계·다른 시간대·날짜 없음 | 다음 달 0시를 포함하지 않고 NULL을 일정으로 오인하지 않음 |
| 동일 시각 다수·한글·긴 본문 | 크기 제한과 페이지 이동이 정적인 데이터에서 누락·중복 없이 동작 |
| 긴 본문 명시 요청 | 필요한 범위를 이어 읽고 부분 결과를 전체처럼 말하지 않음 |
| 직원 권한 차이·차단 필드 | 권한 밖의 행·비밀값이 본문·건수·오류 메타데이터로 새지 않음 |
| 긴 기존 대화·강제 압축 뒤 질문 | 질문의 기간·대상·출처를 유지하고 없는 근거를 완료 사실로 만들지 않음 |
| 개인 메일을 명시한 별도 요청 | 허용된 일반 기능이 유지되고 필요한 출처만 사용 |

초기 인수 기준은 아래와 같다. 원래 질문과 바꿔 말한 질문을 각 3회씩 새 세션·긴 대화·압축 이후 조건에서 반복한다. 전체 조합의 성공을 보장하는 숫자가 아니라, 이번 변경을 통과시키기 위한 최소 반복 확인이다.

- 답변 정확도·조회 범위·권한·근거 표시: 모든 평가 사례 통과.
- 단순 Exdigm 일정 조회에서 터미널·직접 IMAP·자격증명 파일 읽기: 0회.
- 원래 질문의 조회 결과: 같은 권한·같은 시점의 공식 정답과 일치. 개발 사례는 통제한 데이터의 정답과 일치.
- 일반 행 조회 최종 도구 출력: 각 16 KiB 이하. 동일 데이터 이중 직렬화: 0회.
- 원래 질문의 새 세션에서 조회 도구 결과 누적량: 우선 12,000토큰 이하 목표. 토크나이저·추정 방식을 명시하고 실제 전체 컨텍스트와 구분. 초과 시 근거·중복·불필요 필드를 검토하고 자동으로 목표를 완화하지 않음.
- 새 세션의 이 단순 질문 때문에 발생하는 자동 압축: 0회. 긴 대화 시험은 압축 자체를 금지하지 않고 압축 뒤의 정확성과 범위 보존을 평가.
- 도구 횟수는 고유 호출 ID로 센다. 실제 모델 지연·최종 입력 토큰·오류·반복 조회를 함께 비교하며 속도만 좋아져도 통과시키지 않음.

운영 배포는 별도 승인 단계다. 공식 `scripts/deploy/deploy.sh prod`로 앱을 반영한 후 필요한 `scripts/deploy/deploy_hermes.sh prod <commit>` 절차로 관리형 파일과 MCP 소스를 맞춘다. 정확한 인자·영향은 최신 배포 스킬에서 다시 확인한다. Hermes 재생성은 활성 대화에 영향을 줄 수 있으므로 적용 시점과 대상 범위를 확인하고, 메모리·개인 스킬·작업공간·키·기록의 보존을 전후 검증한다.

## 7. 별도로 처리할 확인 사항

### 일일 초기화 시간대 보완

현재 일일 리셋 기능은 존재한다. 다만 관리형 설정의 `timezone: Asia/Seoul`을 사용하는 일반 시간 함수와, 컨테이너의 UTC `datetime.now()`를 사용하는 세션 만료 함수가 다르다. 같은 컨테이너에서 두 함수의 실제 반환 시각을 비교했고, 만료 로그 `2026-09-15 04:01:51` UTC와 DB 종료 시각 `2026-09-15 13:01:51` KST가 일치했다. 만료 감시는 기본 5분 주기이며 진행 중인 작업을 보호하는 조건도 있으므로 정각 강제 종료로 설명하지 않는다.

후속 구현에서는 한국 시간 새벽 4시라는 의도와 실제 세션 만료 시계를 일치시키는 최소 변경을 검토한다. 관리형 컨테이너의 시간대 공급 경로부터 확인하고, Hermes 본체의 직접 수정이나 두 번째 리셋 스케줄러를 추가하지 않는다. 기존 시간 기록·활성 세션 전환·예약 작업에 미치는 영향을 확인한 뒤 서울 시간 04:00 경계 전후와 실제 만료를 검증한다. 메모리·작업공간·과거 기록 보존 조건은 유지한다. 이 항목도 현재는 조사와 개선 제안이며 운영 변경은 수행하지 않았다.

### 인증값 후속 조치

조사 중 개인 메일 설정의 인증값이 당시 도구 응답에 평문으로 들어간 사실을 확인했다. 값은 이 문서·GBrain·새 로그에 복사하지 않는다. 해당 인증값의 폐기·재발급과 필요한 범위의 기록 정리는 별도 승인·사용자 인증이 필요한 후속 조치로 남긴다. 이번 개선안 작성으로 교체나 기록 삭제가 수행되지는 않는다.

개발 SDK·공식 ORM과 실제 모델의 검증 결과는 아래 재개 정보와 구현·리뷰 근거에 기록한다. 개발 시험의 통과와 운영 반영 후 재발 확인은 구분하며, 모델 교체 여부도 전송부 검사만으로 결정하지 않는다.

## 9. 구현·리뷰 근거

### 기준선과 검증 환경

- 공식 평가 경로는 관리형 skill/SOUL → 공식 Hermes AIAgent/MCP 초기화 → 기존 MCP → 실제 HTTPS Django `/agent/orm/read/` → 개발 전용 시험 DB다. 별도 답변 에이전트나 업무 조회 우회 경로를 제품에 추가하지 않았다.
- 시험 DB와 접속 역할을 각각 `exdigm_debug_test`, `exdigm_debug`로 확인하고 시험 사용자·일정을 만들었다가 지운다. 기존 공용 pytest 잠금을 잡아 다른 검증의 DB 초기화와 충돌하지 않게 한다. 운영 DB·직원 Agent key·Telegram·개인 메일은 시험에 사용하지 않는다.
- 모델 공급자 연결만 기존 공급자 인증으로 사용한다. 공식 image digest, Gemini 3.8 Flash, 기본 반복 상한과 100,000토큰 압축 임계치는 유지한다. 시험 메시지는 Telegram으로 보내지 않는다.
- 초기 시험 준비 중 MCP 초기화 누락, 시험 네트워크·인증서 신뢰 설정 문제를 각각 수정했다. 이 실행은 정상 경로 개선 효과의 평가에서 제외한다. TLS 검증은 끄지 않고 시험 CA를 시험 컨테이너에만 공급한다.
- 기존 시험 DB에 ActionType 시드 23개가 없어 초기 기준선 2건이 실패했다. 개발 역할의 CREATE DATABASE 권한 부족을 확인한 뒤 권한을 높이지 않고 정본 migration 시드의 누락분만 기존 시험 DB에 복원했다. 운영 데이터는 변경하지 않았다.
- 기존 notification catalog의 hint 16개는 기존 최대 10개 계약과 충돌했다. 중복 모델·함수·검사 위치를 aliases/inspect로 옮겨 검색 연결을 보존했고 해당 6개 이름의 조회를 검증했다.
