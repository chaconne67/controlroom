## 문제해결 게이트 기록

### 현상 잠금

- 필수 결과: 대상 후보자에 김두영의 실제 정보와 이력서가 표시되고, 다른 사람의 입력이 그 정보를 덮어쓰지 않아야 한다.
- 관측 현상: 표시 이름·현재 이력서·생년·경력과 기존 제출용 김두영 이력서가 서로 맞지 않는다.
- 원래 경로: 이메일 첨부 → 원문 추출 → 연락처 매칭 → 이력서 저장 → 후보자 현재 정보 갱신 → 운영 상세 화면.
- 완료 조건: 데이터 복구와 매칭 책임 수정 후 공식 저장 경로의 실패 사례·변형·정상 사례를 검증하고, 정확한 운영 상세 화면에서 결과를 확인한다.

### 연속 질문

1. 대상 후보자의 현재 정보가 홍길동 정보인 이유는 무엇인가? → 김두영 후보자에 홍길동 이력서가 연결되어 현재 정보로 쓰이기 때문이다. 현재 포인터·JSON·화면으로 확인.
2. 김두영 후보자에 홍길동 이력서가 연결되어 현재 정보로 쓰이는 이유는 무엇인가? → 섞인 연락처가 같은 사람의 근거로 사용되기 때문이다. 현재 공식 `identify_candidate`는 해당 홍길동 JSON을 대상 후보자에 이메일로 매칭한다. 확인.
3. 섞인 연락처가 같은 사람의 근거로 사용되는 이유는 무엇인가? → 매칭 코드가 전화번호의 여러 후보자 충돌과 이메일 불일치를 검사하지 않고 한 후보자를 선택하기 때문이다. `candidates/services/candidate_identity.py`의 이메일 우선·전화번호 fallback 구현으로 확인.

현재 표시 이름은 마지막 직접 이름 저장으로 설명된다. 두 번째 직접 저장의 의도와 과거 유현필 원문에서 홍길동 추출값이 만들어진 원인은 미검증이다. 연락처 매칭 결함과 혼동하지 않는다.

### 버드뷰와 결과 대조

- 정상 책임: 본인 확인은 같은 사람으로 판정할 근거를 제공하고, 저장 단계는 그 판정에 따라 현재 정보를 갱신한다.
- 최초 통제 가능한 이탈 후보: 연락처가 충돌하는 상황을 확실한 본인 확인으로 취급하는 매칭 판단.
- 이탈 전파: 잘못 연결된 Resume의 연락처가 Candidate에 남고, 후속 입력이 그 이메일로 다시 매칭된다.
- 소비자: 현재 프로필 선택·갱신, 프로젝트에 후보자 추가할 때의 최신 이력서 동기화, 후보자 상세 화면.
- 두 조사 결과는 잘못된 이력서 연결에 관해 일치한다. 표시 이름은 별도 저장 이력이 원인이다.

### 근본 원인 판정 상태

잘못 연결된 자료와 연락처를 통해 실패가 전파되는 실행 구조는 확인했다. 이 구조를 제거하면 정상 결과가 반복 생산되는지, 변형 사례도 막히는지는 수정 후 검증이 필요하다. 전체 근본 해결과 재발 닫힘은 아직 판정하지 않는다.

## 승인된 통합 변경

### 1. 자동 연결 판단 수정

- 대상: `candidates/services/candidate_identity.py`, `data_extraction/services/save.py`, 필요한 신원 충돌 상태 정의를 위한 `data_extraction/services/data_decision_policy.py`. 직접 소비자인 `data_extraction/services/multi_candidate.py`와 `data_extraction/services/next_actions.py`에도 같은 충돌 판단·종결 상태를 연결한다.
- 기존 이메일 우선 매칭과, 이름·생년이 달라도 충돌 없는 본인 연락처로 동일인을 찾는 동작은 보존한다.
- 전화번호 fallback에서 여러 후보자가 나오거나, 유효한 입력 이메일과 선택 후보자의 유효한 이메일이 다르면 자동 연결을 보류한다.
- 보류는 Candidate 생성·갱신 전에 결정한다. 원문·구조화 결과와 구체적 사유를 기존 FileData 보류 저장 경로에 남기고, 자동 재시도와 중복 후보자 생성을 막는다.
- 본인 확인을 위해 사용자가 직접 선택한 수동 갱신 경로는 보존한다.
- 부작용: 이메일이 바뀌었지만 전화번호만 같은 정상 후보자도 자동 연결이 보류될 수 있다. 기존 후보자를 사람이 확인해 선택하는 절차가 필요하다.

### 2. 공식 복구 진입점 추가와 개발 DB 검증

- 필요한 신규 진입점: `candidates/management/commands/repair_candidate_resume_identity.py`.
- 후보자, 프로필 기준 Resume, 본인 연락처 기준 Resume, 제외할 Resume을 명시하는 좁은 Django 명령으로 만든다.
- 기본은 dry-run이다. 명시적 적용 옵션이 있어야 데이터가 바뀐다.
- 기존 최신 이력서 동기화 함수, 수동 값 보호, Django transaction을 재사용한다. 운영 셸에서 임의 SQL로 값을 바꾸지 않는다.
- 적용 전에 지정한 기록의 소속·상태·본문 근거와 다른 후보자의 현재 포인터를 확인한다. 대상이 달라졌거나 모순이 있으면 중단한다.
- 한 transaction 안에서 잘못된 연결 제외, 이름·연락처 복구, 올바른 현재 정보 갱신을 처리한다. 실패하면 전부 rollback한다.
- 실제 값은 문서·Git·일반 로그에 쓰지 않는다. 필요한 복구 전 상태는 서버의 비공개 증거에 최소한으로 보존한다.

최소 구현 게이트의 근거: 기존 `identify_candidate`, `save_pipeline_result`, 최신 프로필 동기화와 FileData 보류 writer를 재사용한다. 원격 management command 목록과 `repair.*candidate`, `detach.*resume` 검색에서 이 작업의 기존 복구 진입점은 찾지 못했다. 별도 라이브러리·DB·브라우저 runner 없이 Django 기본 명령을 얇게 연결한다. 실제 코드 작성 직전 최종 단계·근거를 다시 출력한다.

### 3. 대상 후보자 한 명의 운영 데이터 복구

| 복구 요소 | 기준 기록 |
|---|---|
| 이름·영문 이름·생년·경력·학력·현재 이력서 | `fec608d9-642f-4946-92c8-ac0979ec4dc5` 김두영 수정 DOCX |
| 실제 이메일·전화번호 | `e9ca8dd6-c108-4cf8-b89d-cbfcefa1601c` 김두영 원본 PDF |

- 제외 기록의 원문·추출 JSON·이력은 삭제하지 않는다. 후보자 연결과 현재 선택 가능 상태만 정리한다.

- 검증된 명령이 운영에 반영된 뒤 운영 경로에서 먼저 dry-run으로 변경 내용을 대조하고 적용한다.

### 4. 검사·리뷰·문서·커밋

- 기존 검사 파일의 기대값은 유지하고, 연락처 충돌·반복 처리·정상 홍길동·명시적 수동 선택에 대한 회귀 검사를 추가한다.
- 복구 명령 검사는 새 `tests/test_repair_candidate_resume_identity.py`에서 실제 Django 명령을 호출한다. dry-run 무변경, 지정한 기록만 복구, 실패 rollback, 재실행 보존을 검증한다.
- 테스트 기준 항목 준비는 `tests/action_type_fixtures.py`에서 기존 seed 정의를 재사용하며, `tests/test_application_lifecycle.py`와 복구 명령 검사에서만 import한다. 보호 계약에 포함된 `tests/conftest.py`는 시작 상태와 byte 단위로 같다. 운영 데이터와 권한은 건드리지 않는다.
- 같은 공식 저장 진입점에서 새 FileData의 보류 사유와 기존 후보자·관계의 보존을 확인한다.
