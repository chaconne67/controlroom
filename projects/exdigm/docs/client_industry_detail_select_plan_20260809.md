# 고객사 세부업종 선택 전환 통합 계획

## 목표

- 고객사 업종 대분류 17개는 유지한다.
- 세부업종 직접 입력을 대분류별 목록 선택으로 바꾼다.
- 세부업종은 선택하지 않아도 고객사를 저장할 수 있게 한다.
- 고객사에 저장된 세부업종은 기존 자동 게시의 사이트별 업종 변환 근거로 계속 사용한다.

## 확인된 현재 상태

- `Client.industry`는 16개 표준 대분류와 `기타` 중 하나를 저장한다.
- `Client.industry_detail`은 빈 값을 허용하는 문자열 필드다.
- `ClientForm`만 세부업종을 필수 자유 입력으로 강제한다.
- BusinessPeople 실측 지도에는 대분류 10개와 세부업종 211개가 있다. 중복 명칭 2개를 합치면 고객사 선택값은 209개다.
- 현재 고객사 대분류 17개에 직접 대응하는 세부업종 정본은 없다.
- 기존 자동 게시 경로는 고객사 세부업종 문자열을 사이트별 실제 옵션으로 변환한다.

## 승인할 변경 범위

### 도메인 목록

- BusinessPeople 실측 세부업종 211개를 어휘 원천으로 사용하고, 중복 명칭은 한 선택값으로 합친다.
- 각 세부업종을 현재 고객사 대분류 17개 중 업무 의미가 가장 가까운 한 곳에 배치한다.
- 여러 대분류에 자연스럽게 속하는 표현만 중복 노출할 수 있다.
- 사이트 옵션 ID나 사이트 전용 대분류명은 고객사 저장값으로 사용하지 않는다.

### 폼과 검증

- 세부업종 필드를 Django 기본 `select`로 렌더링한다.
- 첫 옵션은 `선택 안 함`으로 두고 필수 표시를 제거한다.
- 선택한 세부업종이 현재 대분류의 허용 목록에 없으면 서버에서 저장을 거부한다.
- 기존 고객사의 자유 입력값이 새 목록에 없으면 수정 화면에서 `기존 값`으로만 보존한다.
- 사용자가 대분류를 바꾸면 기존 세부업종 선택을 지우고 새 목록을 표시한다.

### 화면 상호작용 계약

- 사용자 의도: `업종`을 선택한 뒤 그 범위 안에서 `세부 업종`을 선택하거나 비워 둔다.
- 입력의 정본: 고객사 대분류와 승인된 대분류별 세부업종표다.
- 상태 전이: 화면 준비 → 대분류 변경 → 세부업종 목록 교체 → 저장 성공 또는 검증 오류다.
- 변경 경계: `세부 업종` 선택지와 안내 문구만 바뀐다.
- 불변조건: 다른 폼 입력, URL, 스크롤, 담당자 목록은 대분류 변경으로 바뀌지 않는다.
- 실패: 허용되지 않은 조합은 세부업종 아래에 오류를 표시하고 모든 입력을 보존한다.

## 구현 위치

- `clients/models.py`
  - 고객사 대분류별 세부업종표를 고객사 도메인 데이터로 둔다.
- `clients/forms.py`
  - 선택 컨트롤, 선택 사항 처리, 대분류·세부업종 조합 검증을 담당한다.
- `clients/templates/clients/client_form.html`
  - 대분류 변경 시 세부업종 선택지만 교체하고 안내 문구를 갱신한다.
- `tests/test_clients_views_form.py`
  - 선택 사항 저장, 목록 렌더링, 올바른 조합, 잘못된 조합, 기존 값 보존을 검증한다.

## 최종 성공 경로

1. 고객사 등록 또는 수정 화면을 연다.
2. 서버가 현재 대분류에 맞는 세부업종 선택지를 렌더링한다.
3. 사용자가 대분류를 바꾸면 브라우저가 같은 정본 데이터로 선택지를 교체한다.
4. 사용자가 세부업종을 선택하거나 비워 둔 채 저장한다.
5. 서버가 대분류·세부업종 조합을 다시 검증한다.
6. 고객사를 저장하고 상세 화면으로 이동한다.

## 최소 구현 게이트

- 1단계: 세부업종을 선택 사항인 종속 목록으로 바꾸라는 요청에 꼭 필요하다.
- 2단계: `auto_posting/site_maps/businesspeople/industry-options.json`에 실측 어휘가 있으므로 새 어휘를 만들지 않고 재사용한다.
- 3단계: JSON 변환과 클라이언트 목록 교체에는 표준 기능을 사용한다.
- 4단계에서 멈춤: Django `ChoiceField`와 폼 검증, 기본 HTML `select`로 구현하며 새 의존성을 추가하지 않는다.

## SSP 수정 전 잠금

- ⓪ 최소 구현 게이트: 4단계에서 멈춤 — Django 폼과 기본 `select`가 선택·검증 계약을 제공한다.
- ① 현재 최종 경로: `client_create/client_update` → `ClientForm` → `client_form.html` → POST → `ClientForm.is_valid()` → `Client.save()` → 고객사 상세 화면이다.
- ② 병합 위치: 기존 `ClientForm`의 세부업종 필수 자유 입력과 같은 템플릿 필드 렌더링 단계에 병합한다.
- ③ 대체·정리 대상: 필수 `TextInput`과 필수 강제 코드를 선택 사항 `Select`와 조합 검증으로 대체한다. 별도 API나 두 번째 저장 경로는 만들지 않는다.
- ④ 검증 방법: 고객사 폼 집중 테스트, 같은 최종 경로의 등록·수정 POST, 개발 URL의 실제 대분류 변경·저장·오류 화면을 검증한다.

## 검증과 완료 조건

- 공용 잠금으로 `tests/test_clients_views_form.py`를 실행한다.
- 직접 관련 고객사 테스트를 추가로 실행한다.
- `uv run --locked python -m tools.code_knowledge catalog_update`를 실행한다.
- 개발 URL에서 등록·수정 화면을 직접 연다.
- 대분류 변경 전후 선택지, 선택하지 않은 저장, 유효한 선택 저장, 오류 시 입력 보존을 확인한다.
- 콘솔과 네트워크에 새 오류가 없어야 한다.
- 변경된 업종 규칙을 GBrain의 자동 게시 입력 계약과 사고 기록에 반영한다.
- 실행 동작과 자동 게시 입력 계약이 바뀌므로 `code-review-loop`로 승인 범위 안의 결함을 재검토한다.
- 검증과 리뷰가 끝난 변경만 커밋한다.
- 주인님의 추가 승인에 따라 운영 배포를 실행하고 운영 화면에서 같은 선택 흐름을 다시 확인한다.
