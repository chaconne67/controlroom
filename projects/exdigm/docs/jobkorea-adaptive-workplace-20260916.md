## 구현 경로와 책임

기존 payload builder → AutoPosting.main → Jobkorea.run/_fill → 근무지 목표 실행 → 실제 입력 확인 → 기존 후속 단계로 연결한다. 신규 서비스·러너·DB 모델·의존성은 없다.

- workflow: 원문 근무지와 사이트 선택값을 분리한다. 정적 지역 코드표 일치를 게시 전 필수 조건으로 요구하지 않는다. 실행 중 의미 판단·행동 선택·최종 의미 검토는 기존 제품 LLM 호출부를 재사용한다.
- common: 현재 근무지 영역의 보이는 컨트롤과 상태를 관찰하고, 이번 관찰에서 발급한 참조만 조작한다. 임의 코드·셀렉터 실행이나 영역 밖 클릭을 허용하지 않는다.
- Jobkorea: 주소·지역의 목표, 허용 조작 영역, 실제 주소·선택 지역 검증을 제공한다. 기존 주소 도구를 재사용하고 코드값으로 상위 지역을 추론하는 특수 분기를 제거한다.
- 알 수 없는 선택지는 재관찰/판단 대상이다. 실제 필수 사실 부족, 안전하지 않은 조작, 예산 소진, 결과 검증 불가는 명시적으로 중단한다. 내용 생략이나 임의 주소로 성공시키지 않는다.
- LLM 호출 수·시간·토큰과 행동/실제 결과를 근무지 증거로 남긴다. 새 정보 없이 같은 행동을 반복하지 않는다.

최소 구현 게이트: 2단계에서 멈춤. 기존 common.llm, AutoPostingCommon.page_session, Jobkorea._set_address, 공식 명령과 테스트를 재사용한다. 검색 근거: _select_region, _select_projected_modal_options, _jobkorea_region_options, _jobkorea_projection_defects, posting_form_snapshot, call_llm_result, gemini_generate_content.

### 구현한 비용·안전 경계

- 기존 선택 힌트가 현재 화면과 맞으면 기계적 입력을 재사용한다. 힌트는 현재 원문의 의미가 맞다는 증거가 아니므로 마지막 의미 검증 1회는 생략하지 않는다.
- 낯선 상태에서는 LLM이 현재 선택지로 목표 주소·추가 지역을 정하고, 스크립트가 이후 동작을 실행한다. 시험의 명확한 사례는 목표 판단 1회 + 독립 검증 1회였다. 모든 변칙이 2회에 끝난다는 보장은 아니다.
- 닫힌 창에서 사라진 안내문도 의미 판단에 유지한다. 행동 참조는 현재 화면 것만 사용한다.
- 최종 검증은 원래 원문과 실제 반영값을 사용하며, 실행 모델의 성공 주장이나 클릭 성공을 근거로 삼지 않는다. 근무지 확정은 다른 입력 뒤, 전체 확인 직전에 실행한다.
- 기본 근무지 예산은 180초와 제한된 판단·행동 횟수(설정 기본 16회)다. 같은 관찰에서 실패한 같은 행동을 반복하지 않으며 응답 형식 보정은 1회다. 시간·토큰을 기록하고 초과·필수 정보 부족은 실패로 남긴다.
- 주소 조회가 실패하면 기존 주소를 덮어쓰지 않는다. 관찰 밖 참조, 제출 버튼, 이동 링크, 임의 셀렉터·코드 실행은 막는다.
- 이미 검증한 주소 입력 도구는 재사용한다. 새로운 사이트 전체 탐색기, 임의 팝업/iframe 처리, 자가 코드 수정·자가 배포·성공 전략의 영구 학습 저장소는 만들지 않았다.

## 검증과 완료 경계

기존 기준선과 새 근무지 변형을 같은 공식 테스트 경로에서 검사한다. 정적 코드표에 없는 입력, ID 변경, 다른 탭, 제한 안내, 기존 값 재사용, 잘못된/모호한 LLM 응답, 무진전, 예산 소진, 조작 범위 차단을 포함한다. 공식 autoposting 명령을 격리 브라우저 페이지와 연결한 dry 검증으로 실제 DOM 반영과 미게시를 확인한다.

## 재개 정보

현재 상태는 **코드 구현·격리 검증 완료, 실제 사이트 검증 대기**다. 운영 장애의 재발이 닫혔다고 판정하지 않는다.

설계 결정은 GBrain 공용 `project/exdigm-auto-posting-process-policy`의 「근무지 실행 중 의미 판단 계약 (2026-09-16)」에 기존 내용을 보존해 기록하고 재조회로 확인했다. 실행 상태 정본은 이 계획이며 GBrain 기록을 운영 활성화로 해석하지 않는다.

- projects/services/auto_posting_workflow.py

앱 커밋·push·배포·실제 잡코리아 로그인·공고 게시/수정/마감은 하지 않았다. 다른 작업이 이 dirty 상태를 포함해 배포하지 않도록 먼저 이 계획과 실제 Git diff를 확인해야 한다.

다음 행동은 실제 계정의 잡코리아 화면에서 저장·게시하지 않는 입력 검증이다. 추가 승인과 인증을 사용할 수 있는 공식 검증 경로가 필요하다. 운영 인증을 개발 DB·프로필에 복사하거나 운영 checkout을 임시 수정하는 우회는 하지 않는다. 승인 뒤 원래 실패 사례, 기존 성공 사례, 다른 지역 변형을 실제 화면에서 확인하고, 성공한 코드만 별도 승인된 배포 절차로 넘긴다.
